A classe de domínio

O estoque guarda os saldos num mapa privado. O identificador deve ser não nulo e conter algum caractere além de espaços; a quantidade de uma movimentação precisa ser positiva. O recebimento calcula o próximo valor antes da atribuição e usa uma operação que detecta overflow. A retirada consulta, decide e altera dentro do mesmo método, mas ainda não está protegida para vários chamadores simultâneos. Esse limite corresponde à versão sequencial do laboratório.

A consulta devolve uma fotografia. Isso torna possível comparar uma observação anterior com outra depois da movimentação, sem permitir que o usuário altere o mapa interno. No modelo atual, os elementos da fotografia são strings e inteiros empacotados. Se você trocar quantidades por objetos mutáveis, reveja a política de exposição. O nome do método não garante independência: ela vem da implementação e precisa ser comprovada pelo teste.

import java.util.Collections;
import java.util.LinkedHashMap;
import java.util.Map;

public class Estoque {
    private final Map<String, Integer> itens = new LinkedHashMap<>();
    private static void validar(String id, int quantidade) {
        if (id == null || id.trim().isEmpty() || quantidade <= 0) {
            throw new IllegalArgumentException("Dados inválidos");
        }
    }
    public void receber(String id, int quantidade) {
        validar(id, quantidade);
        int novo = Math.addExact(itens.getOrDefault(id, 0), quantidade);
        itens.put(id, novo);
    }
    public boolean retirar(String id, int quantidade) {
        validar(id, quantidade);
        int atual = itens.getOrDefault(id, 0);
        if (quantidade > atual) return false;
        itens.put(id, atual - quantidade);
        return true;
    }
    public Map<String, Integer> consultar() {
        return Collections.unmodifiableMap(new LinkedHashMap<>(itens));
    }
}

A interface de console

O fluxo principal interpreta linhas completas. Isso evita misturar leitura de tokens e leitura de fim de linha no menu. Um comando tem ação, identificador e quantidade, separados por espaços. Os comandos especiais listar e fim não precisam desses dois argumentos. A condição de leitura verifica se ainda existe uma linha; assim, a entrada pode terminar tanto por fim quanto pelo esgotamento dos dados fornecidos.

Um formato inválido é tratado antes de chamar o domínio. Uma quantidade textual não numérica recebe uma orientação própria. Uma quantidade inteira fora da regra é recusada pela classe Estoque. O código não usa um catch geral para converter falhas inesperadas em sucesso. Essa distinção permite que os testes de domínio continuem independentes da apresentação de mensagens no console.

import java.util.Scanner;

public class Main {
    public static void main(String[] args) {
        Estoque estoque = new Estoque();
        Scanner entrada = new Scanner(System.in);
        System.out.println("Comandos: receber ID QTD | retirar ID QTD | listar | fim");
        while (entrada.hasNextLine()) {
            String linha = entrada.nextLine().trim();
            if (linha.equals("fim")) break;
            if (linha.equals("listar")) {
                System.out.println(estoque.consultar());
                continue;
            }
            String[] partes = linha.split("\s+");
            if (partes.length != 3 ||
                    !(partes[0].equals("receber") || partes[0].equals("retirar"))) {
                System.out.println("Comando inválido");
                continue;
            }
            try {
                int quantidade = Integer.parseInt(partes[2]);
                if (partes[0].equals("receber")) {
                    estoque.receber(partes[1], quantidade);
                    System.out.println("Recebimento concluído");
                } else {
                    System.out.println(estoque.retirar(partes[1], quantidade)
                        ? "Retirada concluída" : "Quantidade indisponível");
                }
            } catch (NumberFormatException erro) {
                System.out.println("Quantidade deve ser inteira");
            } catch (IllegalArgumentException erro) {
                System.out.println(erro.getMessage());
            } catch (ArithmeticException erro) {
                System.out.println("Quantidade excede o limite do estoque");
            }
        }
    }
}

Testes que acompanham o pacote

Os testes verificam recebimento, acumulação, retirada parcial e exata, recusa sem alteração, fotografia, proteção da consulta, independência entre instâncias, argumentos inválidos e overflow. Eles usam verificações explícitas e não dependem da opção -ea. O programa de teste termina com falha se uma expectativa não for satisfeita. A frase final só é apresentada depois de todas as verificações concluídas.

Cada expectativa descreve o comportamento observado. Não há acesso ao campo privado do estoque. Isso permite mudar a representação interna sem invalidar testes que ainda expressem o mesmo contrato. Quando uma regra de negócio mudar, revise conscientemente os cenários afetados, em vez de editar todas as saídas para fazer os testes passarem. Um teste que deixou de representar a necessidade do usuário precisa ser discutido, não apenas conservado por hábito.

import java.util.Map;

public class Testes {
    static int cenarios;
    static void conferir(boolean condicao, String nome) {
        if (!condicao) throw new AssertionError(nome);
        cenarios++;
    }
    public static void main(String[] args) {
        Estoque estoque = new Estoque();
        estoque.receber("A", 5);
        conferir(estoque.consultar().get("A") == 5, "Receber em estoque vazio");
        estoque.receber("A", 2);
        conferir(estoque.consultar().get("A") == 7, "Acumular recebimento");
        conferir(estoque.retirar("A", 3), "Aceitar retirada parcial");
        conferir(!estoque.retirar("A", 5) && estoque.consultar().get("A") == 4,
            "Recusa deve preservar saldo");
        Map<String, Integer> fotografia = estoque.consultar();
        estoque.receber("A", 1);
        conferir(fotografia.get("A") == 4, "Fotografia independente");
        boolean protegeu = false;
        try { fotografia.put("A", 99); }
        catch (UnsupportedOperationException esperado) { protegeu = true; }
        conferir(protegeu && estoque.consultar().get("A") == 5, "Proteger consulta");
        conferir(new Estoque().consultar().isEmpty(), "Instâncias independentes");
        conferir(estoque.retirar("A", 5) && estoque.consultar().get("A") == 0,
            "Aceitar retirada exata");
        boolean invalido = false;
        try { estoque.receber(" ", 1); }
        catch (IllegalArgumentException esperado) { invalido = true; }
        conferir(invalido, "Recusar identificador vazio");
        invalido = false;
        try { estoque.receber("A", 0); }
        catch (IllegalArgumentException esperado) { invalido = true; }
        conferir(invalido && estoque.consultar().get("A") == 0, "Recusar zero");
        estoque.receber("LIMITE", Integer.MAX_VALUE);
        boolean overflow = false;
        try { estoque.receber("LIMITE", 1); }
        catch (ArithmeticException esperado) { overflow = true; }
        conferir(overflow && estoque.consultar().get("LIMITE") == Integer.MAX_VALUE,
            "Overflow deve preservar estado");
        System.out.println(cenarios + " cenários verificados");
    }
}

Persistência, SQL e transações

Do arquivo para uma representação persistente

O tema 12 apresentou a importação em memória e o contrato de substituição. Este laboratório acrescenta o acesso real a arquivos em uma pasta de estudo. O programa local cria dados-estudo abaixo do diretório de execução, escreve um temporário em UTF-8, tenta substituição atômica e lê de volta. Ele compara o conteúdo recuperado com o esperado antes de confirmar a operação. Não usa arquivos pessoais como destino.

A substituição atômica depende do provedor e das condições do sistema de arquivos. O exemplo recusa a operação se essa opção não estiver disponível; não troca silenciosamente por outra garantia. A limpeza final trata apenas o temporário criado pelo próprio programa. O destino permanece para consulta. A demonstração é de representação e conferência, e não de backup, criptografia ou durabilidade garantida diante de qualquer falha física.

Baixar o laboratório local de arquivos (.zip)

import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.nio.file.AtomicMoveNotSupportedException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.Paths;
import java.nio.file.StandardCopyOption;
import java.util.Arrays;
import java.util.List;

public class Main {
    public static void main(String[] args) throws IOException {
        Path diretorio = Paths.get("dados-estudo");
        Files.createDirectories(diretorio);
        Path destino = diretorio.resolve("alunos.txt");
        Path temporario = Files.createTempFile(diretorio, "alunos-", ".tmp");
        List<String> linhas = Arrays.asList("versao=1", "A01;João;8", "A02;Ana;9");
        try {
            Files.write(temporario, linhas, StandardCharsets.UTF_8);
            try {
                Files.move(temporario, destino, StandardCopyOption.ATOMIC_MOVE,
                    StandardCopyOption.REPLACE_EXISTING);
            } catch (AtomicMoveNotSupportedException erro) {
                throw new IOException("Substituição atômica indisponível neste ambiente", erro);
            }
            List<String> recuperadas = Files.readAllLines(destino, StandardCharsets.UTF_8);
            if (!recuperadas.equals(linhas)) throw new IOException("Conferência divergente");
            System.out.println("Gravação e leitura conferidas");
            for (String linha : recuperadas) System.out.println(linha);
        } finally {
            Files.deleteIfExists(temporario);
        }
    }
}

Confirmar um conjunto de alterações

Uma transação delimita alterações que devem ser confirmadas ou desfeitas no armazenamento conforme o contrato. Em uma transferência entre dois estoques, retirar da origem e acrescentar ao destino não devem ser anunciados como sucesso se apenas um lado foi persistido. Defina a transação em torno do caso de uso, e não necessariamente em torno de cada método de acesso a dados. Confirme apenas depois de todas as operações exigidas concluídas.

Quando a operação falha, o código responsável pela transação precisa solicitar a reversão de acordo com o mecanismo usado e propagar um resultado coerente. Restaurar configuração de conexão e fechar recursos também fazem parte do ciclo de vida. Uma exceção na tentativa de rollback não deve apagar sem registro a falha que iniciou o problema. Concorrência no armazenamento

Uma sequência de consultar saldo e depois gravar um valor calculado pode sofrer conflito entre solicitações. O banco oferece níveis de isolamento, bloqueios e operações condicionais, mas o programa precisa escolher uma estratégia coerente. Uma atualização que só retira quando quantidade é suficiente pode usar a condição na própria instrução e conferir a quantidade de linhas afetadas. Esse resultado precisa ser interpretado como parte do contrato, não ignorado.

Isolamento não é uma palavra que garante qualquer comportamento desejado em todo banco. Escreva o cenário de duas solicitações disputando as últimas unidades e observe a garantia da estratégia adotada. Teste também conflito, timeout e repetição. Se a operação possui um identificador de pedido, considere uma restrição que permita reconhecer um pedido já aplicado. Repetir uma retirada porque uma resposta se perdeu pode duplicar o efeito sem essa política.

APIs HTTP e contratos de integração

Da chamada de método para uma troca de mensagens

Uma API HTTP permite que um cliente solicite operações por uma mensagem de rede. A troca possui método, endereço, cabeçalhos e, quando aplicável, corpo. A resposta possui status, cabeçalhos e corpo. Cada parte carrega um papel. Um texto com aparência de JSON não informa sozinho se a operação foi aceita, e uma conexão bem-sucedida não significa que a regra de negócio concluiu com sucesso.

Mantenha o contrato de domínio separado do transporte. O cliente envia um identificador e uma quantidade; a camada de entrada valida o formato e chama a operação de estoque. A resposta deve representar sucesso ou recusa de maneira consistente. Não exponha detalhes de banco ou exceções internas como se fossem a interface pública. O consumidor precisa saber o que pode tentar de novo e o que deve corrigir na solicitação.

Rotas, métodos e significado das operações

Uma rota identifica o recurso ou a operação disponibilizada. Um método expressa parte da intenção no protocolo. Leituras não devem produzir retiradas escondidas apenas porque uma URL foi acessada para consulta. A aplicação precisa definir quais chamadas alteram estado, quais podem ser repetidas com o mesmo efeito e como uma resposta perdida será investigada. Uma escolha coerente ajuda clientes, testes e ferramentas de observação.

Para uma primeira API do estoque, separe consulta de disponibilidade e solicitação de movimentação. Escreva exemplos de pedido aceito, argumento inválido, item inexistente e disponibilidade insuficiente. Defina o status e um corpo de resposta estável para cada classe de resultado. Não decida isso copiando o status do último exemplo que você viu: o contrato deve descrever o significado que seu consumidor poderá usar.

Formato JSON e validação de entrada

JSON possui regras de escape, tipos e estruturas. Não use split em vírgulas para interpretar um corpo geral, nem concatene strings arbitrárias para produzir JSON com entrada do usuário. Aspas, barras e quebras de linha tornam essa abordagem incorreta. Em uma aplicação com dados dinâmicos, use uma biblioteca de parsing e serialização configurada no projeto. Neste laboratório, o corpo de demonstração é um texto constante e não recebe campos arbitrários.

Limite o tamanho de entrada e defina o tratamento de campos ausentes, desconhecidos e nulos. O número JSON recebido ainda precisa corresponder ao tipo e à faixa do domínio. Uma string vazia não é automaticamente equivalente a ausência. Uma versão nova da API pode acrescentar campos, mas precisa de uma política de compatibilidade. Documente o que um cliente antigo continua podendo enviar e interpretar.

Laboratório local com servidor e cliente

O programa abaixo usa recursos do JDK 17 para criar um servidor apenas no endereço local 127.0.0.1 e numa porta escolhida pelo sistema. Em seguida, o próprio programa consulta a rota conhecida e outra inexistente, apresenta as respostas e encerra os recursos. Ele não publica um serviço na internet nem usa uma API de terceiros. O endereço só existe durante essa execução.

A rota /estado aceita GET e devolve um corpo constante. Um caminho diferente recebe 404; outro método recebe 405 com o cabeçalho Allow. A resposta usa tamanho em bytes e codificação UTF-8. O cliente tem limites de conexão e de solicitação. O exemplo depende da API HTTP posterior a Java 8, por isso deve ser executado no JDK local, e não no compilador atual do Playground. Consulte HttpClient.

Baixar o laboratório HTTP local (.zip)

import com.sun.net.httpserver.HttpServer;
import java.net.InetSocketAddress;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.time.Duration;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class Main {
    public static void main(String[] args) throws Exception {
        HttpServer servidor = HttpServer.create(new InetSocketAddress("127.0.0.1", 0), 0);
        ExecutorService executor = Executors.newFixedThreadPool(2);
        servidor.setExecutor(executor);
        servidor.createContext("/", troca -> {
            int status;
            String corpo;
            if (!troca.getRequestMethod().equals("GET")) {
                status = 405; corpo = "{\"erro\":\"metodo\"}";
                troca.getResponseHeaders().set("Allow", "GET");
            } else if (troca.getRequestURI().getPath().equals("/estado")) {
                status = 200; corpo = "{\"estado\":\"pronto\"}";
            } else {
                status = 404; corpo = "{\"erro\":\"rota\"}";
            }
            byte[] bytes = corpo.getBytes(StandardCharsets.UTF_8);
            troca.getResponseHeaders().set("Content-Type", "application/json; charset=UTF-8");
            troca.sendResponseHeaders(status, bytes.length);
            try (java.io.OutputStream saida = troca.getResponseBody()) { saida.write(bytes); }
            finally { troca.close(); }
        });
        try {
            servidor.start();
            HttpClient cliente = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(3)).build();
            for (String rota : new String[]{"/estado", "/ausente"}) {
                URI uri = URI.create("http://127.0.0.1:" + servidor.getAddress().getPort() + rota);
                HttpRequest pedido = HttpRequest.newBuilder(uri)
                    .timeout(Duration.ofSeconds(5)).GET().build();
                HttpResponse<String> resposta = cliente.send(pedido,
                    HttpResponse.BodyHandlers.ofString(StandardCharsets.UTF_8));
                System.out.println("GET " + rota + ": " + resposta.statusCode() + " " + resposta.body());
            }
        } finally {
            servidor.stop(0);
            executor.shutdownNow();
        }
    }
}

Conferir a resposta e o tipo do conteúdo

Execute o programa do pacote com o JDK local e compare as duas linhas esperadas. A consulta de /estado deve apresentar 200 e o estado pronto. A consulta de /ausente deve apresentar 404 e um corpo de erro. O cliente não deve tentar interpretar qualquer resposta como se tivesse a mesma estrutura do sucesso. Em uma integração real, confira também o tipo do conteúdo e trate a falha de parsing separadamente da falha de conexão.

Um status de erro HTTP ainda é uma resposta recebida do servidor. Ele difere de uma falha que impediu receber resposta, como timeout ou recusa de conexão. Essa distinção influencia uma tentativa posterior e a orientação ao usuário. Não troque todos esses casos por uma mensagem que diga apenas “sem internet”, pois a máquina pode estar conectada e o servidor pode ter recusado uma solicitação válida no transporte.

Timeout não decide o efeito produzido

Um cliente pode parar de esperar depois que a operação já foi aplicada no servidor. Reenviar uma retirada nesse momento pode descontar novamente. Se o domínio exige repetição segura, inclua uma identificação de operação e uma política para reconhecer o resultado anterior. A decisão não deve depender apenas da duração escolhida para o timeout. Conectividade, confirmação e efeito de negócio são observações diferentes.

Uma estratégia de repetição também deve ter limites. Repetir imediatamente sem controle pode aumentar a carga sobre um serviço que já está falhando. Só repita automaticamente operações e classes de falha para as quais o contrato permite isso. Registre a tentativa e mantenha uma forma de investigação. Para um primeiro laboratório, é suficiente distinguir claramente falha de transporte e resposta de recusa, antes de implementar repetição automática.

Browser, CORS e autenticação

Um programa Java local e um JavaScript em uma página não possuem exatamente as mesmas regras de acesso à rede. O navegador aplica políticas de origem e pode exigir uma autorização CORS do servidor para determinada troca. Isso não é resolvido acrescentando um cabeçalho de permissão arbitrário no pedido do cliente. A política de resposta pertence ao serviço que decide quais origens e operações aceita.

CORS também não substitui autenticação e autorização. Saber de onde uma página foi carregada não decide se uma pessoa pode retirar um item. Uma API real precisa identificar o chamador conforme seu modelo e verificar acesso à operação. Não inclua senhas, tokens reais ou chaves em exemplos publicados. Build, testes e entrega reproduzível

Reproduzir antes de automatizar

Um build reproduzível começa por instruções que outra pessoa consegue seguir. Registre a versão de Java, os fontes usados, o destino das classes e a classe principal. Uma ferramenta de build automatiza tarefas e resolve dependências declaradas. Ela não corrige sozinha uma classe pública no arquivo errado, uma operação de negócio inválida ou um teste que observa o resultado errado. Comece conferindo uma execução manual do caso pequeno. Depois faça a ferramenta repetir as mesmas propriedades e acrescente o que ela oferece de organização, sem perder a capacidade de explicar onde a compilação e os testes acontecem.

O projeto pode ser escrito com uma sintaxe, compilado para uma versão alvo e executado por uma JVM que precisa aceitar esse resultado. Usar um JDK recente não significa que você pode chamar qualquer API e ainda executar em um ambiente antigo. Se uma IDE compila uma chamada que o build recusa, compare o JDK selecionado e a versão alvo antes de suspeitar de um defeito na biblioteca. Não remova a restrição de versão apenas para aceitar o erro sem verificar o ambiente de destino. A mudança pode gerar um programa que sua pessoa usuária não consegue executar.

Maven e Gradle no percurso de estudo

Maven organiza um ciclo de vida com tarefas como compilação, teste e empacotamento. O arquivo de projeto declara dependências e configuração. Gradle oferece outra forma de descrever o build, com suas tarefas e mecanismos. Em ambos, mantenha versões e arquivos de configuração sob o mesmo controle do código. Estude uma ferramenta por vez. Reproduza o projeto integrador nela, preserve a sequência de testes e confira o artefato gerado. Não declare sucesso apenas porque a ferramenta terminou uma tarefa diferente da necessária: empacotar sem executar os testes não é a mesma verificação que testar a regra. Consulte os guias do Maven e a documentação do Gradle para relacionar os comandos ao ciclo de vida.

Dependências e arquivos de distribuição

Importar uma classe não obtém seu código automaticamente. Uma dependência externa precisa ser resolvida e disponibilizada na compilação e, quando necessária, na execução. Um JAR que contém só suas classes pode falhar se a distribuição não inclui as bibliotecas de runtime. O modo de empacotar deve corresponder ao comando de execução oferecido ao usuário. Se o programa pequeno funciona com a biblioteca padrão, não acrescente uma dependência apenas para substituir poucas linhas claras.

Pirâmide de verificações por responsabilidade

Um teste de domínio confere regras isoladas, como recusa que preserva saldo. Um teste de integração confere a colaboração com arquivo, banco ou outro componente real. Um teste de transporte confere rotas, corpo e status. Um teste de interface observa ações que a pessoa consegue realizar. Eles respondem a perguntas diferentes. Manter só o teste da tela pode tornar lento localizar uma falha aritmética, enquanto manter só um teste de método não comprova que o botão chama a operação correta.

No projeto integrador, comece pelos cenários do domínio. Ao acrescentar arquivo, inclua escrita e leitura de volta em diretório de teste. Ao acrescentar HTTP, teste consulta e erro de rota com o servidor real do laboratório. Evite que todos os casos dependam da internet ou de um serviço remoto não controlado. Uma indisponibilidade externa pode impedir o teste de uma integração, mas não deve apagar a evidência das regras locais já verificadas.

Dublês, relógio e aleatoriedade

Um dublê de teste substitui um colaborador para produzir uma situação controlada. Um substituto que sempre devolve sucesso não ajuda a conferir o caminho de recusa e pode criar uma confiança falsa sobre o que a integração real oferece.

Receba o relógio ou a data nos lugares que precisam decidir um prazo, e use uma semente conhecida quando o objetivo for repetir um sorteio de exercício. Não altere a regra de negócio apenas para facilitar um teste. Procure a fronteira onde o dado externo entra e controle essa fronteira. Testes que precisam esperar segundos sem observar um evento de conclusão costumam indicar que o fluxo ainda está difícil de coordenar.

Automação de verificação

Uma rotina de integração contínua pode obter o código, configurar o JDK, compilar e executar testes a cada alteração. Ela deve usar os mesmos comandos documentados para o projeto, ou uma configuração equivalente que esteja disponível no repositório. Não coloque dados sensíveis na definição da rotina. Segredos de uma integração real pertencem ao mecanismo apropriado do ambiente e não são necessários aos laboratórios deste guia.

A rotina precisa sinalizar falhas de forma que impeça apresentar uma entrega quebrada como verificada. Ignorar o código de saída dos testes ou acrescentar uma continuação incondicional elimina a finalidade da verificação. Ao mesmo tempo, não confunda um problema de infraestrutura, como falha ao obter uma dependência, com um resultado de regra de negócio. Registre qual etapa não foi concluída e preserve o diagnóstico suficiente para repetir a investigação.

Critério de entrega para o projeto de estudo

Extraia o pacote numa pasta nova. Execute os comandos do roteiro, confira todos os cenários e forneça a entrada de exemplo. Depois altere uma regra pequena, como permitir apenas determinados identificadores, atualize seus testes e confirme as recusas. Peça que outra pessoa execute usando apenas os arquivos e as instruções distribuídos. Essa experiência revela dependências ocultas que sua máquina de trabalho pode estar suprindo sem você perceber.

Um projeto está pronto para esta etapa quando compila na versão declarada, passa nos testes correspondentes ao contrato, oferece uma forma clara de execução e descreve suas limitações. Publicar um serviço, operar dados reais e administrar credenciais são outras etapas. Os laboratórios fornecem a base para compreendê-las, sem anunciar uma configuração de estudo como implantação completa de produção.

Diagnóstico, segurança e desempenho

Investigar um sintoma com uma hipótese verificável

Uma investigação começa pelo que foi observado: qual entrada, qual resultado, em que versão e em qual ambiente. Reduza o caso sem retirar a condição que provoca a falha. Se um erro acontece só na importação de arquivo, compare o conteúdo e a codificação antes de reescrever toda a classe de domínio. Se o programa usa uma versão antiga do .class, mudar a regra do fonte não resolverá a execução até recompilar o caminho correto.

Escreva uma hipótese que possa ser contrariada por uma verificação. “A linha vazia está sendo descartada antes da validação” pode ser testada com uma entrada mínima. “Java não funciona” não identifica uma operação nem uma causa. Preserve a primeira mensagem relevante e a sequência que a produziu. Isso permite corrigir a causa e repetir o teste original, em vez de apenas trocar o sintoma por outro.

Ler stack traces e preservar a causa

Um stack trace mostra a sequência de chamadas associada à falha. Comece pela exceção, pela mensagem e pelo ponto do seu código que participou da operação. As causas encadeadas podem indicar que um erro de domínio foi provocado por uma conversão ou por I/O. Não apague essa relação ao criar uma exceção nova apenas com o texto da antiga. A causa original ajuda a identificar a fronteira em que o dado deixou de atender ao contrato.

Na interface, apresente uma orientação apropriada ao usuário. Num relatório local de teste, mantenha os detalhes técnicos que permitem investigar. Esses dois públicos não precisam receber exatamente a mesma mensagem. Não exponha caminhos internos, tokens ou conteúdo pessoal apenas para tornar a mensagem mais longa. Registre o identificador da operação e um contexto suficiente, de acordo com a necessidade real do diagnóstico.

Logs úteis e dados que não devem aparecer

Um log pode registrar início, resultado e duração de uma operação, com um identificador que ajude a relacionar eventos. Ele não deve depender de cada pessoa adivinhar a ordem entre mensagens de várias tarefas. Ao acrescentar concorrência, inclua o contexto da solicitação e evite misturar resultados sem identificação. Uma impressão isolada de “falhou” pode ser insuficiente para descobrir qual operação alterou o estado.

Não registre senhas, tokens completos e dados que não são necessários à investigação. Uma entrada externa também pode conter quebras de linha e outros caracteres que confundem a leitura de um log textual. O formato de registro deve tratar esses valores como dados. Em exercícios, use identificadores fictícios e mensagens pequenas para concentrar a prática na relação entre evento, resultado e estado posterior.

Validação em fronteiras e menor exposição

Valide dados quando entram no programa e quando cruzam um contrato que exige uma propriedade. Verificar formato na interface não elimina a necessidade de proteger o domínio de outro chamador. Defina limites de tamanho, faixa de números, identificadores aceitos e comportamento para valores nulos. Uma validação que só imprime aviso e continua a alteração não estabeleceu a propriedade desejada.

Exponha apenas as operações necessárias. Um getter que devolve um mapa interno mutável pode permitir contornar a validação dos métodos de movimentação. Um campo private não substitui autenticação, e uma interface pública não decide quem deve ser autorizado a usá-la numa rede. A segurança depende das fronteiras do sistema e do modelo de acesso. Os guias de programação segura Java SE oferecem referências para esse estudo.

Injeção, desserialização e configuração

Ao construir SQL, separe valores e estrutura usando parâmetros e escolhas estruturais conhecidas. Ao interpretar um formato, use o parser adequado e limites do contrato. Não trate conteúdo externo como código ou configuração privilegiada apenas porque ele chegou num arquivo de estudo. Um formato de dados deve declarar o que pode representar, e o programa deve recusar algo fora dessa representação em vez de executar instruções contidas nele.

A desserialização de objetos de origem não confiável possui riscos e não é necessária aos exemplos deste guia. Para intercâmbio de dados, prefira uma representação explícita com campos e validação que você consegue explicar. Mantenha configurações sensíveis fora dos fontes publicados. Se um exemplo requer um serviço externo, distribua um modelo de configuração sem valores reais e descreva quais campos a pessoa precisa fornecer no próprio ambiente.

Medir antes de mudar por desempenho

Comece por uma pergunta de desempenho ligada à tarefa: qual consulta demora, para quantos registros e com que expectativa de resposta. Medir o tempo de uma única execução pode misturar inicialização, compilação JIT, leitura de disco e variação do sistema. Isso não permite afirmar que uma estrutura é sempre mais rápida. Use dados representativos e repita a medição de uma forma que preserve a regra do programa.

Uma mudança que usa um mapa para consultas frequentes pode ajudar, mas exige memória e manutenção de coerência. Uma consulta que ordena todos os registros a cada tecla pode gastar mais trabalho do que precisa. Antes de introduzir cache, confirme qual cálculo custa tempo e quando seus dados mudam. Um resultado antigo servido rapidamente continua errado se a operação exigia estado atual. A invalidação faz parte do contrato do cache.

Memória e retenção de objetos

A coleta de lixo recupera objetos que deixaram de ser alcançáveis, não objetos que a regra de negócio simplesmente deixou de precisar. Uma lista global que acumula todos os relatórios pode manter referências indefinidamente. Um cache sem política de limite pode crescer mesmo quando cada entrada está correta. Observe quais coleções conservam os dados e por quanto tempo eles precisam existir.

Ao investigar consumo de memória, diferencie um volume esperado de trabalho de retenção indevida. Compare entradas, tamanho das estruturas e ciclo de vida das tarefas. Ferramentas de monitoramento ajudam a observar, mas seus resultados precisam de contexto. Não ajuste um limite de heap como única resposta a uma coleção que nunca é liberada. O tema 1 explicou o modelo de memória; os laboratórios de cadastro permitem experimentar o ciclo de referências em escala pequena.

Revisão aplicada antes de distribuir

Revise uma operação inteira: entrada, conversão, validação, alteração, persistência e apresentação. Confira se uma falha em cada fronteira conserva o que o contrato promete. Para o estoque, tente quantidade negativa, item inexistente, overflow e consulta por fotografia. Para arquivos, tente formato incompatível e recusa de gravação. Para HTTP, diferencie status de erro e ausência de resposta.

Registre o que foi verificado e o que ainda depende de ambiente ou integração. Uma lista extensa de ferramentas não substitui essa evidência. Para o projeto de estudo, os testes distribuídos comprovam as regras locais descritas; operação pública, banco real e autenticação precisam de verificações próprias. Use o próximo laboratório para transformar uma dessas limitações em um objetivo concreto e revisável.

Laboratório 1: identidade e busca

Cadastre seis alunos, incluindo dois com o mesmo nome e matrículas diferentes. Use matrícula como identidade. A inclusão de uma matrícula existente deve ser recusada sem substituir o aluno anterior. Uma consulta pelo nome pode devolver mais de um resultado. Defina se a comparação de nomes distingue maiúsculas e registre essa política antes de testar. Laboratório 2: ordenação e fotografia

Produza uma consulta por nota decrescente, nome crescente e matrícula como último desempate. Preserve a ordem original de inclusão. Laboratório 3: importação por lote

Crie um arquivo de estudo com matrícula e nota. Inclua linha vazia, campo ausente, texto no lugar da nota e matrícula repetida. Critérios de aceitação: a versão integral preserva o cadastro anterior em qualquer falha; o relatório da versão parcial identifica linhas aceitas e recusadas; repetir a entrada possui uma política definida; UTF-8 é usado de forma consistente. Para revisar, explique por que capturar uma exceção dentro do laço e imprimir “importação concluída” no final é insuficiente.

Laboratório 4: prazo e aritmética decimal

Represente a data de entrega de um material e calcule um total decimal a partir de preço textual, quantidade e desconto fornecidos pelo exercício. Declare quando o arredondamento acontece e qual modo utiliza. Receba uma data de referência no cálculo de prazo em vez de consultá-la internamente em todos os métodos. Use valores fictícios; o foco é representação e repetição do teste.

Critérios de aceitação: os testes repetem a mesma saída em qualquer dia; fim de mês e ano são verificados; quantidade inválida é recusada; o total corresponde à política de arredondamento. Compare 2.0 e 2.00 por equals e compareTo e explique qual operação serve à regra que você escreveu.

Laboratório 5: tarefas independentes

Divida um conjunto pequeno de cálculos em tarefas que não alteram o mesmo objeto. Submeta o trabalho a um executor, aguarde os resultados e apresente-os em ordem definida pelo chamador. Acrescente uma tarefa que falha e mantenha sua falha distinta de um valor numérico. Encerre os recursos nos caminhos de sucesso e erro.

Critérios de aceitação: o total confere com a versão sequencial; a ordem de apresentação não depende do tempo de cada tarefa; falhas não viram zero silenciosamente; o processo encerra sem deixar o executor ativo. Para revisar, explique por que sleep não comprova conclusão e por que timeout na espera não comprova ausência de efeito.

Laboratório 6: disputa pelas últimas unidades

Modele duas solicitações de retirada que disputam um estoque insuficiente para atender ambas. Escreva uma intercalação que quebraria a regra na implementação sem coordenação. Depois escolha uma estratégia que proteja a decisão e a alteração como uma unidade. Não tente corrigir apenas a impressão da mensagem; o resultado de sucesso precisa corresponder à mudança real do saldo.

Critérios de aceitação: o saldo nunca se torna negativo; a soma das retiradas aceitas não supera o disponível; recusas preservam o estado; a explicação do bloqueio ou operação atômica mostra por que a intercalação inválida não pode publicar dois sucessos. Uma repetição sem falha é evidência de teste, mas a justificativa da coordenação continua necessária.

Laboratório 7: comando de console robusto

No projeto integrador, acrescente uma consulta por item e um comando de ajuda. Teste linha vazia, comando desconhecido, quantidade textual, fim de entrada e várias operações em sequência. Critérios de aceitação: dados inválidos não alteram o estoque; uma consulta não faz movimentação; fim de entrada encerra sem exceção de leitura; os testes do domínio continuam executando sem digitação. Para revisar, identifique uma validação que pertence ao transporte e outra que precisa continuar dentro do domínio para proteger qualquer chamador.

Defina uma representação com versão de formato. Grave uma fotografia do estoque e carregue-a em uma instância nova. Uma versão desconhecida deve ser recusada de modo claro, preservando a fonte. 2. A regra completa e independente da janela

Os dois projetos usam a classe abaixo. A conversão da vírgula atende à entrada decimal simples anunciada pelo formulário. Ela não aceita um formato regional completo com separadores de milhar. A verificação de finitude ocorre antes da comparação de faixa, evitando que NaN seja interpretado como uma nota comum. A função recebe texto e devolve a mensagem, sem acessar controles nem exibir um diálogo.

package br.estudo;
public final class Nota {
    private Nota() {}
    public static String avaliar(String texto) {
        if (texto == null || texto.isBlank()) throw new IllegalArgumentException("Informe a nota.");
        final double nota;
        try { nota = Double.parseDouble(texto.trim().replace(',', '.')); }
        catch (NumberFormatException e) { throw new IllegalArgumentException("Use um número de 0 a 10."); }
        if (!Double.isFinite(nota) || nota < 0 || nota > 10) throw new IllegalArgumentException("Use um número de 0 a 10.");
        return nota >= 7 ? "Aprovado" : "Em recuperação";
    }
}

14 · Multiplataforma: empacotamento e matriz de suporte

1. Uma distribuição começa pela matriz de suporte

Defina quem vai executar a aplicação e em quais ambientes. Sistema operacional, arquitetura e runtime são informações separadas. Windows x64 com runtime incluído é uma combinação diferente de Linux arm64 com JDK já instalado. Registre as combinações verificadas e deixe as demais como pendentes.

package br.estudo.catalogo;
import java.util.NoSuchElementException;
import org.springframework.data.domain.*;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
@Service
public class ProdutoService {
 private final ProdutoRepository repositorio;
 public ProdutoService(ProdutoRepository repositorio){this.repositorio=repositorio;}
 @Transactional public Contratos.Resposta criar(Contratos.Criar dados){
  return Contratos.Resposta.de(repositorio.saveAndFlush(new Produto(dados.codigo(),dados.quantidade())));
 }
 @Transactional(readOnly=true) public Contratos.Resposta buscar(long id){return Contratos.Resposta.de(encontrar(id));}
 @Transactional(readOnly=true) public Page<Contratos.Resposta> listar(int pagina,int tamanho){
  return repositorio.findAll(PageRequest.of(pagina,tamanho,Sort.by("id").ascending())).map(Contratos.Resposta::de);
 }
 @Transactional public Contratos.Resposta retirar(long id,Contratos.Retirar dados){
  Produto produto=encontrar(id);produto.retirar(dados.quantidade(),dados.versao());repositorio.flush();
  return Contratos.Resposta.de(produto);
 }
 private Produto encontrar(long id){return repositorio.findById(id).orElseThrow(()->new NoSuchElementException("Produto não encontrado"));}
}

18 · Integrações: falhas, idempotência, cache e eventos

1. Simular a falha de uma dependência com controle

Uma integração precisa ser testada quando responde, demora, falha e repete informação. 2. Quatro situações que o cliente precisa distinguir

Uma resposta 200 com JSON válido pode atualizar a tela. Uma resposta 404 indica ausência conforme o contrato daquela rota. Um 409 representa conflito e pede tratamento do estado atual. Uma falha de conexão ou timeout pode deixar o resultado desconhecido. Não converta as quatro situações na mesma lista vazia.

Acrescente um caso de JSON malformado com status 200 e confira que o cliente recusa o conteúdo, preservando o rascunho. A validade do status não garante a validade da representação. Depois forneça um campo ausente ou tipo incompatível e observe o erro de contrato. Defina se campos adicionais são tolerados para permitir evolução compatível.

Se o cliente estiver numa interface gráfica, execute a chamada fora da thread de eventos e verifique o resultado antigo chegando depois do novo. Se estiver no Android, confira a relação da resposta com a tela e seu ciclo de vida. O adaptador precisa entregar dados para o estado atual, sem reabrir uma tela descartada.

3. Um experimento de idempotência

Modele uma retirada com id de operação, produto, quantidade e versão. No teste em memória, mantenha um registro de resultado e uma coordenação que una a verificação com a alteração. Envie duas vezes a mesma operação e confira um único desconto. Depois reutilize o id com quantidade diferente e espere conflito.

Essa implementação em memória é uma etapa para compreender o contrato, sem garantia durável após reinício. Ao levar para o banco, o registro da operação e o desconto devem confirmar juntos. Uma restrição única ajuda a tratar a concorrência entre tentativas do mesmo id. Teste as disputas na tecnologia de banco escolhida.

Defina também a política de retenção e escopo. Uma chave pode ser exclusiva por usuário e tipo de operação. O resultado guardado não deve ser exposto a outro usuário que adivinhe o mesmo texto. O tema de integrações distribuídas relaciona esse contrato ao timeout e à repetição.

4. Uma tabela de quedas para outbox

Descreva o processo em etapas: gravar retirada e evento na mesma transação, confirmar, publicar evento e marcar a publicação. Simule uma queda antes do commit e espere ausência dos dois registros. Depois simule queda após commit e antes do envio; a pendência deve continuar disponível. Por fim, simule envio confirmado com queda antes da marcação e espere possível repetição.

O consumidor deve registrar o id do evento e seu efeito de forma consistente. Reentrega do mesmo evento não pode descontar novamente nem emitir uma confirmação duplicada como nova operação. Se o processamento falhar, decida quando confirmar, quando repetir e como encaminhar uma falha permanente.

Não é necessário instalar um broker para a primeira tabela de cenários. Um adaptador de teste com filas controladas permite conferir o contrato local. Quando integrar uma infraestrutura real, acrescente seus testes de confirmação, reentrega, ordenação e disponibilidade. O adaptador simulado não demonstra essas propriedades do produto externo.

5. Cache como experimento independente

Escolha uma consulta que admita defasagem e registre uma política de validade. Conte quantas vezes a fonte é consultada em duas leituras da mesma chave. Altere o produto e confirme a invalidação ou a expiração prometida. Se houver escopo por usuário, teste chaves que não possam compartilhar dados.

Depois simule indisponibilidade do cache e observe a carga sobre a fonte. O fallback deve preservar a regra e respeitar limites de recursos. Retirada de estoque não deve usar um saldo em cache como autoridade única. A decisão transacional continua na fonte que confirma o estado.

6. Prática: um caderno de cenários de integração

Entregue uma tabela com sucesso, ausência, conflito, timeout, representação inválida, repetição e queda após commit. Para cada cenário, indique o efeito permitido e a mensagem ao usuário. Registre se o teste usa simulação, servidor local ou infraestrutura real.

Escolha uma propriedade para automatizar primeiro, como um único desconto para a mesma operação. Depois introduza a falha que quebraria essa propriedade e confirme que o teste detecta. A etapa termina quando você consegue repetir a falha e explicar o resultado sem depender de uma rede sempre disponível.

19 · Operação: diagnóstico, desempenho e entrega

1. Observar um processo antes de otimizar

Uma aplicação lenta pode estar aguardando banco, rede, CPU, bloqueio ou recursos esgotados. Comece registrando o sintoma, a carga e a operação afetada. Reproduza com dados fictícios num ambiente controlado e compare com uma execução conhecida. Alterar parâmetros aleatórios dificulta relacionar causa e efeito.

O catálogo Spring fornece saúde sem detalhes e logs de inicialização. Para estudar métricas, acrescente uma integração oficial compatível com a linha e limite sua exposição. O tema de operação apresenta configuração, probes e encerramento. Esta seção organiza experimentos e critérios para você acompanhar o serviço.

2. Uma ficha de configuração efetiva

Registre versão de Java, ferramenta de build, versão do projeto, porta, banco e perfil ativo. Valores secretos devem aparecer apenas como presentes ou ausentes, com sua origem descrita. Não cole o ambiente completo num relatório, pois ele pode conter tokens e senhas de outros programas.

Teste uma configuração obrigatória ausente e uma inválida. A inicialização deve falhar de forma compreensível quando a aplicação não pode operar com segurança. Se uma propriedade foi sobrescrita por argumento ou variável, identifique a precedência. Guarde um exemplo de configuração com valores fictícios que outra pessoa consiga adaptar.

Para o laboratório, observe que a porta padrão é 8080 e o endereço é 127.0.0.1. Um cliente em outro dispositivo não alcança esse loopback diretamente. Qualquer mudança de exposição precisa vir acompanhada da revisão de credenciais, transporte e acesso.

3. JFR, threads e memória com dados de estudo

Java Flight Recorder permite coletar eventos do runtime para investigar comportamento. Use as ferramentas do JDK conforme a versão e o ambiente. Uma gravação pode conter informações sobre a aplicação; trate o arquivo como artefato de diagnóstico, revisando onde ele será armazenado e compartilhado. Consulte a documentação de Flight Recorder para os mecanismos disponíveis.

Um thread dump mostra o estado observado das threads e ajuda a investigar esperas e bloqueios. Uma única captura é uma fotografia; capturas em momentos distintos podem revelar persistência de uma espera. Antes de concluir que há deadlock, identifique quais recursos e relações explicam o bloqueio.

Heap dumps podem conter dados sensíveis e ocupar muito espaço. Não os publique como material aberto. Para o estudo, use dados fictícios e um ambiente local. Diferencie heap ocupado, memória retida e pressão temporária de alocação; um número alto isolado não explica sozinho um vazamento.

4. Um teste de carga pequeno e interpretável

Defina uma operação, um conjunto fixo de dados, concorrência limitada e duração. Meça latência, erros e uso de recursos. Comece com uma carga baixa e aumente em etapas no seu próprio serviço. Não use o servidor de produção de outra pessoa como alvo de prática.

Separe leitura de escrita. Consultar lista repetidamente possui efeito diferente de criar produtos com código único. Uma carga que repete o mesmo código e recebe 409 está medindo recusas, não a vazão de cadastros bem-sucedidos. Registre o mix de operações e os status esperados.

Compare antes e depois de uma mudança usando a mesma condição. Aquecimento, cache e volume de dados podem alterar os resultados. Uma média pode esconder uma parcela de chamadas muito lentas; observe a distribuição e os limites de resposta que importam para o usuário. Evite transformar um único resultado local numa promessa universal de desempenho.

5. Entrega contínua e ambiente de teste

Uma sequência mínima de integração pode obter o código, selecionar o JDK declarado, resolver dependências, executar testes e produzir o artefato. O pipeline não deve embutir segredos no pacote nem publicar resultados como se fossem aprovados quando uma etapa falha. Identifique a revisão que produziu cada entrega.

Para o catálogo, mvn clean verify é um ponto de entrada de build. Os testes distribuídos rodam com H2; um estágio com banco alvo deve ser adicionado quando esse banco entrar no escopo. Não marque uma migração como verificada apenas porque os testes em memória passaram.

Se a entrega inclui Android ou desktop, cada artefato exige seu ambiente. Um job que compila o servidor não prova a instalação do APK nem a acessibilidade da janela. Mantenha uma matriz por plataforma e guarde resultados que possam ser associados à versão correspondente.

6. Encerramento e recuperação

Teste o encerramento do servidor e confira o tempo de saída. Uma aplicação com tarefas próprias precisa parar a aceitação de novos trabalhos e tratar os já aceitos. A janela de encerramento da infraestrutura deve ser compatível com o prazo interno. Uma parada forçada pode deixar o cliente sem confirmação.

Para dados permanentes, pratique restauração em outra base de teste. Verifique contagem, registros relevantes e capacidade de executar operações depois da restauração. Ter um arquivo de backup não comprova que ele corresponde ao esquema ou que você sabe recuperá-lo. Registre o procedimento e o tempo observado.

7. Prática: relatório de uma investigação

Escolha um sintoma reproduzível, como uma consulta com atraso artificial. Registre hipótese, medição, evidência e alteração. Repita a medição e explique o efeito observado e seus limites. Remova o atraso de teste ou mantenha-o restrito ao cenário controlado.

Entregue também um roteiro de início, saúde, teste de acesso, encerramento e restauração conforme o escopo. Marque os itens não executados. O trabalho termina quando outra pessoa consegue repetir a investigação e distinguir uma conclusão medida de uma hipótese ainda aberta.

Apresente uma lista com código e saldo e mantenha a seleção por identidade estável. Carregue fora da thread gráfica. Mostre vazio, carregando, falha e conteúdo. Não deixe uma resposta antiga substituir a consulta atual. Depois acrescente uma escrita usando o mecanismo de acesso do servidor local.

5. Entrega D: cliente Android

Abra o projeto básico, compile e execute a tela antes de ligar a rede. Depois modele estado e repositório. Rotação não deve duplicar uma operação nem perder o rascunho definido para restauração. O endereço do servidor precisa ser configurado para o ambiente real de teste, respeitando loopback, emulador e transporte.

Se adicionar banco local, escreva uma migração e teste a preservação de registros. Se adicionar pendências de sincronização, diferencie o que foi aceito localmente do que foi confirmado pelo servidor. Não anuncie uma retirada concluída apenas por colocá-la numa fila no aparelho.

6. Entrega E: resultado desconhecido e repetição

Simule perda de resposta depois de uma operação confirmada. O cliente deve consultar o resultado por uma identidade adequada ou repetir de acordo com uma política idempotente implementada no servidor. Repetir um POST comum às cegas pode produzir outro efeito.

Se houver eventos, teste publicação pendente e reentrega. Registre a fronteira transacional e o id estável. Se não houver necessidade de eventos na primeira versão, mantenha esse item como evolução e explique a limitação. A entrega deve ser coerente com o que realmente existe.

Em cada linha, indique ambiente, resultado esperado, resultado observado e evidência.

Separe compilado, testado automaticamente e observado manualmente. Android sem emulador executado permanece com a interface pendente, mesmo que a regra tenha passado. Desktop em um sistema não comprova outro. H2 não comprova o banco permanente. Essa matriz ajuda o grupo a saber o que aprendeu e o que ainda precisa experimentar.

8. Prática: apresentação e avaliação por evidências

Prepare uma demonstração curta com cadastro, retirada, conflito e recuperação de falha. Cada integrante explica uma fronteira e repete um teste feito por outra pessoa. A revisão deve conferir se o texto publicado e os arquivos disponíveis bastam para reproduzir o sistema.

O projeto está concluído no escopo escolhido quando suas regras estão escritas, seus artefatos têm comandos de execução e as garantias anunciadas possuem evidência.
