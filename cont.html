09 · Encapsulamento e regras de negócio

Referência para consulta: Desenvolvimento de aplicações, páginas 85 a 92. A explicação e os exemplos estão completos abaixo.

1. Manter o objeto em um estado válido

Encapsulamento reúne estado e operações e controla a forma de acesso aos detalhes internos. Uma conta que permite atribuir qualquer valor ao saldo deixa o chamador ignorar regras de depósito e saque. Tornar o saldo privado e oferecer operações que validam valores permite concentrar essas regras. O objetivo deve ser a coerência do objeto e um contrato compreensível para quem o usa.

private é um controle de acesso da linguagem. Ele não cifra valores, não autentica pessoas e não protege uma conta bancária real apenas por estar escrito no atributo. O exemplo deste tema é uma simulação de console. Uma aplicação real precisaria tratar autenticação, armazenamento, concorrência e outros requisitos fora do alcance desse exercício.

2. Getters e setters são métodos

Um getter consulta uma informação, como getNome(). Um setter solicita alteração, como setNome(String nome). Esses nomes são convenções; get e set não são palavras-chave especiais. Um getter pode calcular um valor sem que exista um campo com o mesmo nome. Para uma propriedade booleana, uma convenção comum é isAtivo().

Não é obrigatório oferecer um setter para cada atributo. Se o saldo deve mudar por depósitos e saques, um setSaldo público permite ignorar o significado dessas operações. Uma classe pode oferecer consulta sem alteração direta. Também precisa decidir se um retorno expõe um objeto mutável interno: devolver a referência do array privado permitiria que o chamador alterasse seus elementos. Quando necessário, devolva uma cópia ou outra representação apropriada.

3. A validação precisa interromper a alteração inválida

class Nivel {
    private int valor;

    Nivel(int valor) {
        setValor(valor);
    }

    public void setValor(int valor) {
        if (valor < 1 || valor > 10) {
            throw new IllegalArgumentException("Nível deve estar entre 1 e 10");
        }
        this.valor = valor;
    }

    public int getValor() {
        return valor;
    }
}

Se um setter apenas imprimir “valor inválido” e executar a atribuição em seguida, o estado inválido ainda será armazenado. No código acima, a exceção encerra esse caminho antes da atribuição. Outra política possível é devolver um booleano e deixar o valor anterior intacto quando houver recusa. Escolha um contrato consistente e faça o chamador tratar o resultado.

4. Conta didática com centavos inteiros

class Conta {
    private long saldoCentavos;

    Conta(long saldoInicial) {
        if (saldoInicial < 0) {
            throw new IllegalArgumentException("Saldo inicial negativo");
        }
        saldoCentavos = saldoInicial;
    }

    public long getSaldoCentavos() {
        return saldoCentavos;
    }

    public void depositar(long valor) {
        if (valor <= 0) {
            throw new IllegalArgumentException("Depósito deve ser positivo");
        }
        saldoCentavos = Math.addExact(saldoCentavos, valor);
    }

    public boolean sacar(long valor) {
        if (valor <= 0 || valor > saldoCentavos) {
            return false;
        }
        saldoCentavos -= valor;
        return true;
    }
}

A unidade precisa acompanhar o nome: 10000 centavos representam R$ 100,00. A conta inicia em um estado não negativo, rejeita depósito não positivo e recusa saque inválido ou acima do saldo. Um saque recusado retorna falso e preserva o saldo. Math.addExact evita que um depósito provoque transbordamento silencioso do inteiro. O exercício simplifica dinheiro para uma unidade inteira fixa; não implementa taxas, juros ou persistência.

Para um estado inicial de 10000, depósito de 2500 e saque de 3000, o saldo final é 9500 centavos. Um saque de 99999 deve retornar falso e manter 9500. Verificar o retorno e consultar o saldo depois da recusa são dois testes diferentes e necessários para conferir a operação. Uma mensagem de sucesso sem alteração correta do estado não comprova a regra.

5. Throw, throws e tratamento de exceções

throw lança um objeto de exceção e interrompe o caminho normal naquele ponto. throws declara, na assinatura de um método ou construtor, tipos de exceção que podem ser propagados. try delimita o código observado e catch trata tipos compatíveis. A captura deve estar na parte do programa que sabe informar a falha ou recuperar a operação. Não esconda uma alteração parcial imprimindo uma mensagem de sucesso depois da captura.

Exceções verificadas, como IOException, precisam ser capturadas ou declaradas quando podem sair do método. Subclasses de RuntimeException, como IllegalArgumentException e NumberFormatException, dispensam essa exigência de compilação. Isso não as torna inofensivas. Error representa outra categoria de falhas; capturar indiscriminadamente Throwable não é um mecanismo adequado de validação de entrada. O guia de exceções explica as categorias e a propagação.

public class Main {
    static int lerQuantidade(String texto) {
        int quantidade = Integer.parseInt(texto);
        if (quantidade <= 0) {
            throw new IllegalArgumentException("Quantidade deve ser positiva");
        }
        return quantidade;
    }

    public static void main(String[] args) {
        String[] entradas = {"3", "zero", "0"};
        for (String texto : entradas) {
            try {
                System.out.println("Quantidade: " + lerQuantidade(texto));
            } catch (NumberFormatException erro) {
                System.out.println("Formato inválido: " + texto);
            } catch (IllegalArgumentException erro) {
                System.out.println(erro.getMessage());
            }
        }
    }
}

Praticar este programa no Playground

A saída mostra Quantidade: 3, Formato inválido: zero e Quantidade deve ser positiva. NumberFormatException é uma subclasse de IllegalArgumentException, por isso a captura específica vem primeiro. Inverter essa ordem deixa a captura específica inalcançável. O primeiro caso falho não impede o laço de experimentar a próxima entrada, pois o tratamento está dentro de cada iteração. Teste esse programa no editor de exceções.

6. Fechar recursos e preservar a causa da falha

Use try-with-resources para recursos que implementam AutoCloseable e cujo ciclo de vida pertence à operação, como um leitor de arquivo. O fechamento é tentado ao sair do bloco, inclusive quando há uma exceção. Um bloco finally permite ações de finalização, mas um return dentro dele pode encobrir o retorno ou a falha anterior. Prefira um fluxo em que o resultado e a falha continuem visíveis.

Ao transformar uma exceção em outra que faça sentido para o chamador, preserve a causa, por exemplo com um construtor que recebe mensagem e exceção original. Isso permite investigar o problema técnico sem obrigar a interface a apresentar detalhes internos ao usuário. Na conta do exercício, uma recusa deve ocorrer antes da mudança do saldo. Para operações que envolvem várias alterações, defina o que acontece se uma etapa falhar; esse raciocínio prepara o estudo de transações.

7. Tratamento de falhas e testes de regra

try delimita uma operação que pode falhar, e catch trata uma exceção de tipo determinado. A captura deve ajudar a recuperar ou explicar a falha. Capturar qualquer exceção e ignorá-la pode esconder um defeito. No exercício, uma entrada inválida pode gerar uma mensagem clara e uma nova tentativa; um erro de programação deve continuar sendo investigado.

try {
    Conta conta = new Conta(10000);
    conta.depositar(-50);
} catch (IllegalArgumentException erro) {
    System.out.println(erro.getMessage());
}

Teste valor negativo, zero, valor válido, saque exato do saldo e saque superior ao saldo. Escreva o estado esperado antes e depois. O construtor também precisa ser testado com saldo inicial inválido. Se você usa assert no computador, lembre que as asserções Java dependem de habilitação na execução; para conferências didáticas explícitas, uma condição que lança AssertionError independe dessa opção.

8. Separar entidade, gerenciamento e interface

Uma organização possível para o banco separa três responsabilidades: ContaBancaria mantém dados e operações de cada conta, Banco reúne as contas e as localiza, e SistemaTerminal controla leitura e menus. A interface recebe a solicitação, chama uma operação e apresenta o resultado. Essa separação permite testar a conta sem executar todo o diálogo de login.

Um método que procura uma conta pode devolver a referência encontrada ou null. O chamador verifica a ausência antes de chamar qualquer método da conta. Em um menu com login, um laço externo pode controlar a entrada na sessão e um laço interno as operações da sessão atual. Um break encerra apenas a estrutura à qual pertence. O menu bancário disponível no Playground permite observar esse fluxo.

9. Evoluir um banco de console

Para representar várias contas, mantenha o saldo como atributo de cada conta e concentre as regras de movimentação nessa classe. Mantenha uma instância de Scanner na interface de console e passe às operações apenas os dados necessários. Um método auxiliar não deve fechar a entrada que outros menus ainda precisam usar.

No caso de transferência, a leitura do destinatário precisa considerar a quebra de linha deixada depois do inteiro do menu. Antes de movimentar, valide destino, valor e saldo. O tipo de investimento também precisa ser conferido antes de retirar dinheiro: um ternário que chama qualquer número diferente de 1 de “CDB” aceita opções desconhecidas. Use um caminho específico para cada opção permitida e um caminho de recusa.

Os exemplos de rendimento e tarifas dos projetos são dados de exercício. Para esta apostila, o foco é verificar o fluxo e a preservação do estado. Se uma operação envolve duas contas, um resultado parcial não pode ser apresentado como uma transferência completa. Esse é um ponto para estudar transações quando o projeto passar a usar armazenamento real.

10. SOLID como perguntas sobre o seu projeto

SOLID reúne cinco princípios para avaliar decisões de projeto. Responsabilidade única pergunta por que uma classe precisa mudar: ler o menu, calcular regras de conta e gravar arquivos podem ser responsabilidades separadas. Aberto/fechado sugere permitir variações por contratos estáveis quando elas existem; o apresentador de mensagens do tema 7 aceita outra implementação sem precisar mudar.

Substituição de Liskov exige que um subtipo preserve as expectativas do contrato da base. Segregação de interfaces evita exigir capacidades sem relação para todos os implementadores. Inversão de dependência propõe que a regra central possa depender de um contrato, recebendo um colaborador compatível. Passar uma implementação pelo construtor é uma forma de injeção de dependência que funciona sem framework. Esses princípios não obrigam a criar uma interface para cada classe.

Padrões de projeto descrevem soluções para problemas recorrentes. Uma fábrica simples pode escolher qual implementação criar. Factory Method organiza a criação por um método que subclasses podem sobrescrever. Observer modela notificações para interessados registrados. Singleton introduz uma instância compartilhada e exige cuidado com concorrência e testes. Antes de escolher um padrão, descreva o problema que ele precisa resolver. Para o banco didático, comece com contas independentes e colaboradores explícitos.

10 · Modificadores de acesso e organização

Referência para consulta: Desenvolvimento de aplicações, páginas 93 a 112. A explicação e os exemplos estão completos abaixo.

1. Visibilidade faz parte do contrato

Modificadores de acesso determinam onde classes e membros podem ser usados diretamente pelo código. Eles ajudam a definir quais operações compõem a interface pública e quais detalhes pertencem à implementação. Uma classe de conta pode permitir consulta de saldo e movimentações sem permitir atribuição direta do saldo. A escolha de acesso deve acompanhar essa responsabilidade.

Há acesso public, protected, private e acesso de pacote quando nenhum desses modificadores é escrito. “Padrão” descreve essa ausência; não se escreve default antes de um atributo para obter acesso de pacote. A palavra default possui outros usos na linguagem, como o ramo de switch e métodos padrão de interfaces.

O ponto inicial para os exercícios é conferir o acesso do tipo, do construtor e do membro. Um método público dentro de uma classe que não é acessível não oferece, por si só, uma classe pública para qualquer chamador.

3. Public e private

public permite acesso onde o tipo e as demais regras de organização o permitem. Use-o nas operações que o código externo deve chamar. Expor todos os atributos como públicos torna os detalhes do estado parte do contrato e permite alterações sem validação. Ao mudar esses detalhes depois, outros arquivos podem deixar de compilar ou passar a depender de um comportamento que você não pretendia oferecer.

private restringe o acesso conforme as regras de encapsulamento da classe. Nos exercícios com classes de topo distintas, outra classe não acessa diretamente o campo privado. A consulta passa por um método acessível. Privado não significa constante: a própria classe pode mudar seu atributo privado quando a operação permite. Para impedir reatribuição de um campo, existe final, que resolve uma questão diferente.

class Produto {
    private int estoque;

    Produto(int estoque) {
        this.estoque = estoque;
    }

    public int getEstoque() {
        return estoque;
    }
}
// Em Main, use produto.getEstoque().
// produto.estoque não é um acesso permitido entre essas classes.

4. Pacotes e importação

Um pacote organiza nomes e participa das regras de acesso. package escola; declara o pacote de um arquivo e deve aparecer antes dos imports e das declarações de tipos. Os diretórios do projeto normalmente refletem esse nome. import escola.Aluno; permite usar o nome curto quando o tipo está disponível; não contorna private, acesso de pacote ou protected.

// Arquivo escola/Aluno.java
package escola;
public class Aluno {
    String nome;
    public Aluno(String nome) {
        this.nome = nome;
    }
    public String getNome() {
        return nome;
    }
}

Nesse exemplo, nome tem acesso de pacote. Uma classe em outro pacote pode chamar o construtor público e o getter público, mas não ler o campo diretamente. Uma subclasse fora do pacote também não recebe acesso ao campo apenas por herdar de Aluno. A relação de herança não abre uma exceção geral ao acesso de pacote.

No computador, os comandos precisam considerar o nome qualificado da classe e o caminho de classes. Se uma classe principal for escola.Main, compile a partir da raiz apropriada, por exemplo javac -d out escola/*.java, e execute com java -cp out escola.Main. O editor do Playground usa um único arquivo sem pacote para os exercícios guiados. O exemplo com arquivos de pacote é uma referência para a IDE, e está identificado como tal.

5. Protected dentro e fora do pacote

No mesmo pacote, protected permite acesso a outras classes. Fora do pacote, o acesso envolve código de uma subclasse e restrições sobre a referência usada para acessar um membro de instância. Dizer apenas “subclasses acessam protected” esconde parte da regra. Uma subclasse não recebe autorização para acessar esse membro em qualquer objeto de um tipo-base arbitrário.

Considere uma superclasse Base com campo protegido e uma subclasse Derivada em outro pacote. Dentro de Derivada, o acesso pelo próprio objeto com this é permitido. Um acesso por uma variável declarada como Base não fica permitido apenas porque o código está na subclasse. Para esse detalhe, confira a regra de acesso protected na especificação.

O exemplo de carro e motor da apostila ajuda a distinguir herança e composição. Uma classe que herda de Carro não herda de Motor só porque o carro guarda um motor. O acesso a motor.darPartida() deve ser verificado usando o pacote e o modificador do método declarado em Motor. Estar no pacote do motor pode permitir um acesso que a relação com carro, isoladamente, não permitiria.

6. Acesso não é static nem final

public, private e protected tratam de acesso. static trata da associação à classe, e final tem significados de restrição conforme a declaração. Um campo pode ser privado e estático ao mesmo tempo. Uma constante de classe pode usar public static final quando sua exposição fizer parte do contrato. Uma referência final a um objeto mutável não torna esse objeto automaticamente imutável.

Em classes de topo comuns, use public ou nenhum modificador de acesso. Não declare uma classe de topo como private ou protected. Quando houver vários tipos no mesmo arquivo dos exercícios, mantenha apenas Main como público. Ao separar o projeto em arquivos, cada classe pública deve estar no arquivo correspondente ao seu nome.

7. Investigar um erro de acesso

Comece localizando a declaração do tipo e do membro. Confira o pacote do chamador, se existe herança e qual é o tipo da referência usada na chamada. Verifique também o construtor quando a falha ocorre no new. Trocar tudo para public pode fazer a mensagem desaparecer, mas altera o contrato e permite operações que deveriam continuar controladas.

Quando o chamador precisa de uma operação legítima, ofereça um método que represente essa necessidade. Para consultar estoque, um getter pode bastar. Para retirar um item, um método que verifica disponibilidade evita que o chamador calcule e atribua um estoque negativo. O projeto deve deixar claro onde a regra é aplicada e como a operação informa uma recusa.

8. Do arquivo único a um projeto com build

Quando o programa cresce, ferramentas de build automatizam tarefas como resolver dependências, compilar, executar testes e empacotar. Maven e Gradle cumprem esse papel e continuam usando ferramentas e regras Java. Uma importação não instala uma biblioteca: ela precisa estar disponível no projeto, com versão e configuração apropriadas.

Em um projeto Maven convencional, src/main/java recebe os fontes da aplicação, src/main/resources os recursos e src/test/java os testes. O pom.xml declara informações e configuração do projeto. mvn test executa a fase de testes e as fases anteriores necessárias; mvn package chega ao empacotamento. A versão Java alvo deve estar explícita. Consulte o guia do Maven antes de criar esse projeto na IDE.

O Playground mantém um único Main.java e não instala bibliotecas externas. Para evoluir o banco que você praticou no Playground, baixe o código, crie um projeto local e separe classes por responsabilidade. Primeiro mantenha o mesmo comportamento no console; depois acrescente testes e armazenamento. Assim você consegue distinguir um erro de reorganização de uma mudança na regra de negócio.

9. Testes que verificam comportamento

Um teste precisa de preparação, operação e verificação do resultado. Para uma conta com 1.000 centavos, depositar 200 deve produzir 1.200. Um depósito inválido deve ser recusado e manter os 1.000. Verificar apenas que não houve mensagem de erro deixa de conferir a regra principal. Use um objeto novo em cada cenário para evitar que o teste dependa de outro.

JUnit fornece recursos para organizar testes e asserções; Mockito permite criar substitutos de colaboradores quando o isolamento é necessário. Um teste unitário observa uma unidade pequena, enquanto um teste de integração confere a colaboração com componentes como um banco. Uma asserção do JUnit funciona pelo mecanismo da biblioteca e não depende de habilitar a palavra-chave Java assert. Configure a biblioteca no projeto local e confira a compatibilidade entre sua versão e o JDK na documentação do JUnit.

Como prática, escreva casos de saque menor que o saldo, saque exato, saldo insuficiente e valor inválido. Verifique retorno ou exceção e o estado posterior. Para uma transferência, confira origem e destino depois de uma operação aceita e de uma recusada. Se o código só pode ser testado digitando todo o menu, retome a separação entre interface e regra de negócio do tema 9.

10. Arquivos, concorrência e limites do ambiente

Para estudar persistência local, Path representa um caminho e Files reúne operações de arquivo. Defina o formato dos dados, a codificação e o tratamento de ausência ou falha de leitura. Ler tudo para a memória pode servir a um exercício pequeno, mas arquivos grandes pedem processamento adequado ao tamanho. Métodos como Files.readString são posteriores a Java 8 e devem ser praticados no JDK local, pois o compilador do site usa assinaturas Java 8. O sistema de arquivos virtual da JVM no navegador não é a pasta pessoal do computador. Consulte o guia de arquivos e NIO.2.

Concorrência permite que tarefas tenham execuções sobrepostas; paralelismo envolve execução simultânea. Uma thread criada com start() agenda uma nova execução, enquanto chamar run() diretamente faz uma chamada comum no fluxo atual. O escalonamento não garante uma ordem fixa de mensagens. Compartilhar um contador e fazer contador++ de várias threads pode perder atualizações, pois leitura, cálculo e escrita não formam automaticamente uma operação atômica.

Compartilhamento exige um projeto que trate visibilidade e coordenação, com mecanismos como sincronização ou classes concorrentes apropriadas. Criar mais threads não garante menor tempo. Virtual threads são um recurso de Java 21 e não fazem parte da JVM Java 17 deste Playground. Dimensione a quantidade de tarefas de acordo com a memória disponível e a carga que precisa processar. O guia de concorrência apresenta os problemas básicos de interferência e sincronização.

11 · Coleções, generics e contratos de dados

1. Do cadastro à regra de consulta

Nos temas anteriores, você criou objetos, protegeu atributos e reuniu valores em arrays, listas e mapas. Agora o problema passa a ser o contrato dessas estruturas: o que significa encontrar um registro, quando dois registros são iguais, como ordenar uma consulta e quem pode alterar os dados recebidos. Essas decisões aparecem mesmo em um programa pequeno. Uma lista que parece correta na primeira impressão pode permitir duplicação indevida, perder a ordem de cadastro ou expor o estado interno de um objeto.

Considere um cadastro de alunos com matrícula, nome e nota. Matrícula identifica o aluno; nome serve para apresentação e busca; nota participa da regra de avaliação. Duas pessoas podem ter o mesmo nome e notas podem mudar. Portanto, usar apenas o nome como chave pode juntar pessoas diferentes, enquanto usar a nota como identidade torna uma atualização capaz de mudar o significado do registro. Antes de escolher uma coleção, escreva qual informação identifica cada objeto e quais consultas serão realizadas.

Neste tema, mantenha o cadastro e suas consultas como conceitos separados. A sequência de inclusão pode ser útil para apresentar o histórico, enquanto outra tela precisa mostrar as maiores notas primeiro. Você não precisa sacrificar uma ordem para obter a outra. Crie uma projeção ou uma cópia apropriada para consultar, aplique o critério nessa estrutura e preserve a regra de alteração do cadastro. Esse cuidado prepara o trabalho com persistência e serviços dos próximos temas.

2. Identidade, igualdade e código de hash

A identidade de referência responde se duas variáveis apontam para o mesmo objeto. A igualdade lógica responde se os objetos representam o mesmo valor segundo o contrato da classe. Em uma classe que não redefine equals, a implementação herdada de Object usa identidade. Criar duas instâncias com os mesmos campos não as torna automaticamente iguais. Se a regra do cadastro define matrícula como identidade lógica, a classe precisa expressar essa decisão de maneira consistente.

Ao redefinir equals, mantenha reflexividade, simetria, transitividade e consistência enquanto os dados relevantes não mudarem. Um objeto não nulo deve ser diferente de null. Se duas instâncias são iguais, seus hashCode precisam ser iguais. O inverso não é obrigatório: colisões existem e a estrutura continua precisando verificar igualdade. Um hash não é uma matrícula, uma assinatura criptográfica nem uma garantia de unicidade. Consulte os contratos de Object para conferir essas obrigações.

Campos usados na igualdade de uma chave devem permanecer estáveis enquanto ela estiver em um mapa ou conjunto baseado em hash. Se uma chave muda de matrícula depois da inclusão, a estrutura pode continuar guardando a entrada numa posição calculada para o valor anterior. Uma busca com o novo valor pode falhar, mesmo que o objeto apareça durante a iteração. Prefira identificadores imutáveis e atualize os dados que não fazem parte da identidade por operações próprias.

3. O que cada estrutura promete

Uma lista oferece sequência e posições, mas não impõe identidade única de aluno. Um conjunto evita elementos repetidos segundo sua regra de equivalência. Um mapa permite localizar uma associação pela chave. A estrutura não decide qual chave representa bem o domínio. Se você escolher Map<String, Aluno> com matrícula textual, ainda precisa validar matrículas vazias, inclusões repetidas e a política para atualização. put substitui uma associação existente e não avisa, por si só, que um cadastro deveria ter sido recusado.

A implementação também participa do contrato de observação. HashMap não garante ordem de inserção. LinkedHashMap, em sua configuração usual, permite percorrer a ordem de inclusão. TreeMap ordena chaves conforme comparação. Não use o resultado de uma impressão ocasional para prometer uma ordem que a implementação não oferece. Um teste que depende de uma ordem inexistente pode passar hoje e falhar depois de uma alteração na quantidade de registros.

Para o cadastro didático, uma política simples é recusar matrícula já existente em uma operação de inclusão e oferecer uma operação diferente para atualização. Isso torna a intenção visível no nome do método e no resultado. Teste as duas operações com a mesma chave: a inclusão deve preservar o registro anterior; a atualização permitida deve mudar apenas os dados previstos. Se outras threads também puderem escrever, a verificação de existência e a inclusão precisarão de coordenação, como será discutido no tema 13.

4. Tipos genéricos como parte do contrato

Um parâmetro genérico relaciona os tipos que uma estrutura recebe e devolve. Uma List<Aluno> permite recuperar um aluno sem espalhar casts pelo programa. Se uma função recebe essa lista, o compilador pode rejeitar a inclusão de um texto no lugar de aluno. Essa verificação ajuda antes da execução, mas não substitui regras como nota dentro da faixa ou matrícula válida. O sistema de tipos e a validação do domínio tratam problemas diferentes.

Generics também evitam trocar uma restrição clara por um contrato amplo demais. Uma lista de Object pode receber valores sem relação entre si; quem a lê precisa descobrir que operações cada elemento oferece. Não escolha Object apenas para fazer uma chamada compilar. Se a função trabalha com alunos, declare esse tipo. Se trabalha com qualquer valor que oferece uma capacidade, considere uma interface que represente essa capacidade. O objetivo é expressar a relação necessária, sem tornar a assinatura mais flexível do que o uso exige.

Uma classe genérica pode ter campos e operações relacionados ao mesmo parâmetro; um método genérico pode declarar seu próprio parâmetro antes do retorno. Em static <T> T primeiro(List<T> itens), o tipo devolvido se relaciona ao tipo dos elementos recebidos. Essa assinatura ainda precisa definir o que fazer com uma lista vazia. Retornar null, lançar uma exceção ou devolver um resultado opcional são escolhas de contrato que devem aparecer na documentação e nos testes. Veja os métodos genéricos.

5. Herança entre elementos não vira herança entre listas

Um Integer pode ser usado como Number, mas List<Integer> não é uma List<Number>. Se a atribuição fosse permitida, um código que recebe a lista de números poderia acrescentar um Double à lista original de inteiros. Mais tarde, outro trecho esperaria ler um inteiro naquela posição. O compilador impede a atribuição para preservar a relação entre o tipo declarado e os elementos aceitos.

Use uma assinatura que corresponda à direção dos dados. Se uma função apenas lê números de uma lista recebida, ela não precisa poder acrescentar qualquer Number. Se outra função só acrescenta inteiros em um destino, ela não precisa saber que tipo específico aquele destino devolveria em todas as leituras. É essa diferença entre fornecer e receber valores que permite usar limites com curingas de maneira segura. Evite memorizar símbolos sem relacioná-los às operações que o método executa.

6. Limites extends e super na prática

Em List<? extends Number>, o tipo concreto dos elementos é desconhecido, mas é compatível com Number. Você pode ler um elemento como número. Não pode acrescentar arbitrariamente um Integer, pois a lista recebida poderia ser de Double. Em List<? super Integer>, o destino aceita inteiros, mas a leitura geral só permite assumir Object. Essa assinatura expressa uma capacidade de escrita, não a certeza de que todos os elementos são inteiros.

O método de cópia abaixo usa um parâmetro T para relacionar a origem e o destino. A origem fornece valores compatíveis com T, e o destino aceita esses valores. A lista de origem não é alterada; o destino acumula os elementos copiados. Antes de executar, observe as duas chamadas e explique qual relação de tipos permite cada uma. O exemplo não implementa cópia profunda dos objetos: ele transfere os valores dos elementos, que podem ser referências compartilhadas.

import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

public class Main {
    static <T> void copiar(List<? extends T> origem, List<? super T> destino) {
        for (T valor : origem) destino.add(valor);
    }
    public static void main(String[] args) {
        List<Integer> inteiros = Arrays.asList(2, 4, 6);
        List<Number> numeros = new ArrayList<>();
        copiar(inteiros, numeros);
        copiar(Arrays.asList(1.5, 2.5), numeros);
        System.out.println(numeros);
        System.out.println("Origem: " + inteiros);
    }
}

7. Apagamento de tipos e limites da verificação

A implementação de generics usa apagamento de tipos. Não é criada uma classe de execução diferente para cada combinação de parâmetros, como ArrayList<String> e ArrayList<Integer>. O compilador realiza verificações e adaptações apropriadas no código gerado. Por isso, algumas operações que parecem naturais para um tipo concreto não são permitidas com um parâmetro genérico, como criar diretamente new T() sem outra informação de construção.

Evite tipos crus e casts não verificados. Misturar uma lista parametrizada com código que a trata como lista crua pode permitir uma inclusão indevida e deslocar a falha para uma leitura posterior. O aviso do compilador é uma informação sobre a perda de garantia, e não um ruído que deve ser silenciado automaticamente. Investigue o limite da API ou adapte o código para manter a relação de tipos. O guia de apagamento de tipos explica o mecanismo.

8. Ordenar por uma regra explícita

Um comparador recebe dois valores e informa a relação de ordem entre eles. O sinal do resultado importa; não é necessário devolver a diferença aritmética entre números. Subtrair inteiros para comparar pode sofrer overflow. Use operações de comparação apropriadas ou construtores de comparadores, como comparingInt. Para uma consulta de notas, declare também os desempates. Duas notas iguais não dizem qual nome deve aparecer primeiro.

O programa a seguir preserva a lista de cadastro e ordena outra lista por nota decrescente e nome crescente. reversed() é aplicado ao critério da nota antes de acrescentar o desempate por nome. Aplicar a inversão depois de compor os dois critérios inverteria ambos. Desenhe a ordem esperada de Ana, Bruno e Carla antes de executar; depois confira que o cadastro continua na sequência original. A cópia da lista compartilha os alunos, que neste exemplo possuem apenas campos finais com valores imutáveis.

import java.util.ArrayList;
import java.util.Arrays;
import java.util.Comparator;
import java.util.List;

class Aluno {
    private final String nome;
    private final int nota;
    Aluno(String nome, int nota) {
        if (nome == null || nome.trim().isEmpty() || nota < 0 || nota > 10) {
            throw new IllegalArgumentException("Aluno inválido");
        }
        this.nome = nome;
        this.nota = nota;
    }
    String getNome() { return nome; }
    int getNota() { return nota; }
    @Override public String toString() { return nome + ":" + nota; }
}

public class Main {
    public static void main(String[] args) {
        List<Aluno> cadastro = Arrays.asList(
            new Aluno("Carla", 7), new Aluno("Ana", 9), new Aluno("Bruno", 7));
        List<Aluno> consulta = new ArrayList<>(cadastro);
        consulta.sort(Comparator.comparingInt(Aluno::getNota).reversed()
            .thenComparing(Aluno::getNome));
        System.out.println("Consulta: " + consulta);
        System.out.println("Cadastro: " + cadastro);
    }
}

9. Ordenação e igualdade precisam ser interpretadas juntas

Uma lista ordenada pode conter vários elementos que o comparador considera equivalentes. Já um conjunto ordenado, como TreeSet, usa a comparação para distinguir suas posições de elementos. Se um comparador considera apenas a nota, dois alunos com a mesma nota podem ser tratados como equivalentes nessa estrutura. Isso pode fazer um conjunto deixar de representar todos os alunos que o domínio considera diferentes. Não é um problema de ordenação aleatória: é uma escolha insuficiente de critério.

Se você precisa apenas apresentar uma consulta ordenada, uma cópia de lista costuma expressar melhor a intenção do que converter o cadastro para um conjunto. Se precisa de um conjunto ordenado, defina uma comparação compatível com a regra de igualdade desejada. Acrescente matrícula como desempate quando ela identifica o registro, e teste alunos com todos os demais campos iguais. Consulte o contrato de Comparator ao combinar estruturas ordenadas com igualdade.

10. Cópia, visão e fotografia do estado

Uma cópia de coleção cria outra estrutura, mas pode continuar compartilhando os objetos dos elementos. Uma visão não modificável pode apenas impedir que o receptor chame operações de alteração por aquele caminho; alterações feitas na coleção de origem ainda podem aparecer na visão. Uma fotografia independente exige copiar a estrutura e definir como tratar os elementos internos. Essas diferenças aparecem no contrato de um getter e na maneira como uma tela conserva resultados de consulta.

No estoque do tema 14, a consulta fará uma cópia do mapa e envolverá essa cópia com uma visão não modificável. Como as chaves são strings e os valores são inteiros empacotados, os elementos usados nesse modelo não permitem editar seu conteúdo interno. A fotografia permanece estável quando novas movimentações alteram o estoque. Se o mapa guardasse objetos mutáveis de produto, seria necessário decidir entre cópias, objetos de valor imutáveis ou uma projeção específica para consulta.

Teste a independência nos dois sentidos. Primeiro modifique a coleção devolvida e observe se a API permite isso. Depois altere o objeto de origem por uma operação legítima e confira se o resultado já guardado mudou. Uma API pode recusar a primeira operação e ainda permitir a segunda por compartilhar uma estrutura. Não use os termos “imutável”, “não modificável” e “cópia” como se descrevessem sempre o mesmo comportamento.

11. Consultas com streams e agregações

Depois de definir os tipos e as regras de igualdade, um pipeline de stream pode selecionar registros e produzir um resultado de consulta. Separe a fonte da agregação: filtrar alunos aprovados, extrair a nota e calcular uma média são operações diferentes. Verifique o caso vazio antes de usar o resultado de uma média opcional. Não substitua ausência por zero sem decidir que isso representa corretamente a situação. Uma turma sem alunos não possui necessariamente uma média igual a zero.

Ao produzir um mapa com coletores, considere chaves repetidas. Uma coleta que exige chave única pode lançar uma exceção quando o dado contém duplicações. Uma função de combinação deve representar uma política clara, como somar quantidades ou escolher o registro mais recente segundo um critério definido. Não escolha “ficar com o último” só para evitar a falha: isso pode apagar uma informação que deveria ter sido recusada. Em importações, a validação da identidade costuma preceder a consulta.

Evite alterar o cadastro de dentro de lambdas de consulta. Um pipeline com efeitos colaterais torna a ordem de avaliação e a observação do estado mais difíceis de acompanhar. Prefira produzir uma nova lista ou um total e aplicar alterações por operações explícitas do domínio. Essa separação também facilita testar o caso sequencial antes de considerar processamento paralelo, que exigirá outros cuidados no tema 13.

12. Escolher custo e memória de acordo com a tarefa

Uma busca linear percorre elementos até encontrar o alvo ou encerrar a sequência. Um mapa indexado pode reduzir o custo médio de consultas por chave, mas ocupa memória e exige atualização consistente. Uma ordenação reorganiza a consulta e tem custo diferente de uma simples filtragem. Para alguns poucos registros de estudo, a implementação mais clara pode ser suficiente. Para um volume maior, descreva a consulta frequente e meça o caminho que realmente consome tempo.

Não mantenha vários índices antes de precisar deles. Se o cadastro possui um mapa por matrícula e outro por nome, cada inclusão, atualização e remoção precisa preservar a coerência entre ambos. Um índice de nome pode mapear para vários alunos, pois nomes repetidos são possíveis. Uma alteração que atualiza só um índice produz resultados contraditórios. Teste uma sequência completa de inclusão, busca, atualização e remoção antes de concluir que o novo índice melhorou o programa.

13. Prática: cadastro, consulta e contratos verificáveis

Monte um cadastro por matrícula com pelo menos seis alunos, dois nomes repetidos e três notas iguais. Recuse uma inclusão com matrícula já existente. Produza uma consulta por nota sem alterar a ordem de inclusão. Depois devolva uma fotografia dos resultados e teste o comportamento quando o cadastro muda. Registre quais objetos continuam compartilhados e quais estruturas foram copiadas. O teste precisa verificar conteúdo e ordem, não apenas quantidade.

Explique também as assinaturas genéricas usadas na cópia. Mostre uma chamada válida e outra que o compilador deve recusar, e restaure o programa executável ao terminar. Uma tentativa de compilação recusada pode ensinar o contrato, mas não deve ser confundida com uma falha em tempo de execução. Use as atividades deste tema no Playground para guardar rascunhos independentes. A seção Laboratórios de continuidade propõe variações desse cadastro.

Se dois alunos têm a mesma nota, posso usar só a nota para guardá-los em um TreeSet?

Esse critério pode tratar os alunos como equivalentes e manter apenas um deles. Para uma consulta ordenada que admite empates, use uma lista. Para um conjunto, a comparação precisa distinguir os registros de acordo com a igualdade pretendida, por exemplo incluindo matrícula.

Uma lista não modificável prova que os alunos internos nunca mudarão?

Não. A restrição da lista não determina a mutabilidade dos elementos. Se os alunos forem mutáveis e compartilhados, suas notas poderão mudar por outra referência. Defina uma projeção ou uma política de cópia que corresponda ao contrato da consulta.

12 · Arquivos, dados e persistência confiável

1. Da memória do programa a um dado que sobrevive

Uma coleção em memória deixa de existir quando o processo termina. Persistir é representar o estado em um meio que possa ser lido depois, como um arquivo ou banco de dados. Essa mudança acrescenta falhas que um exemplo de console não apresenta: falta de permissão, conteúdo interrompido, codificação diferente e registros incompatíveis com a versão atual. O programa precisa distinguir “não há dados ainda” de “há dados, mas não foi possível lê-los”. Tratar ambos como cadastro vazio pode ocultar perda de informação.

Continue usando o cadastro por matrícula do tema 11. Antes de escolher uma API de arquivo, descreva o formato: quais campos existem, como são separados, quais valores são obrigatórios e como uma linha inválida deve ser tratada. A política deste tema é validar uma importação inteira em uma estrutura temporária e publicar o novo cadastro somente depois do sucesso. Assim, uma falha na segunda linha não substitui o estado atual por um cadastro parcial.

O Playground permite testar a leitura e a validação usando texto em memória. O acesso a arquivos reais do dispositivo pertence ao projeto local, com JDK instalado. A JVM do navegador usa seu próprio ambiente virtual e não abre automaticamente sua pasta pessoal. Os programas de leitura em memória demonstram a regra sem exigir acesso ao disco; o pacote em Extra inclui um programa local de gravação e leitura para completar a experiência.

2. Caminho, arquivo e diretório são conceitos distintos

Um Path representa um caminho; criá-lo não cria o arquivo nem confirma que ele existe. Um caminho relativo depende do diretório de trabalho do processo. A pasta que contém o fonte e a pasta de execução podem ser diferentes, principalmente numa IDE. Por isso, um programa que procura dados/alunos.txt deve explicar qual é sua base de execução. Para investigar uma falha, apresente o caminho resolvido em um diagnóstico local, sem assumir que a instalação de outra pessoa possui o mesmo diretório.

Combine trechos com resolve em vez de concatenar manualmente barras de um sistema operacional. Uma normalização sintática pode retirar segmentos redundantes, mas não garante autorização de acesso nem resolve todos os efeitos de links simbólicos. Se um programa aceita caminhos externos, precisa definir o limite permitido. Neste guia, os exercícios locais gravam dentro de um diretório de trabalho escolhido para eles; não solicitam acesso arbitrário a arquivos do sistema. O guia de operações com Path explica a composição.

Também evite verificar existência e assumir que a operação seguinte necessariamente terá sucesso. O arquivo pode mudar entre a verificação e a abertura. Trate a exceção da própria operação e informe o que não foi concluído. Um diretório com o nome esperado não é o mesmo que um arquivo legível, e um arquivo existente pode ter outro formato. Validação do caminho, abertura e interpretação do conteúdo pertencem a etapas diferentes.

3. Codificação e fronteiras entre bytes e texto

Arquivos armazenam bytes. Uma codificação define como interpretá-los como texto. Se você grava em UTF-8 e lê com outra codificação, nomes acentuados podem aparecer incorretos. Declare a codificação nas operações que oferecem essa escolha, por exemplo StandardCharsets.UTF_8. Não tente corrigir os caracteres trocando letras depois da leitura sem investigar a origem: isso pode mascarar o problema e alterar dados que estavam corretos.

Uma linha é uma convenção do formato textual. Leitores podem reconhecer quebras de linha sem devolver esses separadores no conteúdo lido. Isso facilita processar registros por linha, mas exige cuidado se o próprio campo puder conter uma quebra. Para o formato didático deste tema, cada registro cabe em uma linha e os campos não contêm o separador. Esse limite é parte do contrato. Um CSV geral permite situações adicionais e precisa de um parser que implemente suas regras, não apenas de uma chamada a split.

Defina também como tratar espaços e linhas vazias. Matrículas podem ser normalizadas com trim se espaços nas bordas não tiverem significado no domínio. Um texto livre pode precisar preservá-los. Uma linha vazia pode ser ignorada ou rejeitada, mas a decisão precisa ser consistente e testada. Não remova silenciosamente todo caractere que cause uma falha, pois o resultado pode passar a representar outro registro.

4. Ler tudo ou processar em fluxo

Ler o conteúdo inteiro simplifica alguns exercícios pequenos, mas consome memória proporcional ao tamanho do arquivo. Processar com um leitor por linhas permite trabalhar progressivamente. Isso não garante consumo constante se o programa ainda guardar todos os registros numa lista; a estrutura final também ocupa memória. Identifique o que precisa permanecer disponível: um total pode ser acumulado sem guardar cada linha, enquanto um cadastro completo exige uma representação dos dados aceitos.

A API Files oferece operações de leitura e escrita, e leitores com buffer ajudam no processamento textual. Ao usar uma stream de linhas vinculada a arquivo, feche a stream conforme seu contrato. Uma stream sobre uma coleção em memória e uma stream que mantém um recurso de I/O não têm o mesmo ciclo de vida externo. Consulte Files para conferir tipos de retorno, codificação, opções e exceções.

Antes de otimizar, experimente um arquivo com poucas linhas conhecidas e outro com volume maior gerado para o teste. Verifique a mesma regra nos dois casos. Se a versão em fluxo aceita uma linha que a versão em memória recusa, elas não são equivalentes. O tamanho da entrada deve mudar o custo do processamento, não o significado dos campos.

5. Fechar o recurso que sua operação abriu

Try-with-resources delimita a propriedade de recursos fecháveis. O método que abre um leitor de arquivo geralmente é responsável por fechá-lo. Se ele recebe um leitor de outro componente, o contrato precisa dizer quem controla o fechamento. Esse detalhe evita fechar uma entrada compartilhada que outra parte do programa ainda precisa usar. O caso de System.in, estudado antes, continua sendo um exemplo de recurso cujo ciclo de vida ultrapassa uma pequena operação auxiliar.

O fechamento pode falhar, e uma operação de leitura também pode lançar uma exceção antes dele. O mecanismo de try-with-resources preserva a falha principal e pode registrar outras como suprimidas. Ao investigar um erro local, confira causa e exceções associadas. Para o usuário final, a mensagem deve dizer que a leitura ou gravação não foi concluída e qual ação é possível. O texto técnico completo pode pertencer ao diagnóstico, não a uma confirmação de sucesso.

Uma mensagem como “arquivo salvo” só deve ser apresentada depois que a operação correspondente terminar. Preencher um buffer ou criar um objeto de caminho não comprova que os dados chegaram ao destino. No projeto de estudo, coloque a confirmação após o fechamento bem-sucedido da escrita. Nos sistemas em que durabilidade diante de falhas de energia é requisito, são necessárias decisões adicionais sobre sistema de arquivos e sincronização; uma chamada de alto nível não promete tudo isso automaticamente.

6. Um formato de registro pequeno e verificável

O formato inicial terá duas colunas: matrícula e nota inteira, separadas por ponto e vírgula. Exemplo: A01;8. Matrícula não pode ser vazia; nota deve estar entre 0 e 10; matrícula repetida é recusada. Um registro com três colunas ou com a segunda coluna vazia também deve falhar. A chamada split(";", -1) preserva campos vazios no final, permitindo reconhecer uma nota ausente em vez de perder essa informação durante a separação.

A numeração de linhas ajuda a localizar a entrada que falhou. Conte cada linha física processada antes de validá-la e mantenha esse número na mensagem. Para erros de conversão, preserve a exceção original como causa ao acrescentar o contexto da linha. Não devolva uma mensagem genérica que diga apenas “erro” se a operação consegue informar qual campo não correspondeu ao formato. Ao mesmo tempo, não apresente como inválido um arquivo inteiro quando o problema foi uma permissão de leitura.

Esse formato não aceita ponto e vírgula dentro da matrícula. Não o anuncie como leitor de qualquer CSV. Se o domínio crescer para nomes com separadores, aspas e quebras de linha, escolha e documente uma representação adequada, como um formato com parser específico. A biblioteca utilizada também precisa ser distribuída e configurada no projeto local. Esconder esse requisito faria o exemplo depender de algo que o leitor não recebeu.

7. Importação em duas etapas: validar e publicar

O programa abaixo recebe o conteúdo em uma string para que possa ser executado diretamente no site. O leitor usado é fechado dentro da operação de importação. Cada linha é validada e inserida num mapa novo, que só é devolvido quando a leitura termina. A variável atual recebe esse novo mapa apenas se a chamada retornar normalmente. Quando a segunda importação falha, a atribuição não acontece e o cadastro anterior continua disponível.

Observe que validar em uma estrutura temporária consome memória para o novo conjunto de dados. Essa política é simples e útil para o exercício, mas não serve como promessa para arquivos de qualquer tamanho. Uma importação muito grande pode precisar de processamento em lotes e transações no armazenamento final. Primeiro compreenda qual estado deve ser visível em caso de falha; depois escolha uma estratégia que preserve esse contrato dentro dos limites do ambiente.

import java.io.BufferedReader;
import java.io.IOException;
import java.io.StringReader;
import java.util.LinkedHashMap;
import java.util.Map;

public class Main {
    static Map<String, Integer> importar(String texto) throws IOException {
        Map<String, Integer> novo = new LinkedHashMap<>();
        try (BufferedReader leitor = new BufferedReader(new StringReader(texto))) {
            String linha;
            int numero = 0;
            while ((linha = leitor.readLine()) != null) {
                numero++;
                String[] partes = linha.split(";", -1);
                if (partes.length != 2 || partes[0].trim().isEmpty()) {
                    throw new IllegalArgumentException("Linha " + numero + " inválida");
                }
                String id = partes[0].trim();
                int nota;
                try { nota = Integer.parseInt(partes[1].trim()); }
                catch (NumberFormatException erro) {
                    throw new IllegalArgumentException("Nota inválida na linha " + numero, erro);
                }
                if (nota < 0 || nota > 10 || novo.containsKey(id)) {
                    throw new IllegalArgumentException("Regra inválida na linha " + numero);
                }
                novo.put(id, nota);
            }
        }
        return novo;
    }
    public static void main(String[] args) throws IOException {
        Map<String, Integer> atual = importar("A01;8\nA02;7\n");
        System.out.println("Cadastro: " + atual);
        try { atual = importar("A03;9\nA04;texto\n"); }
        catch (IllegalArgumentException erro) { System.out.println(erro.getMessage()); }
        System.out.println("Após recusa: " + atual);
    }
}

8. Falha completa e aceitação parcial são políticas diferentes

Recusar o lote inteiro é uma escolha. Outra possibilidade é aceitar linhas válidas e emitir um relatório das recusadas. Essa segunda política precisa dizer quais linhas foram publicadas, quais falharam e como reexecutar sem duplicar dados. Um simples catch dentro do laço, seguido de uma confirmação de importação, não descreve adequadamente o resultado. O chamador pode acreditar que todos os registros foram aceitos quando apenas parte deles entrou.

Para exercitar as duas políticas, prepare três registros e torne o segundo inválido. Na política do exemplo, nenhum deles substitui o cadastro anterior. Uma operação idempotente produz o mesmo efeito observável quando repetida nas condições definidas; ela não é obtida apenas por dar esse nome ao método.

9. Gravação substitutiva e arquivo temporário

Gravar diretamente por cima do arquivo atual pode deixá-lo incompleto se a operação for interrompida. Para o projeto local, uma estratégia é escrever a nova representação em um arquivo temporário no mesmo diretório, fechar a escrita e só então tentar substituir o destino. A movimentação atômica, quando suportada pelo provedor e pelas condições da operação, pode evitar que um leitor observe uma representação parcialmente substituída. Confira as opções e as exceções da API antes de prometer essa propriedade.

Se ATOMIC_MOVE não for suportado, você precisa escolher uma política explícita: informar que não conseguiu concluir com a garantia exigida ou aplicar uma alternativa que ofereça uma garantia diferente e a documente. Não capture qualquer falha de I/O e apresente a substituição comum como se fosse equivalente. Um problema de permissão, espaço ou caminho não significa simplesmente que o movimento atômico está indisponível.

O pacote local em Extra demonstra criar um diretório próprio para os arquivos do exercício e gravar uma nova representação antes da leitura de conferência. Mantenha cópias dos dados que precisam ser preservados e teste uma falha num diretório de estudo, sem experimentar sobre documentos pessoais. A documentação de leitura e escrita ajuda a relacionar abertura, fechamento e opções de criação. A operação do exemplo não configura, por si só, um sistema de backup.

10. Datas civis, instantes e relógio do teste

Uma data de vencimento como 22 de outubro não contém, por si só, horário nem fuso. LocalDate representa essa data civil. Um instante representa um ponto na linha do tempo e exige outra interpretação para exibição em um local. Não converta uma data civil para milissegundos inventando um horário apenas para fazer uma comparação. Escolha o tipo de acordo com o significado do dado e defina como o programa interpreta o limite de um prazo.

Usar a data atual diretamente em todos os métodos torna alguns testes dependentes do dia da execução. Para verificar uma regra de prazo, receba a data de referência como argumento ou use um relógio controlável na parte que o consulta. O exemplo a seguir usa uma data fixa para que qualquer pessoa consiga repetir a mesma saída. Não interprete a data escolhida como uma consulta ao calendário atual do dispositivo.

Teste a travessia do fim do mês, do fim do ano e de um fevereiro com duração diferente. Acrescentar um mês e acrescentar trinta dias não são operações equivalentes em todo calendário. Ao ler datas em um arquivo, declare o formato aceito e recuse ambiguidades como uma string que possa representar dia e mês em ordens diferentes. A família java.time separa tipos de acordo com esses significados.

11. Decimais com escala e arredondamento definidos

Quando a regra exige aritmética decimal controlada, BigDecimal permite representar números decimais e escolher escala e arredondamento. Construa o valor a partir de uma string decimal quando ela expressa o dado esperado. Criá-lo diretamente a partir de um double pode carregar a aproximação binária que você pretendia evitar. O tipo não escolhe sozinho a regra comercial, o momento do arredondamento ou a moeda utilizada.

Uma divisão decimal pode não terminar. Dividir sem definir uma política apropriada pode causar uma exceção quando não existe representação exata nas condições da chamada. Decida a escala e o modo de arredondamento no ponto exigido pelo contrato, em vez de aplicar duas casas em toda etapa por hábito. Arredondar cada item e depois somar pode produzir outro total que somar valores exatos e arredondar só no final. Os dois cálculos representam políticas distintas.

A comparação também exige intenção. equals leva em conta a representação com escala; compareTo permite comparar o valor numérico. Assim, 2.0 e 2.00 podem ter comparação numérica igual a zero sem serem iguais segundo equals. Se um valor decimal será uma chave ou parte da igualdade de um objeto, defina uma representação canônica consistente. Consulte BigDecimal antes de combinar comparação, armazenamento e arredondamento.

import java.math.BigDecimal;

13 · Concorrência e coordenação de tarefas

1. Quando duas tarefas passam a existir ao mesmo tempo

Até aqui, acompanhamos um fluxo principal: ler, validar, calcular e apresentar. Uma aplicação maior pode receber várias solicitações, processar arquivos e aguardar respostas externas em tarefas distintas. Concorrência permite lidar com execuções que se sobrepõem no tempo; paralelismo envolve execução simultânea. O programa continua precisando de uma regra clara mesmo quando a ordem de passos entre tarefas varia. Uma saída que aparece correta numa execução isolada não comprova que a coordenação está correta.

Comece separando tarefas independentes de tarefas que alteram o mesmo estado. Calcular quadrados de dois números usando apenas variáveis locais é diferente de duas retiradas que leem o mesmo estoque e gravam um novo saldo. No primeiro caso, é possível combinar resultados depois. No segundo, a regra de disponibilidade precisa ser preservada durante toda a operação que a verifica e altera. A presença de várias threads torna explícita uma fronteira de alteração que já existia no domínio.

Os exemplos deste tema usam a biblioteca de concorrência disponível no ambiente do site. Eles possuem quantidades pequenas de tarefas e produzem resultados apresentados pelo fluxo principal, para permitir conferência. Não use um laço enorme como demonstração de capacidade de uma máquina. O tempo e os recursos variam entre dispositivos; a primeira pergunta deve ser se a regra continua correta, e depois se a execução concorrente ajuda a tarefa real.

2. Thread, start, run e a ordem observada

Uma thread possui seu fluxo de execução. Chamar start() solicita que uma nova thread execute seu trabalho; chamar run() diretamente é uma chamada comum de método na thread atual. O nome de uma classe ou de uma variável não cria paralelismo. Também não há garantia geral de que a thread iniciada primeiro apresentará sua primeira mensagem antes das demais. O escalonamento pode variar entre execuções.

Para aprender a diferença, crie duas tarefas curtas que apenas calculam valores e devolvem resultados. Evite usar a ordem de mensagens do console como a regra principal do teste. Duas ordens de impressão podem ser válidas se as tarefas são independentes. Quando a aplicação exige ordem de apresentação, imponha essa ordem no componente que reúne os resultados, em vez de esperar que a velocidade de cada tarefa produza a sequência desejada.

Um atraso com sleep não é uma maneira confiável de provar que outra tarefa terminou. A duração escolhida pode ser insuficiente em outro dispositivo e desperdiçar tempo quando o trabalho já acabou. Use um mecanismo de conclusão, como join, um Future ou uma coordenação apropriada ao caso. O teste deve esperar pelo evento que importa, e não por uma estimativa de quanto tempo ele costuma levar.

3. Estado compartilhado e operações compostas

Considere contador++. A expressão envolve obter um valor, calcular outro e gravá-lo. Duas tarefas podem ler o mesmo valor antes de ambas gravarem o incremento, fazendo uma atualização se perder. Mesmo que cada leitura isolada pareça simples, a sequência inteira precisa de uma propriedade de coordenação. O resultado esperado de quatro tarefas com mil incrementos é quatro mil; um contador comum compartilhado não oferece essa garantia automaticamente.

A mesma ideia aparece no estoque: verificar que há cinco unidades e depois retirar quatro precisa ser tratado junto quando duas tarefas podem fazer a mesma solicitação. Proteger só a leitura ou só a escrita não impede que ambas decidam com base numa disponibilidade anterior. Identifique a região crítica pela regra de negócio que deve permanecer verdadeira. A unidade de coordenação deve cobrir a decisão e a alteração correspondentes.

Um defeito concorrente pode não aparecer em várias tentativas e surgir depois de uma alteração de carga. A ausência de falha observada não equivale a uma prova de segurança. Para o exercício, desenhe uma intercalação possível: tarefa A lê cinco, tarefa B lê cinco, A grava um, B grava um. O saldo final não representa duas retiradas de quatro e o programa pode ter anunciado dois sucessos. Esse rastreamento explica o problema sem depender da sorte de uma execução.

4. Exclusão mútua e visibilidade

Uma região sincronizada pode garantir que apenas uma thread por vez entre naquela região usando o mesmo monitor. A coordenação também participa da visibilidade entre leituras e escritas conforme o modelo de memória. A garantia depende de todos os caminhos relevantes usarem uma estratégia consistente. Proteger uma operação com um objeto de bloqueio e outra com um objeto diferente não cria automaticamente exclusão entre elas.

Mantenha a região crítica focada no estado e na regra que ela protege. Fazer uma chamada de rede ou esperar indefinidamente por outra tarefa dentro do bloqueio pode impedir outros trabalhos de avançar. Se a operação precisa de um recurso externo, separe o que pode ser preparado antes e defina como verificar o estado de novo no momento da alteração. A documentação de sincronização apresenta interferência e consistência de memória.

A palavra-chave volatile ajuda a estabelecer visibilidade para acessos ao campo, mas não transforma qualquer sequência composta em uma operação indivisível. Um contador volátil ainda não faz contador++ virar um incremento atômico. Escolha a ferramenta pela propriedade necessária: publicar uma sinalização, atualizar um número isolado e preservar a relação entre vários campos são problemas diferentes.

5. Atualizações atômicas e o limite do que elas protegem

AtomicInteger oferece operações atômicas para um valor inteiro. No exemplo abaixo, cada incremento é coordenado, e o fluxo principal aguarda todas as tarefas antes de apresentar o total. A combinação dessas duas decisões importa: um contador protegido consultado antes do término das tarefas ainda pode mostrar um valor parcial. Atomicidade da operação e conclusão do trabalho são propriedades distintas.

Não conclua que dois campos atômicos preservam automaticamente uma regra entre eles. Uma transferência com saldo de origem e destino precisa de um contrato para a operação composta. Atualizar cada saldo separadamente pode permitir que outro observador veja um estado intermediário. Para o primeiro exercício, mantenha uma regra pequena e isolada; para a transferência, identifique a transação do domínio e escolha uma coordenação que cubra o conjunto necessário.

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    public static void main(String[] args) throws Exception {
        AtomicInteger contador = new AtomicInteger();
        ExecutorService executor = Executors.newFixedThreadPool(2);
        List<Future<?>> tarefas = new ArrayList<>();
        try {
            for (int t = 0; t < 4; t++) {
                tarefas.add(executor.submit(() -> {
                    for (int i = 0; i < 1000; i++) contador.incrementAndGet();
                }));
            }
            for (Future<?> tarefa : tarefas) tarefa.get();
            System.out.println("Total: " + contador.get());
        } finally {
            executor.shutdownNow();
        }
    }
}

6. Separar tarefa de administração das threads

Criar uma thread para cada pequeno cálculo espalha detalhes de ciclo de vida e pode consumir recursos sem controle. Uma fila que aceita trabalho mais rápido do que ele é concluído pode crescer e pressionar memória. Em uma aplicação real, defina a capacidade de espera e o que fazer quando ela for atingida: recusar, aguardar por um limite ou reduzir a produção. O exemplo didático usa apenas duas tarefas conhecidas para concentrar a leitura no resultado. Ele não é uma configuração pronta para receber solicitações sem limite. 7. Future representa resultado ou falha de uma tarefa

Ao submeter um cálculo, você pode receber um Future. A chamada a get aguarda sua conclusão quando o resultado ainda não está disponível. Uma tarefa pode terminar com sucesso, lançar uma falha ou ser cancelada. Uma exceção de execução não deve ser convertida silenciosamente em um número que pareça um resultado válido. Diferencie ausência de resultado, falha e valor zero quando eles têm significados distintos.

No programa a seguir, o cálculo das duas potências pode ocorrer em tarefas distintas, mas a apresentação segue a ordem escolhida pelo fluxo principal. Consultar novamente um Future concluído devolve seu resultado; isso não agenda o mesmo cálculo de novo. Antes de executar, preveja cada valor e a soma. Depois acrescente uma tarefa que falha e observe que obter seu resultado exige tratar o caminho de falha, não apenas somar um valor substituto.

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class Main {
    public static void main(String[] args) throws Exception {
        ExecutorService executor = Executors.newFixedThreadPool(2);
        try {
            Future<Integer> primeira = executor.submit(() -> 12 * 12);
            Future<Integer> segunda = executor.submit(() -> 7 * 7);
            System.out.println("Primeira: " + primeira.get());
            System.out.println("Segunda: " + segunda.get());
            System.out.println("Soma: " + (primeira.get() + segunda.get()));
        } finally {
            executor.shutdownNow();
        }
    }
}

8. Tempo limite, cancelamento e interrupção

Esperar sem limite pode tornar uma interface incapaz de responder quando um recurso externo não termina. Algumas operações oferecem espera com timeout. Quando esse limite termina, a tarefa não necessariamente parou: o timeout descreve o que aconteceu com a espera. Se o contrato exige cancelar o trabalho, solicite o cancelamento apropriado e considere se a operação responde a essa solicitação. Não apresente a ausência de resposta como uma confirmação de que nada foi alterado.

Interrupção é um mecanismo cooperativo. Uma tarefa precisa executar operações que a reconheçam ou verificar a sinalização em pontos adequados. Capturar InterruptedException e continuar um laço sem decisão pode ignorar o pedido de encerramento. Quando um método não consegue tratar o pedido e precisa repassá-lo por outro caminho, pode ser necessário restaurar a sinalização de interrupção. A política deve combinar com o nível que controla o ciclo de vida da tarefa. Consulte o guia de interrupções.

Uma operação de negócio que já produziu efeito não é desfeita automaticamente pelo cancelamento de quem estava esperando. Uma compra enviada a um serviço externo pode ter sido aceita mesmo que a resposta não chegou. Esse caso exige um identificador de operação e um protocolo para consultar ou repetir com segurança, discutido no Extra. O mecanismo de thread, sozinho, não decide a semântica da operação.

9. Encerrar o executor faz parte do programa

Um executor possui ciclo de vida. shutdown deixa de aceitar novas tarefas e permite concluir as já submetidas conforme o contrato. shutdownNow tenta interromper tarefas em andamento e devolve as que não chegaram a começar; não garante que qualquer trabalho arbitrário obedecerá imediatamente. Uma aplicação que cria executores sem encerrá-los pode continuar consumindo recursos ou impedir o término esperado do processo.

Os exemplos usam um bloco finally para solicitar o encerramento mesmo se a obtenção de um resultado falhar. Em aplicações com trabalho que precisa terminar de forma ordenada, defina um período de espera, confira a conclusão e escolha uma política de encerramento adicional. Não use um finally para imprimir “tudo concluído” se houve falha ou cancelamento. O estado final apresentado ao usuário deve corresponder ao que foi confirmado.

10. Coleções concorrentes e sequências de decisões

Uma coleção concorrente oferece garantias próprias para suas operações. Isso não significa que qualquer combinação de chamadas feitas pelo seu código se torna uma transação. Consultar um mapa, verificar ausência e depois inserir são vários passos. Quando a intenção é uma inclusão condicional, procure uma operação que represente esse contrato ou proteja a sequência no nível necessário. Leia também as regras das funções executadas por métodos de atualização.

Um iterador de uma coleção concorrente pode oferecer uma forma de observação diferente da de uma lista comum. Não suponha que ele produz uma fotografia estável do cadastro inteiro. Se uma tela precisa de um relatório consistente em determinado instante, defina como a fotografia será produzida. Uma coleção segura para acesso simultâneo não determina, sozinha, que todos os valores de um relatório representam o mesmo momento do domínio.

Evite tentar resolver toda aplicação substituindo HashMap por ConcurrentHashMap. Essa troca não corrige invariantes distribuídos por vários objetos, ordem de chamadas, erros de persistência ou relatórios mal definidos. Primeiro declare quem pode alterar o estado e como a alteração é confirmada. Depois escolha a coleção que atende ao padrão de acesso que permaneceu.

11. Compor etapas assíncronas sem perder as falhas

CompletableFuture permite compor etapas que produzem e transformam resultados. Uma transformação como thenApply calcula outro valor a partir do resultado anterior. Uma composição como thenCompose conecta uma etapa que já devolve outro futuro. Confundir as duas pode produzir estruturas aninhadas que dificultam perceber qual conclusão está sendo aguardada. Desenhe o tipo de entrada e saída de cada etapa antes de encadear chamadas.

As versões assíncronas e o executor utilizado também influenciam onde o trabalho é executado. Não envie tarefas bloqueantes sem avaliar o recurso que ficará ocupado. Um pipeline deve preservar as falhas até um ponto capaz de decidir recuperação ou apresentação. Retornar uma lista vazia em qualquer exceção pode fazer uma indisponibilidade parecer uma consulta legítima sem registros. A API de CompletableFuture descreve os caminhos de composição e conclusão.

Para o estudo, comece com uma etapa que produz uma nota, outra que calcula a situação e uma última que monta uma mensagem. Teste uma falha na primeira etapa e confira se a apresentação continua distinguindo falha de reprovação. Só depois substitua a etapa inicial por uma chamada externa. Assim, a semântica da composição pode ser verificada antes de acrescentar a variabilidade da rede.

12. Deadlock, ordem de bloqueios e trabalho limitado

Um deadlock pode acontecer quando tarefas ficam esperando recursos umas das outras sem conseguir avançar. Por exemplo, uma segura o bloqueio da conta A e espera B, enquanto outra segura B e espera A. Uma política consistente de ordem dos bloqueios pode evitar esse ciclo nesse modelo. A solução precisa ser aplicada em todos os caminhos da operação; um método que usa a ordem inversa reintroduz a possibilidade de espera circular.

Outro problema aparece quando todas as threads de um pool aguardam tarefas que também precisam daquele mesmo pool para começar. Limitar threads não dispensa analisar as dependências entre tarefas. Evite submeter trabalho e bloquear indiscriminadamente dentro de uma tarefa do mesmo recurso limitado. Descreva quem espera por quem e teste o encerramento sem usar apenas um timeout para esconder o travamento.

Virtual threads, disponíveis a partir de Java 21, mudam parte do custo de administrar threads, mas não corrigem automaticamente dados compartilhados, deadlocks ou limites de um serviço externo. Elas não pertencem à JVM Java 17 do Playground. Estude esse recurso em um JDK local compatível depois de compreender o contrato da tarefa. O limite de conexões de um banco, por exemplo, continua sendo uma restrição relevante mesmo com muitas tarefas leves.

13. Prática: conclusão, falha e estado observável

Execute as duas atividades e confira seus resultados. Depois mude a quantidade de incrementos, mantendo a previsão do total. Crie uma tarefa que falha e outra que conclui, e apresente os estados separadamente. Verifique que o executor é encerrado nos dois caminhos. Não conte uma tarefa que lançou exceção como concluída com sucesso apenas porque seu processamento terminou.

Para uma retirada concorrente, comece pelo desenho de duas solicitações disputando o mesmo estoque. Escreva a regra: a soma das retiradas aceitas não pode superar a quantidade disponível. Identifique a operação composta que precisa de proteção e teste o saldo posterior. Uma repetição de teste ajuda a procurar sintomas, mas a justificativa do mecanismo de coordenação deve explicar por que uma intercalação inválida não consegue publicar dois sucessos.

AtomicInteger garante que uma transferência entre dois saldos será uma única operação?

Não. Cada atualização isolada possui seu contrato, mas a regra entre origem e destino ainda exige uma coordenação que cubra a operação composta. O estado intermediário precisa ser considerado por quem pode observá-lo.

Se Future.get com timeout falhou por tempo, posso afirmar que a tarefa não mudou nada?

Não. O limite terminou para a espera. A tarefa pode continuar ou já ter produzido efeitos. Cancelamento, confirmação e eventual consulta posterior precisam de uma política definida para a operação.

2. Requisitos observáveis antes das classes

Escreva os requisitos em termos de operações e efeitos. Receber cinco unidades de um item válido deve aumentar sua disponibilidade em cinco. Retirar duas de um saldo cinco deve aceitar a operação e deixar três. Retirar quatro de um saldo três deve recusar e manter três. A identidade do item é um texto não vazio. Neste modelo, A e a são identificadores diferentes; o programa não transforma a grafia por conta própria. Se você preferir ignorar maiúsculas, a normalização precisa acontecer de forma consistente em todas as operações e nos dados persistidos. Faça essa escolha antes de gravar um cadastro. 3. Escolher responsabilidades que acompanham mudanças

A classe de domínio concentra disponibilidade e movimentações. A interface de console interpreta comandos e apresenta mensagens. O teste chama a classe de domínio diretamente para verificar suas regras. Separar essas responsabilidades permite alterar a forma de entrada sem reescrever a aritmética de estoque. Também evita que uma validação de quantidade só funcione quando o usuário passa por determinado menu.

Não coloque um Scanner dentro de cada método de estoque. O domínio deve receber identificador e quantidade já representados em tipos apropriados. Isso não elimina sua validação: o método ainda precisa impedir argumentos inválidos de qualquer chamador. A interface valida o formato de entrada; o domínio valida a operação. Uma string “dois” falha na conversão; um inteiro -2 falha na regra. Saber em qual fronteira o erro ocorreu ajuda a apresentar uma orientação correta.

Comece com poucas classes e dependências explícitas. Uma interface é útil quando existe um contrato que precisa de implementações distintas, como um repositório em memória e outro persistente. Ela não é obrigatória para cada classe pequena do exercício. Introduzir camadas vazias torna o caminho da operação mais difícil de acompanhar sem acrescentar uma responsabilidade. A organização deve permitir localizar a regra pelo nome da operação.

4. Representação do estado e invariantes

O mapa associa um identificador à quantidade disponível. A invariante principal é que uma operação aceita não deixa quantidade negativa. O tipo int possui limite, por isso a soma de recebimento usa Math.addExact. Se houver overflow, a exceção acontece antes de publicar o novo valor no mapa. Fazer a soma diretamente e gravar o número transbordado quebraria a regra mesmo com argumentos individualmente positivos.

Uma retirada consulta o saldo, compara a quantidade solicitada e só altera quando há disponibilidade suficiente. Nesse modelo, item ausente possui disponibilidade zero para a decisão de retirada. A consulta do cadastro continua permitindo distinguir ausência de um registro e registro com quantidade zero, pois o mapa apresentado mostra quais chaves existem. Decida se um item que chega a zero permanece cadastrado; a versão inicial mantém a chave para tornar a regra simples e verificável.

A criação de uma fotografia copia o mapa antes de aplicar uma restrição de modificação. Assim, o receptor não consegue editar o estoque por aquele resultado, e recebimentos posteriores não mudam a fotografia já guardada. Essa independência se baseia também nos tipos dos elementos: strings e inteiros empacotados não oferecem alteração interna de conteúdo. Trocar o valor por um objeto mutável exigiria rever a política de cópia.

5. Operações de domínio com resultado claro

No exemplo, um argumento inválido lança IllegalArgumentException; uma falta de disponibilidade retorna false. Essa distinção comunica que a solicitação tem formato e intervalo válidos, mas não pôde ser atendida no estado atual. Outra API poderia representar recusas de outro modo. O ponto necessário é manter a política consistente e não apresentar sucesso quando a retirada não aconteceu.

Leia o programa inteiro antes de executá-lo. O primeiro recebimento cria disponibilidade cinco. A retirada aceita deixa três. A fotografia é obtida nesse momento. A retirada seguinte pede quatro, recebe recusa e mantém três. Um recebimento posterior muda o estado atual para quatro, mas a fotografia anterior deve continuar mostrando três. A saída inicial confere a recusa e a independência da fotografia em uma sequência curta.

import java.util.Collections;
import java.util.LinkedHashMap;
import java.util.Map;

class Estoque {
    private final Map<String, Integer> itens = new LinkedHashMap<>();
    private static void validar(String id, int quantidade) {
        if (id == null || id.trim().isEmpty() || quantidade <= 0) {
            throw new IllegalArgumentException("Dados inválidos");
        }
    }
    void receber(String id, int quantidade) {
        validar(id, quantidade);
        int novo = Math.addExact(itens.getOrDefault(id, 0), quantidade);
        itens.put(id, novo);
    }
    boolean retirar(String id, int quantidade) {
        validar(id, quantidade);
        int atual = itens.getOrDefault(id, 0);
        if (quantidade > atual) return false;
        itens.put(id, atual - quantidade);
        return true;
    }
    Map<String, Integer> consultar() {
        return Collections.unmodifiableMap(new LinkedHashMap<>(itens));
    }
}

public class Main {
    public static void main(String[] args) {
        Estoque estoque = new Estoque();
        estoque.receber("A", 5);
        System.out.println("Retirada aceita: " + estoque.retirar("A", 2));
        Map<String, Integer> fotografia = estoque.consultar();
        System.out.println("Retirada recusada: " + estoque.retirar("A", 4));
        System.out.println("Estoque: " + estoque.consultar());
        estoque.receber("A", 1);
        System.out.println("Fotografia anterior: " + fotografia);
    }
}

6. Separar formato, regra e apresentação de falha

Na versão de console, uma linha de comando pode conter a ação, o identificador e a quantidade. A interface primeiro verifica a estrutura e converte a quantidade. Depois chama o domínio e interpreta o resultado. Um comando desconhecido deve produzir uma orientação e permitir nova entrada, sem cair em uma operação arbitrária de recebimento ou retirada. A leitura do fim da entrada também precisa encerrar o fluxo sem tentar obter uma linha inexistente.

Trate exceções específicas nos pontos que conseguem orientar a correção. Um erro de conversão pode informar que a quantidade precisa ser inteira. Uma violação de regra pode apresentar a mensagem do domínio. Uma falha inesperada de programação deve ser investigada e não transformada em “item não encontrado” apenas para continuar o menu. Esse tipo de captura genérica dificulta saber se o programa preservou seu estado.

Não use o texto da mensagem como único contrato entre as classes. O domínio pode devolver um booleano ou um tipo de resultado, e a interface escolhe uma mensagem para o usuário. Testes da regra verificam o valor e o estado; testes da interface verificam o que foi apresentado e como o fluxo segue. Essa separação permite melhorar a escrita da interface sem quebrar todo teste de cálculo.

7. Testes pequenos, independentes e repetíveis

Prepare um estado conhecido, execute uma operação e confira o resultado. Cada teste deve poder começar com um estoque novo, sem depender de uma operação executada por outro teste. Se o cenário envolve uma sequência, essa sequência deve estar explícita dentro dele. Um teste que só passa depois de outro pode esconder estado global compartilhado ou preparação incompleta.

Verifique exemplos aceitos e recusados. Para a retirada, teste quantidade menor que o saldo, igual ao saldo e maior que o saldo. Para o recebimento, teste saldo inicial vazio, acumulação e overflow. Verifique ainda argumento nulo, identificador em branco e quantidade não positiva. Um teste não precisa experimentar todos os números possíveis; ele deve representar classes de comportamento e os limites que mudam a decisão.

Uma mensagem de teste precisa permitir localizar a regra que falhou. Se todos os casos lançam apenas “erro”, a investigação vira outra busca. Nomeie a expectativa, como “recusa preserva saldo” ou “fotografia não acompanha alteração posterior”. Essas frases também ajudam a revisar se o teste está observando o resultado desejado ou apenas repetindo uma linha da implementação.

8. Verificações que não dependem de -ea

A palavra-chave Java assert pode estar desativada na execução. Não coloque uma operação necessária ao teste apenas dentro dela, porque essa operação pode nem ser avaliada sem a opção correspondente. Para este projeto sem bibliotecas externas, uma função explícita lança AssertionError quando a condição não é satisfeita. O resultado do teste passa a independer dessa opção do lançador.

O pequeno programa abaixo verifica uma função de recebimento antes de levá-la para um domínio maior. Os dois primeiros casos observam resultados aceitos; os outros dois conferem as recusas. Se uma exceção esperada não ocorrer, a variável de verificação continua falsa e o teste falha. Capture apenas a exceção que comprova o comportamento esperado, evitando tratar qualquer falha como uma aprovação do cenário.

public class Main {
    static int acrescentar(int atual, int quantidade) {
        if (atual < 0 || quantidade <= 0) throw new IllegalArgumentException("Dados inválidos");
        return Math.addExact(atual, quantidade);
    }
    static void conferir(boolean condicao, String nome) {
        if (!condicao) throw new AssertionError(nome);
    }
    public static void main(String[] args) {
        conferir(acrescentar(0, 3) == 3, "Entrada inicial");
        conferir(acrescentar(3, 2) == 5, "Acumulação");
        boolean recusouZero = false;
        try { acrescentar(3, 0); }
        catch (IllegalArgumentException esperado) { recusouZero = true; }
        conferir(recusouZero, "Recusar zero");
        boolean recusouNegativo = false;
        try { acrescentar(-1, 2); }
        catch (IllegalArgumentException esperado) { recusouNegativo = true; }
        conferir(recusouNegativo, "Recusar estado negativo");
        System.out.println("4 cenários verificados");
    }
}

9. Testar a fotografia e o encapsulamento

Um teste de fotografia deve guardar o resultado de consulta, alterar legitimamente o estoque e comparar o resultado guardado com o esperado anterior. Se a fotografia mudou junto, o getter devolveu uma visão compartilhada ou um objeto interno mutável, em desacordo com esse contrato. Não basta conferir que o mapa devolvido possui os dados corretos no momento da criação.

Faça também uma tentativa de modificar o mapa devolvido e verifique a recusa prevista. Em seguida consulte o estoque de novo para confirmar que nada foi alterado. O teste de encapsulamento observa uma fronteira pública da API, e não o nome privado do campo. Se a implementação mudar de mapa para outra estrutura, esse teste ainda deve representar uma necessidade válida do chamador.

Crie dois estoques e receba material em apenas um. A consulta do outro deve continuar vazia. Esse teste detecta compartilhamento acidental de estado, como um mapa estático. Se você usar um repositório compartilhado intencionalmente em outra versão, atualize o contrato e o teste: independência por instância e compartilhamento global são decisões diferentes e não devem ser confundidas.

11. Introduzir persistência sem trocar a regra central

Depois de verificar a versão em memória, defina como representar os dados e quando confirmá-los no armazenamento. Uma interface de repositório pode separar o contrato de consulta e gravação das decisões de arquivo ou banco. A troca de implementação deve preservar o significado das operações. Se o repositório de arquivo aceita matrículas duplicadas que o de memória recusa, a abstração não preservou a mesma regra.

Não acrescente uma gravação depois de cada linha de menu sem considerar falhas. Se a regra mudou em memória e a persistência falhou, o programa precisa saber qual estado considera confirmado e o que deve informar ao usuário. Uma transação de banco pode reunir alterações do armazenamento; um arquivo requer outra estratégia. O tema 12 e a seção Persistência, SQL e transações ajudam a escolher a fronteira de confirmação.

Teste a integração com um diretório ou banco exclusivo de teste. Um teste de domínio não precisa de disco para verificar uma retirada; um teste de persistência precisa conferir que o dado gravado é lido corretamente por outra instância da operação. Manter os dois tipos de teste separados ajuda a localizar uma falha de formato sem suspeitar da aritmética que já foi verificada isoladamente.

12. Evoluir a interface para uma API

Uma API HTTP pode substituir o menu como ponto de entrada. Ela precisa converter a solicitação para os tipos do domínio, chamar a operação e traduzir o resultado em uma resposta. A regra não deve depender de qual tela ou cliente enviou o pedido. Uma quantidade inválida continua inválida quando chega por JSON, formulário ou linha de comando. Esse é um motivo para manter a validação essencial na operação de domínio.

A passagem para um servidor também muda o padrão de acesso. Solicitações podem chegar ao mesmo tempo, exigindo reavaliar a coordenação do estado compartilhado. Expor pela rede a classe sequencial deste tema não a transforma automaticamente numa implementação concorrente correta. Antes de aceitar várias retiradas simultâneas, defina a fronteira de proteção ou use garantias transacionais do armazenamento. A seção APIs HTTP e contratos aprofunda esse passo.

Uma nova interface exige testes próprios de transporte: comando ou rota inexistente, corpo inválido, status de resposta e limite de tamanho. Preserve os testes do domínio e acrescente essas verificações, em vez de substituir tudo por um teste que apenas confere se o servidor iniciou. Iniciar um processo prova uma condição diferente de cumprir a regra de estoque.

2. Pacote, módulo e artefato têm responsabilidades diferentes

Um pacote organiza nomes e participa do controle de acesso da linguagem. Um módulo nomeado, introduzido pelo sistema de módulos da plataforma, declara dependências e quais pacotes exporta. Um artefato de build é uma unidade publicada ou produzida, como um arquivo JAR identificado por coordenadas Maven. Um projeto pode conter muitos pacotes, produzir um artefato e ainda executar sem um módulo nomeado.

O arquivo module-info.java fica na raiz dos fontes de um módulo. A diretiva requires declara leitura de outro módulo; exports disponibiliza um pacote para uso por outros módulos. Exportar não torna membros privados públicos. Acesso continua sujeito à visibilidade das classes e dos membros. Também não equivale a liberar reflexão sobre todos os detalhes internos. Bibliotecas que precisam de reflexão profunda podem exigir opens, de preferência restrito ao módulo que realmente precisa dela.

Evite acrescentar module-info.java ao primeiro projeto Spring apenas para torná-lo mais organizado. Bibliotecas e plugins possuem requisitos de resolução e reflexão próprios. Primeiro faça o build funcionar, entenda como as dependências entram e decida se a fronteira de módulos resolve uma necessidade do projeto. Consulte a especificação de pacotes e módulos quando precisar conferir as regras de leitura e exportação.

A saída esperada é Módulo pronto. Se a classe não for localizada, confira a pasta a partir da qual executou o comando, a declaração de pacote e o nome qualificado depois da barra. 5. Maven e Gradle no trabalho cotidiano

Maven organiza um ciclo de vida com etapas como compile, test e package. O pom.xml declara a identidade do projeto, as dependências e a configuração dos plugins. Gradle descreve tarefas e relações num build próprio. Um projeto deve indicar qual ferramenta usa e sua versão adequada. Aprender os dois ao mesmo tempo não é requisito para acompanhar o laboratório Spring, que usa Maven.

Uma dependência pode trazer outras dependências transitivas. É por isso que adicionar um starter fornece várias bibliotecas sem listar cada uma manualmente. O gerenciamento de versões coordena esse conjunto. Alterar individualmente uma biblioteca gerida pelo framework pode criar incompatibilidades que só aparecem na inicialização. Inspecione a árvore com mvn dependency:tree e leia a recomendação da linha utilizada antes de sobrescrever versões.

O escopo também importa. Uma biblioteca necessária apenas em teste deve ficar no escopo test. Uma implementação de banco pode entrar em runtime quando o código compila usando APIs mais gerais. O artefato que você entrega deve carregar o necessário para executar, com licenças e configuração apropriadas. A pasta de cache local do desenvolvedor não deve ser a única explicação de por que um programa funciona.

6. Recursos, codificação e caminhos portáveis

Um arquivo dentro do JAR é um recurso da aplicação. Um documento criado pelo usuário é um dado externo. Para um modelo de relatório empacotado, use getResourceAsStream com caminho conhecido e trate retorno nulo. Para uma exportação escolhida pelo usuário, receba um Path externo e verifique permissões e falhas. Um recurso dentro do JAR não oferece necessariamente um caminho gravável no sistema de arquivos.

Um campo com espaços deixa de ser vazio para essa expressão, e o domínio ainda deve recusá-lo. A condição visual orienta a interação, enquanto a validação mantém o contrato completo. Não apresente o botão habilitado como garantia de que todos os campos estão corretos.

Bindings unidirecionais e bidirecionais têm usos diferentes. No primeiro caso, uma propriedade deriva de outra expressão; no segundo, alterações podem propagar nos dois sentidos. Ao conectar dois campos com conversão numérica, pense no estado temporário da digitação: um sinal de menos ou uma vírgula ainda pode fazer parte de uma edição incompleta. Evite converter cada tecla em uma gravação definitiva.

conferir.disableProperty().bind(nota.textProperty().isEmpty());
conferir.setDefaultButton(true);
rotulo.setLabelFor(nota);

18 · Desktop avançado: tarefas, estado e acessibilidade

1. A tela possui estado e tempo de resposta

Um formulário deixa de ser simples quando precisa carregar dados, manter seleção, mostrar erro e continuar respondendo enquanto uma tarefa está em andamento. Antes de acrescentar botões, descreva os estados observáveis: vazio, editando, carregando, pronto e falha. Cada estado determina ações disponíveis e a informação que precisa aparecer.

No cadastro de notas, uma consulta ao histórico pode falhar depois de o usuário editar o nome. Limpar todos os campos nessa situação apaga trabalho válido. Mantenha o rascunho e apresente a falha da consulta na área correspondente. Uma mensagem deve dizer qual operação falhou e o que o usuário pode tentar, sem sugerir que um dado foi salvo quando a confirmação não chegou.

Este tema aprofunda o modelo das telas Swing e JavaFX. Use os dois projetos disponíveis como base local. As tarefas de fundo discutidas aqui são uma evolução orientada, sem ligação automática com um servidor público. Você pode simular dados e atrasos no próprio processo antes de introduzir rede e autenticação.

2. Separar domínio, apresentação e adaptadores

O domínio contém as regras de notas ou estoque. Um modelo de apresentação mantém os dados que a tela precisa exibir, como rascunho, mensagem e indicador de carregamento. A view conhece controles e layout. Um adaptador consulta arquivo ou API. Essa divisão permite testar uma decisão de apresentação sem precisar localizar um botão em uma janela aberta.

O padrão MVC organiza relações entre modelo, visualização e controle; há variações conforme o kit gráfico e a aplicação. Em JavaFX, propriedades observáveis favorecem modelos de apresentação ligados à tela. Em Swing, um TableModel separa os dados e a notificação da JTable. Escolha nomes que indiquem responsabilidade concreta e evite criar uma classe de serviço que apenas encaminhe todas as chamadas sem acrescentar regra ou fronteira.

Uma tela deve receber suas dependências de modo explícito. Um construtor que recebe ConsultaHistorico facilita usar uma implementação em memória no teste e uma implementação HTTP depois. O teste pode fornecer uma resposta controlada ou uma falha. A interface Java do contrato pertence à camada que precisa da capacidade; o adaptador fornece a implementação.

3. SwingWorker e a devolução para a EDT

SwingWorker divide trabalho de fundo e atualização visual. doInBackground executa o processamento fora da EDT. done é chamado na EDT quando a tarefa termina. publish e process permitem comunicar resultados intermediários sem fazer a thread de fundo tocar diretamente nos componentes. Cada instância representa uma execução; crie outra para uma nova consulta.

O esqueleto abaixo usa a mesma lógica de validação como demonstração. Num aplicativo real, o trabalho de fundo faria uma consulta demorada. Ele deve capturar antes os dados necessários, sem ler controles em doInBackground. O listener da ação desabilita o botão enquanto a tarefa está em andamento e o reabilita no encerramento. O código pertence ao contexto de uma tela que já declarou conferir, resultado e nota.

String entrada = nota.getText();
conferir.setEnabled(false);
new SwingWorker<String, Void>() {
    protected String doInBackground() { return Nota.avaliar(entrada); }
    protected void done() {
        try { resultado.setText(get()); }
        catch (java.util.concurrent.CancellationException e) { resultado.setText("Consulta cancelada"); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); resultado.setText("Consulta interrompida"); }
        catch (java.util.concurrent.ExecutionException e) { resultado.setText("Não foi possível concluir a consulta"); }
        finally { conferir.setEnabled(true); }
    }
}.execute();

4. Task, Service e cancelamento no JavaFX

Task representa uma computação observável. Seu método call faz o trabalho de fundo; handlers de sucesso, falha e cancelamento permitem atualizar a interface na thread gráfica. Um Service pode criar tarefas para execuções repetidas, respeitando seu ciclo de vida. O programa ainda precisa escolher um executor, limitar a quantidade de trabalhos e encerrá-lo quando não for mais necessário.

Cancelar uma tarefa é uma solicitação cooperativa. Um laço deve conferir o estado de cancelamento e operações bloqueantes precisam de timeouts ou mecanismos próprios. Exibir Cancelado na tela não prova que uma gravação remota foi desfeita. Quando uma requisição já pode ter sido efetivada, apresente a incerteza e ofereça consulta do estado. A política de repetição precisa conhecer a operação.

Ao iniciar uma consulta, preserve um identificador crescente da solicitação. Se a busca por Ana demora mais que a busca posterior por Bruno, a resposta antiga pode chegar por último. Antes de aplicar o resultado, confira se ele ainda corresponde à consulta atual. Cancelamento ajuda a economizar trabalho, mas a verificação de relevância protege a tela quando o trabalho antigo já terminou.

5. Tabelas, seleção e edição consistente

Uma tabela apresenta uma projeção dos dados. O índice visual de uma linha pode mudar quando há ordenação ou filtro. Use um identificador estável para localizar o registro correspondente e, no Swing, converta o índice da view para o modelo quando o mecanismo exigir. Remover pelo índice errado pode atingir outra pessoa depois de uma ordenação.

Ao editar, mantenha separado o valor em digitação do valor confirmado. O usuário pode cancelar ou receber uma recusa do servidor. Atualize a linha definitiva quando a operação for confirmada ou quando uma política de atualização otimista conseguir reconciliar a falha. Para começar, aguarde a confirmação e preserve o rascunho em caso de erro.

Notifique a tabela quando o modelo mudar. Alterar uma lista interna sem o evento correspondente pode deixar a visualização antiga. No JavaFX, uma ObservableList informa mudanças estruturais, enquanto alterações dentro de cada item dependem das propriedades observadas pelas células. Um teste deve verificar inclusão, atualização, exclusão e seleção depois de ordenar.

6. Acessibilidade e internacionalização

Cada campo precisa de um nome compreensível e uma relação com seu rótulo. O foco deve percorrer os controles numa ordem previsível. Erros precisam de texto e contexto. Um ícone vermelho sem descrição deixa a pessoa sem saber qual campo corrigir. Confira a interação por teclado e, quando disponível, com o leitor de tela da plataforma.

Use ResourceBundle para separar textos quando houver tradução. Datas e números devem seguir o formato anunciado para o usuário. Texto traduzido pode ocupar mais espaço; layouts precisam suportar essa diferença. O identificador de um registro continua estável mesmo quando sua legenda muda de idioma. Evite usar o texto apresentado como chave de negócio.

Um teste com fonte ampliada deve incluir mensagens de erro e diálogos. A tela inicial legível não garante que a confirmação final seja legível. A aparência oferecida pelo sistema pode mudar contraste, métricas e tamanhos. Registre as combinações de plataforma, escala e tecnologia assistiva que você realmente conferiu.

7. Prática: consulta com atraso e resultado antigo

Adapte uma das telas para consultar uma lista em memória por nome. Simule dois tempos de resposta no adaptador, fora da thread gráfica. Faça a primeira consulta demorar mais e inicie a segunda logo depois. A resposta apresentada deve corresponder à segunda entrada, independentemente da ordem em que as tarefas terminarem.

19 · Java multiplataforma e distribuição de aplicações

1. O que significa executar em várias plataformas

Uma aplicação Java de desktop pode executar sobre uma JVM compatível em sistemas diferentes. Para isso, o bytecode precisa ser aceito pelo runtime e todas as dependências utilizadas precisam existir no destino. Quando há bibliotecas nativas, componentes gráficos ou integração com o sistema, entram também diferenças de arquitetura e empacotamento. A portabilidade deve ser conferida nos ambientes que você pretende atender.

Java no Android segue outro caminho de build e execução. O código usa APIs do Android, passa pelas ferramentas dessa plataforma e chega ao runtime ART em formato adequado. Swing e JavaFX do desktop não se tornam telas Android ao copiar o JAR. Uma regra de cálculo pode ser reaproveitada se estiver restrita a APIs compatíveis; janela, permissões, ciclo de vida e instalação precisam de adaptadores próprios.

Defina uma matriz de suporte antes de distribuir: sistema, arquitetura, versão mínima de runtime e recursos exigidos. Para uma aplicação Swing de notas, a primeira matriz pode conter Windows x64 e Linux x64 com ambiente gráfico e JDK 17. Uma plataforma ainda não testada deve aparecer como pendente. Isso dá ao usuário uma informação verificável sobre onde o pacote foi conferido.

2. Escolher a versão de compilação e as APIs

A opção --release 17 do javac seleciona a versão de linguagem, o formato de classe e as APIs públicas correspondentes ao Java 17. Compilar apenas com um nível de sintaxe antigo, mantendo acesso livre à biblioteca de um JDK mais novo, pode produzir um programa que chama uma API ausente no runtime alvo. O build deve declarar a intenção de compatibilidade de forma consistente.

Dependências externas possuem requisitos próprios. Um JAR que você utiliza pode ter sido compilado para um Java posterior. A JVM pode recusar essa classe mesmo que seus fontes tenham sido compilados com --release 17. Inspecione as versões e execute o artefato com o runtime mínimo declarado. A IDE usando um JDK novo pode esconder essa diferença durante o desenvolvimento.

O laboratório JavaFX fixa uma versão compatível com seu JDK e resolve bibliotecas específicas do sistema pelo Maven. Para um pacote destinado a outra plataforma, produza o conjunto correspondente e confira o resultado nessa plataforma. Misturar bibliotecas nativas x64 e arm64 não é resolvido pelo bytecode portável da aplicação.

3. Produzir um JAR executável

Um JAR reúne classes e recursos. O manifesto pode declarar a classe principal para a execução com java -jar. O comando abaixo pressupõe que você compilou o laboratório Swing para out, como descrito no tema 16. A pasta dist é criada manualmente antes do empacotamento. O programa continua precisando de um runtime Java compatível no computador de destino.

jar --create --file dist/notas.jar --main-class br.estudo.Main -C out .
java -jar dist/notas.jar

4. Dependências e imagem de execução

Um JAR simples não incorpora automaticamente todos os JARs de que seu projeto depende. Bibliotecas podem ser distribuídas numa pasta lib com classpath documentado ou reunidas por uma ferramenta que trate os recursos e metadados adequadamente. O Spring Boot possui seu próprio empacotamento executável. O modo correto depende da estrutura do projeto e do carregador utilizado.

jlink cria uma imagem de runtime a partir de módulos. Ela contém o necessário para a configuração declarada, com redução de componentes em relação a um JDK completo. O exemplo abaixo prepara um runtime com java.desktop para o laboratório Swing. Ele é produzido para o sistema e a arquitetura das ferramentas utilizadas. A imagem não substitui a verificação de bibliotecas externas e recursos carregados dinamicamente.

Use o manual de jlink para conferir opções e limitações. Um aplicativo não modular pode ser distribuído com um runtime preparado a partir dos módulos da plataforma, enquanto sua aplicação permanece no classpath. A escolha precisa ser documentada para que o comando de lançamento encontre tanto o runtime quanto o JAR.

jlink --add-modules java.desktop --output runtime-notas
runtime-notas/bin/java -jar dist/notas.jar

5. jpackage e instaladores próprios de cada destino

jpackage produz uma imagem de aplicação e, quando o ambiente oferece as ferramentas necessárias, pacotes de instalação nativos. Uma imagem inclui um lançador e pode incluir o runtime. O usuário passa a executar o aplicativo pelo lançador, sem configurar manualmente um JDK. Consulte a visão geral de empacotamento para os formatos e requisitos por sistema.

Produza o pacote em cada sistema alvo com ferramentas compatíveis. Um instalador Windows não serve como pacote de instalação macOS. Assinatura, permissões, nome do aplicativo e diretório de instalação também merecem uma decisão explícita. Para começar, gere uma app-image e teste o lançador numa conta que não dependa do ambiente da IDE.

No comando abaixo, dist contém somente os arquivos que devem acompanhar o aplicativo. Evite incluir capturas, arquivos temporários ou credenciais nessa pasta. A imagem de runtime criada no passo anterior é fornecida explicitamente. O comando é um exemplo para o laboratório Swing; JavaFX e Spring possuem requisitos adicionais que precisam ser tratados nos seus builds.

jpackage --type app-image --name NotasEstudo --input dist --main-jar notas.jar --main-class br.estudo.Main --runtime-image runtime-notas --dest pacote

6. Sistema de arquivos, recursos e preferências

O diretório de instalação pode ser protegido contra escrita. Salve dados do usuário numa localização apropriada e escolhida de forma documentada, como uma pasta selecionada no diálogo de exportação. Não presuma que o diretório corrente do processo é a pasta do JAR. Atalhos e lançadores podem iniciar o programa com outro diretório corrente.

Nomes de arquivo, separadores, sensibilidade a maiúsculas e regras de permissão variam. Teste um arquivo com acentos e uma pasta com espaços. Feche streams antes de substituir arquivos e trate operações não suportadas. Uma gravação atômica do laboratório de arquivos precisa continuar falhando de forma explícita se o sistema não conseguir oferecer a garantia exigida.

Preferências pequenas, como tamanho da janela, podem ter um armazenamento específico. Elas não devem substituir um documento de trabalho sem que o usuário saiba onde o dado fica e como recuperá-lo. Ao atualizar o aplicativo, preserve dados e explique eventuais migrações. Uma nova versão que reinicia preferências não deve apagar o histórico de negócio.

7. GraalVM Native Image e o custo de mudar o runtime

Native Image produz um executável para um alvo, usando análise e compilação antecipada. Isso muda inicialização, distribuição e algumas exigências sobre reflexão, carregamento de classes e recursos. Uma aplicação que executa sobre a JVM pode precisar de metadados e ajustes para uma imagem nativa. Consulte a documentação oficial de Native Image para o ambiente escolhido.

Compare tempo de inicialização, memória, tamanho do pacote e comportamento sob a carga que você realmente utiliza. Não prometa que a compilação nativa tornará qualquer programa mais rápido. O custo de build e as restrições também entram na escolha. Frameworks oferecem integração específica, que deve ser usada conforme a versão documentada.

Para o estudo inicial, o JAR com runtime ou a app-image são suficientes para compreender a entrega. Deixe a imagem nativa como um experimento com hipótese: por exemplo, reduzir a latência de inicialização de uma ferramenta curta. Registre como mediu e quais testes foram repetidos no artefato final.

8. Prática: entregar uma aplicação fora da IDE

Empacote o laboratório Swing como JAR e depois como app-image. Execute o teste de domínio com o runtime mínimo declarado e abra a imagem num ambiente gráfico. Confira um nome de pasta com espaços, entrada com vírgula e o fechamento. O pacote deve incluir um texto curto com versão, requisitos, comando ou lançador e limitações.

Como revisão, explique por que um JAR, uma imagem de runtime e um APK Android possuem funções diferentes no processo de distribuição.

Não. jpackage atende a distribuição desktop da plataforma em que o pacote é produzido. Android usa seu próprio projeto, SDK, formato de pacote e mecanismos de instalação.

5. O ciclo de vida da Activity

A Activity passa por estados de criação, início, retomada, pausa, parada e destruição conforme a interação com o sistema. onCreate prepara a instância; onStart e onResume acompanham sua entrada em primeiro plano. onPause e onStop ajudam a suspender recursos associados à visibilidade. onDestroy pode ocorrer numa recriação, mas não deve ser tratado como uma garantia de salvamento de todos os dados antes de o processo desaparecer.

Uma mudança de configuração pode destruir a instância e criar outra. Se você guardar o resultado apenas num campo da Activity, a nova instância começa sem esse valor. O laboratório salva o texto do resultado em onSaveInstanceState e o recupera quando recebe um Bundle. O campo de entrada tem id e usa os mecanismos da hierarquia de Views para seu estado de edição.

Bundle é apropriado para estado pequeno necessário à reconstrução da interface. Ele não substitui armazenamento persistente de registros nem deve carregar grandes coleções de objetos. O guia do ciclo de vida descreve as transições. Diferencie recriação da tela, morte do processo e remoção definitiva do aplicativo ao planejar o que precisa sobreviver.

21 · Android avançado: arquitetura, dados e trabalho em segundo plano

1. Organizar uma aplicação que pode ser interrompida

Depois da primeira Activity, o próximo problema é manter regras e dados coerentes enquanto telas são recriadas, consultas falham e o processo pode desaparecer. Uma aplicação de notas precisa distinguir rascunho, registro salvo e resultado de consulta. A indicação Salvo deve corresponder a uma operação persistente confirmada, com uma política definida para sincronização quando existir servidor.

Uma organização comum separa a UI, um ViewModel que apresenta o estado e um repositório que coordena as fontes de dados. O domínio continua contendo regras que podem ser testadas sem Activity. Essa estrutura permite representar carregamento, lista vazia, conteúdo e falha como estados explícitos. O projeto inicial do tema 20 é a base local; as evoluções deste capítulo exigem acrescentar as bibliotecas indicadas nas referências de cada etapa.

Faça uma alteração por vez. Primeiro extraia a regra, depois modele o estado da tela, depois persista localmente e só então acrescente rede. Se introduzir banco, servidor e trabalho de fundo ao mesmo tempo, será difícil descobrir qual camada causou uma perda de estado ou uma duplicação.

2. ViewModel, estado salvo e tempo de vida

Um ViewModel mantém dados de apresentação associados a um proprietário de ciclo de vida e pode sobreviver a mudanças de configuração. Ele não mantém automaticamente seus valores após a morte do processo. Use um mecanismo de estado salvo para informações pequenas de reconstrução e armazenamento persistente para registros que precisam sobreviver ao encerramento.

Evite guardar Activity ou View num ViewModel de vida mais longa, pois isso pode reter uma instância descartada. Entregue dados ao estado de apresentação e deixe a tela observá-los conforme seu ciclo. Uma referência ao contexto também exige critério: use apenas o tipo de dependência necessário e conheça o tempo de vida dele. Consulte o guia oficial de ViewModel para os proprietários e mecanismos disponíveis.

Um estado de tela pode incluir entrada, itens, carregando e mensagem. Se campos independentes permitirem combinações impossíveis, agrupe-os em uma representação que preserve a regra: por exemplo, um resultado de consulta com estados explícitos. O teste deve verificar a transição de carregando para falha e a manutenção do rascunho, além do caminho de sucesso.

3. Repositório e fonte de verdade

O repositório oferece operações que a aplicação precisa, como observar notas e registrar uma alteração. Ele pode consultar um banco local e uma API. Defina qual fonte decide o dado apresentado em cada momento. Uma estratégia que lê sempre do banco local e atualiza esse banco após sincronizar dá à tela uma origem estável, mas ainda precisa representar alterações pendentes e conflitos.

DTOs de rede, entidades de banco e objetos de tela têm contratos diferentes. O DTO representa o formato da API; a entidade representa o armazenamento local; o modelo de apresentação representa o que a pessoa vê. Mapeamentos explícitos evitam que uma mudança de coluna ou campo remoto quebre diretamente o formulário. Uma única classe pode bastar num protótipo, desde que você reconheça os contratos que ela está acumulando.

Inclua resultados de falha na operação. Uma lista vazia significa que a consulta terminou sem registros; uma falha de conexão significa que o resultado pode ser desconhecido ou desatualizado. Mostrar a mesma mensagem para as duas situações leva o usuário a decisões erradas, como cadastrar novamente algo que já existe.

4. Room: entidade, DAO e banco

Room organiza persistência local sobre SQLite com entidades, interfaces de acesso e uma classe de banco. No projeto Java, o processamento de anotações precisa ser configurado conforme a versão escolhida; não copie uma configuração exclusiva de Kotlin sem adaptá-la. Use o guia oficial de Room para as dependências Java, runtime e annotationProcessor correspondentes.

Uma entidade define colunas, chave e restrições. O DAO declara consultas e operações. O banco registra as entidades e a versão do esquema. Consultas observáveis podem alimentar o estado da UI, enquanto escritas devem ocorrer fora da thread principal. Uma chamada de banco pequena hoje pode crescer quando o usuário acumular meses de dados.

Escreva uma migração quando o esquema mudar e preserve os registros existentes. Apagar o banco como solução automática para qualquer mudança pode destruir dados do usuário. Um teste de migração deve criar o esquema anterior, inserir exemplos, migrar e conferir o novo formato e os valores. Diferencie dados descartáveis de cache dos registros que o usuário considera permanentes.

5. Rede, segurança de transporte e emulador

O adaptador HTTP deve ter endereço configurável, timeout e política de erro. Android exige permissões e políticas de rede próprias. Use HTTPS para dados reais e mantenha exceções de desenvolvimento restritas ao ambiente necessário. Não transforme uma dificuldade de certificado local numa permissão ampla de tráfego inseguro para a versão distribuída.

O endereço 127.0.0.1 no aparelho aponta para o próprio aparelho. O emulador padrão do Android possui um endereço especial para alcançar o host de desenvolvimento, descrito na documentação de rede do emulador. Um servidor limitado a loopback pode exigir um túnel ou encaminhamento específico para o teste. Não altere o laboratório Spring para exposição pública apenas para contornar essa etapa.

Uma resposta HTTP precisa ser interpretada pelo status e pelo corpo esperado. Erro de autenticação, conflito de versão e timeout pedem ações diferentes. Preserve o rascunho e evite repetir automaticamente uma criação sem saber se ela já aconteceu. O servidor e o cliente precisam compartilhar uma estratégia de identificação da operação para resolver essa incerteza.

6. Trabalho persistente e WorkManager

Uma tarefa que deve continuar de forma confiável após sair da tela pode exigir WorkManager. Ele oferece agendamento persistente com restrições e política de repetição. Seu uso não promete executar imediatamente em um instante exato. A decisão depende do tipo de trabalho, das limitações do sistema e da urgência percebida pelo usuário.

Para sincronizar notas, registre a alteração pendente antes de agendar. O trabalho consulta pendências, envia operações com identificadores estáveis e marca o resultado confirmado. Se o processo cair entre envio e confirmação local, a repetição precisa ser tolerada pelo contrato remoto. O processamento deve ser idempotente ou possuir uma política explícita contra duplicação.

Consulte a documentação de trabalho persistente para as restrições e os testes. Um carregamento curto ligado à tela pode usar outro mecanismo. O fato de uma operação ocorrer fora da thread principal não implica que ela continuará existindo depois que o processo for encerrado.

7. Conflitos, sincronização e recuperação

Considere dois aparelhos editando a mesma nota. Um carrega a versão 2, outro salva a versão 3 e o primeiro tenta enviar sua edição. O servidor pode recusar a versão antiga e devolver um conflito. O cliente deve preservar o rascunho e permitir comparar com o valor atual. Sobrescrever silenciosamente elimina trabalho de outra pessoa.

Uma política de último valor recebido é simples, mas precisa ser uma decisão assumida para aquele dado. Para quantidades de estoque e operações financeiras, uma edição genérica pode violar invariantes. Modele comandos como retirar uma quantidade e valide o estado no servidor. O aplicativo móvel pode antecipar uma mensagem, mas não decide sozinho o saldo compartilhado.

Registre erros sem copiar senhas, tokens ou dados pessoais completos. Uma falha de sincronização deve informar o que permanece pendente e quando tentar novamente. A saída da conta precisa esclarecer o destino de rascunhos e dados locais. Uma limpeza indiscriminada pode apagar uma alteração que ainda não chegou ao servidor.

23 · Spring Boot e APIs REST: contratos, validação e erros

1. Uma API precisa de um contrato observável

Uma API HTTP descreve recursos, operações, formatos e respostas que outro programa consegue interpretar. No catálogo, produtos possuem identificador, código, quantidade e versão. O cliente pode listar, consultar, criar e solicitar retirada. Cada operação precisa dizer quais campos recebe, quais regras podem recusá-la e como o cliente identifica o resultado.

O controller transforma o protocolo em chamada de aplicação. A regra não deve depender de HttpServletRequest nem de um componente gráfico. Um DTO de entrada representa o contrato recebido e limita os campos aceitos pela operação. Um DTO de saída escolhe o que será apresentado. Isso evita expor automaticamente toda a entidade de persistência, inclusive relações e atributos internos.

Os exemplos usam JSON e a pilha Spring MVC servlet do laboratório. O servidor real executa localmente, fora do Playground. O projeto completo do tema 22 contém Contratos.java, ProdutoController.java e Erros.java. Ao copiar um trecho isolado, mantenha os imports e os colaboradores correspondentes do pacote para que o exemplo tenha o mesmo comportamento.

2. Rotas, métodos e status

GET /api/produtos lista uma página e GET /api/produtos/{id} consulta um produto. POST /api/produtos cria um registro e devolve 201 com Location apontando para o recurso. POST /api/produtos/{id}/retiradas expressa um comando que altera a quantidade e devolve o estado confirmado. A escolha deixa visível a operação de negócio.

GET deve ser usado para consulta, sem depender de uma alteração de negócio para cumprir sua finalidade. Um formulário que retira estoque ao abrir um link pode sofrer acionamentos inesperados por navegação ou ferramentas. Métodos e status precisam acompanhar a intenção da operação. Uma resposta 200 com um corpo que diz erro obriga o cliente a adivinhar um contrato paralelo.

No laboratório, 400 corresponde a entrada inválida, 404 a produto ausente e 409 a conflito com o estado atual. A segurança pode produzir 401 ou 403 antes de o controller executar. O cliente deve distinguir essas situações de uma falha de conexão, na qual pode não ter recebido resposta alguma.

3. DTOs com validação de entrada

Contratos.Criar exige código não vazio com letras maiúsculas, dígitos, sublinhado ou hífen, de 1 a 30 caracteres, e quantidade inteira não negativa. Contratos.Retirar exige quantidade positiva e uma versão não negativa. Os wrappers Integer e Long permitem distinguir ausência do campo de um valor numérico zero.

@Valid na entrada do controller solicita a validação do objeto convertido. Anotações como @NotNull e @Positive representam restrições desse contrato. A validação de faixa na entidade ou no serviço mantém a regra mesmo para chamadas que venham de outro adaptador. A documentação de validação em controllers explica os caminhos e exceções conforme a assinatura.

Não aceite id ou versao gerados pelo servidor na operação de criação apenas porque existem na entidade. Um DTO específico permite revisar o que o cliente realmente controla. Para edição, descreva quais campos podem mudar e quais identificam o estado observado. Validação sintática e autorização continuam sendo verificações diferentes.

Um JSON malformado pode falhar antes da validação de campos. Um parâmetro textual onde se espera um long pode falhar na conversão da rota. A resposta deve continuar legível para o cliente e preservar o status adequado. Não devolva uma página de stack trace como contrato de API.

Defina limites de tamanho e quantidade nos pontos de entrada. O laboratório limita a página a 100 itens e aceita apenas a ordenação fixa por id. 24 · Spring Data JPA: persistência, transações e concorrência

1. Guardar dados preservando as regras

JPA define uma forma de mapear objetos e operações de persistência; Hibernate é a implementação utilizada pelo conjunto padrão do laboratório. Spring Data JPA organiza repositórios sobre essa integração. Uma entidade participa de um contexto de persistência e tem identidade própria. Ela não é apenas um DTO com uma anotação.

Produto possui id gerado, código único, quantidade e versão. O construtor de negócio valida código e quantidade. Um construtor protegido sem argumentos atende à criação pela infraestrutura. A entidade não oferece setters genéricos que permitam qualquer alteração; a retirada passa por uma operação que confere a quantidade e o estado observado.

O H2 em memória permite estudar sem instalar um servidor de banco. Ele não demonstra automaticamente o comportamento de PostgreSQL, MySQL ou outro destino. Dialeto, isolamento, tipos e bloqueios podem variar. Ao escolher um banco permanente, execute os testes de integração nesse banco e defina migrações e cópias de segurança.

2. Entidade, identidade e restrição no banco

@Id identifica a chave e @GeneratedValue define sua geração conforme a estratégia. @Column marca obrigatoriedade e tamanho no mapeamento. A restrição única de código protege o banco contra cadastros duplicados inclusive quando duas requisições competem. Uma consulta prévia pode ajudar a apresentar a intenção, mas não substitui a restrição transacional.

O id gerado pode não existir antes da persistência. Isso exige cuidado com equals e hashCode de entidades colocadas em conjuntos. Retome os contratos do tema 11 e escolha uma estratégia de identidade que permaneça consistente durante o uso da estrutura. Não gere igualdade automaticamente a partir de todas as relações e campos mutáveis.

Use DTOs para retornar dados. Serializar uma entidade com relações pode disparar consultas, produzir ciclos ou revelar campos fora do contrato. O laboratório desativa open-in-view e transforma a entidade numa resposta dentro da operação do serviço. Assim, a camada web recebe os dados que precisa sem depender de uma sessão de persistência aberta durante a escrita do JSON.

3. Repositórios e consultas

ProdutoRepository estende JpaRepository<Produto, Long> e recebe operações básicas. Consultas derivadas podem expressar buscas simples pelo nome do método. Para consultas maiores, avalie JPQL, projeções ou outro mecanismo apropriado. Parâmetros devem ser vinculados pelo mecanismo de consulta; concatenar texto recebido do cliente cria problemas de segurança e de conversão.

Uma consulta com filtro e paginação precisa de uma ordem conhecida e de índices adequados ao volume. O método listar do laboratório fixa a ordem por id e converte os resultados para DTOs. Conte o número de consultas quando relações forem acrescentadas. Carregar uma lista e, para cada linha, disparar outra busca pode criar o problema conhecido como N+1.

Fetch joins, entity graphs e projeções possuem usos e limites, especialmente com coleções e paginação. Escolha a forma conforme o resultado necessário e verifique o SQL produzido em ambiente de estudo. Mudar uma relação para eager em toda a aplicação pode aumentar a carga de consultas que nem precisavam daquela informação.

4. Fronteira transacional do caso de uso

@Transactional delimita a operação do serviço que precisa consultar e alterar de modo consistente. No laboratório, retirar carrega o produto, confere a versão, aplica a regra e executa flush antes de produzir a resposta. Uma falha que provoque rollback deve preservar a quantidade anterior no banco.

A propagação e as regras de rollback dependem da configuração e do tipo de exceção. Entenda o padrão da versão utilizada e declare outra política quando o caso exigir. No modo habitual baseado em proxy, uma chamada interna ao próprio objeto pode não passar pela interceptação transacional. Organize a fronteira em um método invocado pelo colaborador correto, em vez de presumir que qualquer anotação em qualquer chamada terá efeito.

readOnly expressa uma intenção e pode orientar otimizações; ele não deve ser a única proteção contra alterações indevidas. Consulte a documentação de transações do Spring Data JPA e teste as garantias importantes na tecnologia de banco escolhida.

5. Dirty checking, flush e confirmação

Uma entidade gerenciada pode ter suas alterações detectadas pelo contexto de persistência. flush sincroniza mudanças pendentes com o banco e pode revelar violações de restrição antes do retorno. Isso não equivale, em qualquer contexto, a encerrar a transação. O commit é a etapa que confirma o conjunto conforme a fronteira transacional.

Um método que apenas chamou save pode ainda falhar quando o SQL for enviado ou quando a transação confirmar. Evite comunicar sucesso definitivo por um efeito externo antes de saber o resultado. Enviar uma mensagem para outro sistema dentro da transação exige uma estratégia que trate a falha entre os dois recursos. O tema 28 apresenta o padrão outbox.

No laboratório, a resposta é criada após flush e a infraestrutura conclui a transação antes de a chamada terminar com sucesso. Testes de recusa consultam o estado novamente. Essa consulta reduz o risco de um teste verificar apenas a representação em memória e ignorar o que foi realmente persistido.

6. Concorrência otimista com versão

@Version permite detectar atualizações concorrentes sobre a entidade. O banco e o provedor usam a versão observada para reconhecer que o registro mudou antes da confirmação. A API também recebe a versão que o cliente leu, permitindo recusar uma edição baseada em dados antigos mesmo quando a requisição só chegou depois da alteração anterior.

Imagine dois clientes vendo quantidade 5 e versão 0. O primeiro retira 2 e confirma uma versão nova. O segundo tenta retirar usando a versão 0. A aplicação recusa a versão desatualizada, sem descontar novamente com base naquela observação. Se duas transações carregarem ao mesmo tempo, o mecanismo de versão da persistência protege a disputa na confirmação.

Os testes distribuídos verificam a recusa de uma versão explicitamente antiga e a preservação do saldo. Eles não são uma prova de todas as intercalações de threads em todo banco. Para a versão de produção, acrescente cenários concorrentes no banco alvo e defina se o cliente deve recarregar, repetir uma operação segura ou pedir uma decisão do usuário.

7. Migrações e dados permanentes

create-drop é adequado ao laboratório descartável e elimina dados no encerramento. Em uma aplicação com registros permanentes, use um esquema versionado e uma ferramenta de migração compatível com seu projeto. Cada mudança deve ter uma ordem, um efeito conhecido e uma verificação sobre dados existentes.

Adicionar uma coluna obrigatória a uma tabela preenchida exige uma estratégia de preenchimento. Renomear ou remover um campo pode quebrar uma versão anterior da aplicação durante uma atualização gradual. Planeje fases compatíveis quando houver versões simultâneas. Uma cópia de segurança só ajuda se o processo de restauração for conhecido e testado.

Credenciais e endereço do banco devem vir da configuração do ambiente. A aplicação não precisa de permissões administrativas para toda operação cotidiana. Diferencie o papel que aplica migrações do papel que consulta e altera registros quando a infraestrutura permitir essa separação. Documente o acesso necessário sem incluir senhas reais no pacote.

25 · Spring Security: autenticação, autorização e proteção de APIs

1. Autenticar e autorizar cada operação

Autenticação identifica quem faz a chamada; autorização decide o que essa identidade pode realizar. No catálogo, leituras de produtos são públicas e escritas exigem o papel ADMIN. Uma API maior também precisa decidir quais registros cada usuário pode acessar. Ter um papel de editor não implica poder alterar qualquer registro de qualquer pessoa.

Spring Security aplica filtros antes de muitas chamadas chegarem ao controller. A configuração do laboratório declara as rotas permitidas e termina com denyAll para os demais casos. Isso torna visível o que foi aberto. Uma nova rota precisa de revisão de contrato e acesso, em vez de herdar uma permissão ampla por acidente.

O projeto usa HTTP Basic com uma conta fictícia local para estudar o fluxo. Ele escuta em 127.0.0.1 e não representa uma configuração pública pronta. Basic deve ser protegido por TLS quando transporta credenciais em uma implantação real. Base64 não oferece sigilo. A documentação de Basic descreve o tratamento pelo filtro e a resposta de autenticação.

2. SecurityFilterChain e ordem de regras

Um bean SecurityFilterChain configura o HttpSecurity da aplicação servlet. As regras precisam considerar método e rota. GET de produtos é permitido; POST de produtos e retiradas exige ADMIN; saúde e token CSRF possuem acesso explícito; as demais requisições são recusadas. A ordem das regras participa da decisão, então coloque os casos específicos de forma intencional.

O laboratório declara httpBasic explicitamente. A conta em memória utiliza BCrypt para armazenar a representação da senha no gerenciador. A senha inicial é pública e didática, fornecida pela configuração do exercício. Um sistema real exige gestão de usuários, política de credenciais e proteção operacional apropriadas. Não publique essa conta de laboratório como acesso administrativo de um serviço.

Regras na camada web podem ser complementadas por segurança de métodos quando houver entradas além do controller. Para autorização por proprietário, receba a identidade confiável do contexto e confira a relação com o recurso no servidor. Um campo usuarioId enviado pelo cliente não comprova que o chamador possui aquele identificador.

3. Por que o laboratório mantém CSRF

CSRF envolve requisições indesejadas em contextos nos quais o navegador pode enviar credenciais automaticamente. A escolha entre sessão, cookie e outro transporte de credencial muda a análise. O uso de Basic não é uma justificativa automática para remover toda proteção CSRF, porque navegadores também podem manter e enviar esse tipo de credencial.

O catálogo mantém a proteção padrão. GET /api/csrf devolve um token e o nome do cabeçalho. O cliente preserva o cookie da sessão e envia o token em X-CSRF-TOKEN nas operações de escrita. Os testes usam o suporte de segurança para confirmar a recusa quando o token está ausente. Consulte a documentação de CSRF para o mecanismo e a configuração da versão.

Ao usar uma ferramenta de API, habilite a preservação de cookies entre as chamadas. Copiar um token e perder sua sessão correspondente pode gerar uma recusa correta. Uma resposta 403 sem token pode acontecer antes da autenticação. Para demonstrar 401 por ausência de credencial no laboratório, forneça primeiro um token válido, como fazem os testes.

4. Sessão, token e OAuth2 têm contratos próprios

Numa arquitetura com sessão, o servidor mantém ou coordena o estado associado à identidade e o cliente usa um identificador de sessão. A aplicação precisa tratar login, expiração, logout, proteção do cookie e CSRF conforme o fluxo. Uma API que recebe um bearer token tem outra forma de apresentar a credencial e precisa validar o token em cada contexto adequado.

JWT é um formato de token, não uma implementação completa de login, revogação ou autorização. Um resource server deve validar assinatura, emissor, validade temporal e as restrições exigidas pelo contrato, incluindo audiência quando aplicável. Use a integração oficial do provedor e do framework. Não escreva um filtro que apenas decodifica o payload e passa a confiar nos campos.

OAuth2 e OpenID Connect organizam papéis e fluxos específicos. Um cliente público móvel não consegue manter um segredo embutido como se fosse um servidor confidencial. A escolha deve seguir o fluxo recomendado pelo provedor, com bibliotecas adequadas e redirecionamentos registrados. Consulte o guia de resource server ao evoluir o laboratório; essa integração não está habilitada no ZIP inicial.

5. CORS não substitui autorização

CORS define como navegadores tratam acesso entre origens. Uma configuração que aceita uma origem de frontend não autentica o usuário e não impede um cliente de terminal de chamar a API. A autorização deve permanecer no servidor para cada operação e recurso. Evite liberar qualquer origem com credenciais apenas para fazer um teste passar.

Quando houver um frontend separado, liste as origens necessárias, os métodos e os cabeçalhos usados. O preflight deve ser tratado de acordo com a integração de segurança. Se a interface e a API forem servidas pela mesma origem, talvez você não precise de uma configuração CORS adicional. Identifique o cenário concreto antes de acrescentar uma regra ampla.

No laboratório local, os testes de MVC não demonstram uma política de navegador entre origens. Faça um teste no ambiente correspondente quando introduzir um frontend. Registre a origem exata, incluindo esquema, host e porta, e confira também a recusa de uma origem que não foi autorizada.

6. Senhas, logs e superfície operacional

Use uma função de derivação de senha apropriada com parâmetros e política de atualização compatíveis com o sistema. Nunca guarde senha recuperável apenas para compará-la em texto. O laboratório utiliza BCrypt pela integração do Spring, com credencial fictícia e conhecida. Contas reais exigem cadastro, recuperação e limites de tentativa tratados como funcionalidades próprias.

Logs não devem registrar Authorization, cookies de sessão, tokens completos ou senhas. Uma mensagem de erro pode informar que a autenticação falhou sem revelar se determinado cadastro existe. Detalhes operacionais devem ficar num canal com acesso apropriado. A saúde pública do laboratório não divulga componentes internos.

Não exponha console de banco, ambiente, heap dump e endpoints de administração sem necessidade e controle. Uma ferramenta útil no computador de desenvolvimento pode revelar configuração ou dados em uma implantação pública. Revise o conjunto efetivamente acessível, em vez de presumir que adicionar Actuator deixou apenas uma página inofensiva.

7. Prática: uma matriz de acesso verificável

Teste leitura pública, escrita com ADMIN, escrita sem autenticação com CSRF válido, papel insuficiente e ausência de CSRF com credencial válida. Como evolução, proponha uma rota que devolva apenas os produtos pertencentes ao usuário autenticado. Escreva cenários em que um usuário tenta acessar o id de outro. Implemente a verificação no servidor e confirme que alterar o id na URL não contorna a política. Conclua documentando quais ameaças foram tratadas e quais recursos, como TLS e OAuth2, ainda não fazem parte do laboratório local.

Liberar CORS para uma origem impede um programa de terminal não autorizado de chamar a API?

Não. CORS participa da política do navegador. Autenticação e autorização precisam ser aplicadas pelo servidor independentemente do tipo de cliente.

Se você deixar todas as condições inválidas num único teste, pode apenas confirmar a primeira barreira e nunca verificar a outra.

Ao acrescentar autorização por recurso, teste dois usuários e um id que pertence ao outro. Confira que a resposta e o estado posterior respeitam a política. Um teste com um único administrador não consegue demonstrar isolamento entre contas.

5. Persistência, limpeza e banco alvo

O método BeforeEach do laboratório limpa o repositório, deixando cada cenário independente. Os ids gerados não são presumidos como 1 em todo teste; o cenário usa o id realmente salvo. Isso evita uma dependência de sequência que pode mudar conforme o banco e o ciclo de execução.

DataJpaTest oferece um recorte útil para mapeamentos e consultas. Ainda é necessário escolher o banco com o qual você pretende comprovar a propriedade. H2 ajuda em cenários rápidos, mas uma consulta nativa ou um bloqueio pode se comportar de outra maneira no banco de produção. Uma instância de teste do banco alvo, eventualmente gerenciada por ferramenta de contêineres, permite conferir esse contrato com maior proximidade.

Testes que são envolvidos em uma transação com rollback automático podem esconder falhas que só aparecem no commit ou no encerramento do contexto. Use flush quando a propriedade exige enviar SQL e planeje cenários que realmente confirmem a fronteira relevante. Não interprete um objeto alterado em memória como prova de gravação permanente.

6. Concorrência e tempo sem testes frágeis

Para testar concorrência, coordene as etapas com mecanismos explícitos em vez de depender apenas de sleep. O cenário deve estabelecer que duas transações observaram um estado, liberar a disputa e conferir o resultado. Defina timeout para o próprio teste não ficar bloqueado indefinidamente. Depois consulte o banco numa transação nova.

Uma espera arbitrária pode passar numa máquina e falhar em outra sem revelar um defeito de negócio. Da mesma forma, um teste que passa uma vez não demonstra todas as intercalações. Escolha invariantes, como saldo nunca negativo e no máximo uma confirmação sobre a versão observada, e confira os efeitos finais.

Para regras de data, forneça um Clock ou outra fonte de tempo controlável quando isso fizer parte do domínio. Para integrações, use um servidor de teste ou um adaptador que responda com dados e falhas previstos. O objetivo é reproduzir a condição que poderia quebrar o contrato, mantendo o resultado interpretável.

7. Ler o relatório de teste e preparar a entrega

mvn clean test deve terminar sem falhas e apresentar os dezessete cenários do laboratório. Os relatórios ficam em target/surefire-reports. Se houver falha de inicialização, a causa pode impedir vários cenários de executar; não trate todos como defeitos independentes. Corrija a causa do contexto e rode novamente o conjunto afetado.

Depois de alterar o contrato, atualize exemplos, DTOs e verificações correspondentes. Rode os testes necessários e produza o JAR a partir desse mesmo código. Uma captura antiga de sucesso não acompanha automaticamente uma mudança posterior. O registro de validação deve identificar a versão de Java, a ferramenta e o conjunto executado.

Cobertura pode ajudar a localizar trechos não exercitados, mas uma porcentagem alta não prova que recusas e limites foram bem escolhidos. Um teste que só verifica status pode deixar escapar a perda de saldo. Revise o que cada assert realmente observaria se a implementação estivesse errada.

8. Prática: acrescentar um defeito que o teste detecta

Execute o conjunto original e leia os cenários. Em uma cópia de trabalho, retire temporariamente a verificação de saldo ou a proteção de versão e observe qual teste falha. Restaure a regra e confirme o sucesso. Essa experiência mostra se o cenário protege o comportamento que seu nome promete.

Depois acrescente um teste de tamanho de página zero, um de campo obrigatório ausente e um de retirada com quantidade zero. Confira status e preservação do estado quando necessário. Entregue uma relação das propriedades verificadas e das limitações: H2, ausência de carga concorrente real, rede externa e ambiente de produção.

Um teste com user("a").roles("ADMIN") comprova a comparação da senha de a?

Não. Ele fornece uma identidade ao contexto de teste para avaliar autorização. O caminho de autenticação por senha precisa de um cenário correspondente, como a chamada com httpBasic e a configuração real do laboratório.

27 · Spring Boot em operação: configuração, observabilidade e entrega

1. O artefato precisa executar fora do ambiente de desenvolvimento

Um serviço pode passar nos testes e ainda falhar ao iniciar por uma configuração ausente, permissão de pasta ou conexão indisponível. A entrega precisa identificar o artefato, a versão de Java, a configuração necessária e a forma de observar o processo. O mesmo JAR pode ser usado em ambientes diferentes quando os valores específicos são fornecidos externamente.

No catálogo do laboratório, as propriedades privilegiam uma execução local descartável. H2 está em memória, o endereço é loopback e a saúde pública não mostra componentes. Para uma instalação permanente, você precisará substituir esses valores, adicionar migrações e estabelecer acesso, transporte seguro e recuperação de dados. A transição deve ser verificável em etapas.

Este capítulo apresenta decisões operacionais e experimentos locais. Ele não configura automaticamente um provedor de nuvem nem publica o servidor. Use o projeto do tema 22 para observar inicialização, saúde e encerramento; mantenha os dados fictícios enquanto experimenta.

2. Configuração externa e perfis

Spring Boot aceita configuração em arquivos, variáveis e argumentos, com uma ordem de precedência definida. Um valor em um local pode ser sobrescrito por outro. Ao investigar um comportamento, identifique a origem efetiva sem registrar segredos. A documentação de configuração externa descreve as fontes e a ordem da linha utilizada.

Perfis permitem ativar conjuntos de configuração, como estudo e integração. Eles não são um cofre. Um arquivo application-producao.properties com senha real continua sendo um arquivo com segredo se for incluído no repositório ou no JAR. Use o mecanismo de segredos do ambiente e restrinja quem pode lê-lo.

Para valores relacionados, ConfigurationProperties permite agrupar e validar a configuração. Uma URL obrigatória ausente pode impedir a inicialização com uma explicação clara, em vez de aparecer como null numa operação posterior. Defina unidades para durações e limites para números. Uma configuração que aceita valor negativo de timeout pode produzir uma falha difícil de relacionar ao preenchimento original.

3. Actuator: selecionar e proteger endpoints

Actuator oferece recursos operacionais. Expor um endpoint na web e autorizar seu acesso são decisões diferentes. O laboratório expõe apenas health e permite essa rota sem detalhes. Endpoints de ambiente, métricas detalhadas, dump de memória e configuração exigem análise de necessidade e acesso.

Saúde pode combinar indicadores de dependências. Um serviço que depende de banco precisa representar a situação de forma útil para a infraestrutura, sem divulgar credenciais ou detalhes desnecessários ao público. Consulte os endpoints do Actuator e escolha explicitamente o conjunto que pretende disponibilizar.

Não abra todos os endpoints apenas para acompanhar uma aula de métricas. Habilite o necessário, configure a exportação para o coletor escolhido e confirme a recusa do restante. Um endereço de administração também precisa de uma política de rede e autenticação compatível com quem o consome.

4. Logs, métricas e rastreamento

Logs registram acontecimentos e contexto; métricas agregam medidas ao longo do tempo; traces ajudam a seguir uma operação entre componentes. Cada recurso responde perguntas diferentes. Um log de erro informa uma falha particular, enquanto uma métrica pode revelar que a taxa de erro cresceu após uma entrega.

Use identificadores de correlação apropriados e preserve o contexto nas chamadas necessárias. Evite colocar dados pessoais, senhas ou tokens em mensagens. Em métricas, rótulos com valores ilimitados, como um id de pedido por série, podem criar cardinalidade excessiva. Prefira dimensões limitadas que ajudem a comparar comportamento, como operação e classe de resultado.

Para o catálogo, comece medindo quantidade de chamadas, duração e recusas de uma retirada. Diferencie conflito de regra de falha inesperada. Uma taxa alta de 409 pode indicar clientes trabalhando com dados antigos, enquanto 500 exige outra investigação. O observador precisa conhecer o contrato para interpretar o número.

5. Disponibilidade, prontidão e encerramento

Uma verificação de vida responde se o processo deve continuar executando. Uma verificação de prontidão responde se ele está apto a receber trabalho. Confundir uma dependência temporariamente indisponível com processo irrecuperável pode provocar reinicializações que aumentam o problema. O significado de cada probe deve acompanhar a arquitetura e a infraestrutura.

Graceful shutdown permite que o servidor pare de aceitar novo trabalho e aguarde operações em andamento dentro de um prazo. O catálogo configura shutdown gracioso e timeout de fase de 20 segundos. Isso não garante que qualquer tarefa arbitrária, chamada externa ou fila própria será concluída. Esses recursos precisam de integração com o ciclo de vida e de limites compatíveis.

Teste o encerramento com uma operação controlada e observe o que o cliente recebe. A infraestrutura também precisa conceder tempo suficiente antes de forçar o término do processo. Um timeout interno maior que a janela de desligamento pode deixar o cliente sem confirmação mesmo que o servidor tenha produzido parte dos efeitos.

server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=20s
management.endpoints.web.exposure.include=health
management.endpoint.health.show-details=never

6. Contêineres e limites de recursos

Um contêiner empacota processo e dependências num formato próprio, mas não elimina a necessidade de configurar memória, CPU, rede e armazenamento. O runtime Java observa os limites disponíveis conforme sua versão e configuração. Meça uso sob carga antes de escolher valores; memória total envolve heap, metaspace, threads, buffers e outros componentes.

Use uma imagem base compatível e mantida, com usuário e permissões adequados. O diretório de dados deve ter persistência planejada quando necessário. Um banco em memória dentro do contêiner continua perdendo registros ao encerrar. Variáveis de ambiente e segredos precisam ser fornecidos pelo mecanismo do ambiente, sem copiá-los para camadas da imagem.

O comando de build de imagem do Spring Boot pode integrar buildpacks quando o projeto e o ambiente oferecem os requisitos. Leia a documentação do plugin Maven antes de executar. O laboratório não exige Docker e não distribui uma imagem de produção pronta.

7. Entrega, migração e reversão

Uma entrega deve ligar código, testes e artefato de forma identificável. Registre a versão ou revisão que produziu o JAR e mantenha a configuração do ambiente separada. Reproduzir o build ajuda a investigar se uma diferença veio do código, das dependências ou da infraestrutura.

Mudanças de banco precisam ser compatíveis com a estratégia de atualização. Se duas versões da aplicação executam ao mesmo tempo, uma coluna removida pode quebrar a versão anterior. Planeje expansões compatíveis, migração de dados e remoção posterior quando o cenário exigir. Reverter apenas o JAR não desfaz automaticamente uma transformação de dados.

Estabeleça um critério de sucesso após a entrega: inicialização, prontidão, consulta de exemplo e operação de teste sem dados reais. Defina também quando interromper a atualização. O roteiro deve dizer onde verificar resultados e como preservar evidências sem copiar informações sensíveis.

8. Prática: um roteiro de operação local

Inicie o catálogo com uma porta alternativa fornecida por argumento e confirme a consulta de saúde. Confira que detalhes internos e rotas não autorizadas permanecem inacessíveis. Cadastre dados fictícios, encerre o processo e observe o catálogo vazio após a nova inicialização. Registre que essa perda faz parte da configuração em memória.

Depois escreva uma proposta de configuração permanente: banco, migrações, segredo, TLS, saúde, logs e restauração. Marque quais itens foram executados e quais são apenas planejamento. A atividade termina quando outra pessoa consegue iniciar, observar e encerrar o serviço a partir do roteiro, sem descobrir valores por tentativa.

Um processo respondendo a health UP comprova que todas as operações de negócio funcionam?

Não. A saúde representa os indicadores configurados. Fluxos de negócio, permissões, dados e integrações precisam das verificações correspondentes; uma consulta de saúde não substitui esses cenários.

28 · Spring avançado: cache, tarefas e mensageria

1. Adicionar trabalho e memória sem perder consistência

Depois do CRUD e da operação básica, cache, tarefas e mensagens podem resolver necessidades observadas. Cada mecanismo também introduz estados e falhas novos. Um cache pode apresentar dado antigo; uma tarefa pode terminar depois do timeout do cliente; uma mensagem pode ser entregue mais de uma vez. A aplicação precisa dizer quais resultados continua garantindo.

Use o catálogo como exemplo. Uma lista pública de produtos pode tolerar alguns segundos de atraso, enquanto a decisão de retirar estoque deve consultar e confirmar o estado consistente. Uma notificação de retirada pode ocorrer depois do commit, mas não deve ser enviada duas vezes como se fossem operações diferentes. Escolha o mecanismo conforme a regra de cada caso.

As evoluções deste capítulo não estão habilitadas no ZIP Spring inicial. Ele fornece a base de domínio, web e transação para experimentar uma capacidade de cada vez. As referências indicam as integrações oficiais; fixe as versões pelo gerenciamento da linha utilizada e documente qualquer serviço adicional.

2. Cache: chave, validade e invalidação

Cache guarda resultados para reutilizar uma consulta. Antes de adicioná-lo, defina a chave e por quanto tempo o resultado pode permanecer válido. Uma chave que omite o usuário ou o filtro pode devolver dados de outra consulta. O cache precisa respeitar a mesma política de visibilidade do dado original.

@Cacheable pode evitar repetir a operação quando existe uma entrada para a chave. @CacheEvict remove entradas e @CachePut atualiza o valor conforme seu contrato. As anotações dependem da configuração de cache e da infraestrutura escolhida. Elas não criam automaticamente uma política distribuída de consistência entre todos os processos.

No modo comum por proxy, uma chamada interna ao próprio objeto pode não passar pela interceptação de cache. O efeito de uma anotação deve ser conferido pela chamada real. Use a documentação das anotações de cache para os detalhes e teste consulta, atualização e invalidação.

3. Uma política para o catálogo

Uma possibilidade didática é guardar a consulta pública de um produto e remover a entrada depois de uma alteração confirmada. A decisão de retirada continua na transação do banco. Se houver vários nós, um cache apenas local não recebe automaticamente a invalidação dos outros nós. Você precisa de validade limitada, invalidação coordenada ou um cache compartilhado conforme a necessidade.

Falha de cache pode permitir uma consulta direta ao banco se isso preservar a regra e a capacidade do sistema. Uma indisponibilidade pode concentrar todas as chamadas na fonte original, causando sobrecarga. Meça acertos, falhas, volume e latência. Um cache que quase nunca acerta pode adicionar complexidade sem reduzir trabalho relevante.

Não use a existência de uma entrada em cache como único controle para uma operação que exige unicidade durável. Expiração, reinicialização e concorrência podem apagar ou duplicar essa observação. Restrições e transações continuam protegendo o estado permanente.

4. Tarefas assíncronas e executores limitados

@Async permite executar uma chamada por um executor configurado quando ela passa pela infraestrutura adequada. O programa precisa definir capacidade, fila, rejeição e tratamento de falha. Criar uma thread nova por solicitação sem limite pode esgotar recursos. Uma fila sem limite pode acumular trabalho que já perdeu utilidade.

Uma tarefa assíncrona não herda automaticamente toda a intenção transacional do chamador. Quando a transação é associada à thread, mudar de executor exige uma fronteira própria. Passe identificadores e dados adequados, em vez de supor que uma entidade carregada num contexto continuará gerenciada em outra thread. Consulte a documentação de tarefas e agendamento para o modelo de execução.

Defina como o cliente acompanha o resultado. Um 202 Accepted pode representar aceitação de um trabalho, com um identificador e uma consulta de estado, mas ainda não significa conclusão. Se a tarefa só existe na memória do processo, uma reinicialização pode perdê-la. Para trabalho durável, use um mecanismo persistente com política de recuperação.

5. Mensagens, confirmação e repetição

Uma mensagem descreve um fato ou comando entregue por uma infraestrutura de comunicação. O produtor precisa saber quando a publicação foi aceita; o consumidor precisa decidir quando confirmar o processamento. Se a confirmação se perder depois de a alteração ser gravada, a mensagem pode reaparecer. O consumidor deve reconhecer a repetição.

Idempotência significa que repetir a mesma operação identificada não produz efeitos adicionais indevidos. Para uma retirada, mantenha um id de operação e registre seu resultado de forma atômica com a alteração relevante. Se o mesmo id voltar com conteúdo diferente, recuse o conflito em vez de reinterpretá-lo como uma nova intenção.

Uma fila de mensagens não torna automaticamente a regra consistente. Você precisa tratar ordem, repetição, falhas permanentes, limite de tentativas e observação das pendências. Uma mensagem que sempre falha deve seguir para um tratamento definido, sem bloquear indefinidamente todas as demais nem ser descartada sem registro.

6. Outbox e a fronteira entre banco e publicação

Considere confirmar uma retirada no banco e depois publicar RetiradaConcluida. Se o processo cair entre essas duas etapas, o saldo muda e a notificação não sai. Publicar antes do commit cria o risco inverso: outro sistema reage a uma operação que depois é desfeita. Uma transação local não coordena automaticamente os dois recursos.

No padrão outbox, a mesma transação grava a alteração de negócio e um registro de evento numa tabela de saída. Um publicador posterior lê os registros pendentes e os envia. Depois marca a publicação conforme a estratégia. A queda entre envio e marcação ainda pode produzir repetição, então consumidores precisam de idempotência.

O evento deve carregar uma identidade estável, versão de contrato e dados necessários ao consumidor. Evite serializar a entidade inteira com todos os campos privados. Defina retenção e limpeza da outbox para não crescer indefinidamente. Métricas de idade e quantidade de pendências ajudam a reconhecer uma publicação que parou.

Operação transacional no banco:
1. Conferir se o id da operação já possui resultado.
2. Validar e aplicar a retirada.
3. Registrar o resultado da operação e o evento na outbox.
4. Confirmar a transação.

Publicação posterior:
1. Selecionar eventos pendentes com coordenação entre publicadores.
2. Publicar com o mesmo id estável.
3. Registrar a confirmação; tolerar repetição no consumidor.

7. Retry, espera e falha permanente

Repetição automática pode ajudar numa falha transitória, mas deve ter limite, intervalo e critério. Um erro de validação não se resolve tentando a mesma entrada dez vezes. Um timeout depois de uma operação não idempotente exige descobrir o estado, pois o efeito pode ter sido confirmado.

Use espera crescente com variação quando muitos clientes podem repetir ao mesmo tempo. Respeite limites do serviço remoto e um orçamento total de tempo. Cada camada repetindo sem coordenação pode multiplicar chamadas. Registre tentativas e resultado final, sem gerar uma mensagem de erro alarmante para cada repetição que ainda faz parte da política esperada.

Para falhas permanentes, ofereça uma forma de diagnóstico e correção. Reprocessar uma pendência manualmente também precisa preservar seu id para não criar outro efeito. O operador deve saber o que aconteceu e o que será tentado, em vez de apenas receber um botão genérico de repetir tudo.

8. Prática: reproduzir a duplicação antes de integrar um broker

Crie um adaptador em memória que entregue duas vezes o mesmo comando de retirada. Registre o id e o resultado numa estrutura de teste, mantendo as duas ações sob a mesma coordenação. Confira que o saldo é descontado uma vez e que o conteúdo diferente com id repetido é recusado.

Depois desenhe a migração dessa regra para tabelas transacionais e uma outbox. Marque as quedas possíveis antes e depois do commit, do envio e da confirmação. Como experimento separado, adicione cache apenas à consulta e verifique a invalidação. A atividade termina quando você consegue explicar o estado resultante em cada falha e tem testes para repetição, recusa e recuperação.

Gravar na outbox elimina qualquer entrega repetida?

Não. Uma queda depois da publicação e antes da marcação pode levar ao reenvio. A outbox coordena o registro do evento com a transação local; os consumidores ainda precisam tratar repetição com uma identidade estável.

29 · Integrações distribuídas: resiliência, contratos e consistência

1. Quando uma chamada atravessa processos

Uma integração distribuída envolve componentes que falham e evoluem de forma independente. Uma requisição pode sair do cliente, chegar ao servidor e perder a resposta. O cliente observa timeout e desconhece se a operação terminou. Essa incerteza aparece mesmo numa rede local e precisa fazer parte do contrato.

O catálogo pode atender uma janela desktop e um aplicativo Android. Ambos convertem suas ações em requisições, mas não compartilham uma transação de memória com o servidor. A validação local orienta o preenchimento; a decisão final permanece no serviço que confirma o estado compartilhado. O cliente precisa representar carregamento, confirmação, conflito e resultado desconhecido.

Comece com um serviço bem delimitado antes de dividir o programa em vários serviços. Separar processos acrescenta deploy, comunicação, observabilidade e consistência. A divisão deve resolver uma necessidade concreta de domínio ou operação, com responsabilidade clara sobre os dados.

2. Timeouts e orçamento de uma operação

Configure limites de conexão e resposta apropriados ao cliente HTTP utilizado. Um timeout muito longo mantém recursos e deixa a pessoa sem retorno; um limite curto demais pode transformar uma operação normal numa sequência de repetições. Meça o comportamento e escolha um orçamento que inclua todas as chamadas necessárias.

Se uma tela aceita esperar no máximo alguns segundos, cada etapa não pode consumir esse prazo integral várias vezes. Propague um limite de trabalho ou coordene os timeouts conforme a arquitetura. Cancele o que perdeu relevância quando possível, lembrando que cancelamento do cliente não desfaz automaticamente o efeito no servidor.

No Java local, HttpClient oferece configuração de conexão e timeout por requisição. A biblioteca precisa ser usada fora da thread gráfica. Erros de transporte devem preservar o rascunho e permitir consulta posterior do estado. Não converta qualquer IOException em produto inexistente.

3. Idempotência no contrato HTTP

Uma criação pode receber uma chave de operação gerada pelo cliente e válida no escopo daquele usuário e ação. O servidor registra a chave junto ao resultado de forma transacional. Repetir a mesma intenção devolve o resultado conhecido; mudar o conteúdo com a mesma chave deve gerar conflito conforme o contrato.

A retenção dessa chave precisa ser definida. Se o registro expira cedo demais, uma repetição tardia pode criar outro efeito. Se nunca expira, o armazenamento cresce. Inclua a política na documentação e proteja a associação entre chave, identidade e payload. Uma chave sem escopo de usuário pode revelar ou reutilizar o resultado de outro chamador.

Não presuma idempotência apenas pelo nome de um método ou pela presença de um cabeçalho que o servidor ignora. O comportamento deve ser implementado e verificado. O catálogo inicial protege versão e código único, mas não implementa uma tabela geral de chaves de operação; essa é uma evolução explícita.

4. Resiliência e limites de isolamento

Circuit breaker pode interromper chamadas para uma dependência que está falhando, permitindo um período de recuperação e testes controlados. Ele precisa de métricas e limites coerentes. Um fallback deve ter significado no domínio: devolver saldo zero quando o servidor está indisponível apresenta um dado falso e pode induzir uma decisão errada.

Bulkheads ou limites de concorrência isolam recursos para que uma dependência lenta não ocupe toda a capacidade. Filas, pools e conexões precisam de tamanhos limitados e política de rejeição. Uma recusa rápida e compreensível pode ser melhor do que acumular trabalho que vai expirar, mas o cliente deve saber que a operação não foi aceita.

Teste falha, lentidão e recuperação separadamente. Uma integração que funciona apenas quando todos os componentes respondem imediatamente ainda não mostrou como preserva recursos sob problema. Registre duração, erros e trabalho pendente para distinguir dependência lenta de saturação no próprio processo.

5. REST, eventos, SSE e WebSocket

REST com requisição e resposta atende bem às operações do catálogo. Eventos comunicam fatos entre componentes com outro acoplamento temporal. SSE fornece um fluxo do servidor para o cliente sobre HTTP e pode servir a notificações simples. WebSocket permite comunicação bidirecional persistente, exigindo tratamento de conexão, autorização e reconexão.

Escolha a comunicação pelo comportamento necessário. Uma tela que consulta uma vez não exige um canal permanente. Uma notificação não substitui a consulta de estado depois de reconectar, pois mensagens podem ser perdidas conforme a solução. Defina como o cliente retoma a posição e reconhece itens já vistos.

Eventos precisam de versão e semântica. RetiradaConcluida deve representar algo confirmado, com id estável e dados suficientes. Um consumidor não deve depender de todos os detalhes internos do produtor para interpretar o fato. Documente alterações compatíveis e mantenha exemplos de mensagens para teste de consumidores.

6. Spring MVC e WebFlux

Spring MVC utiliza o modelo servlet; WebFlux oferece um modelo reativo com tipos e infraestrutura próprios. Trocar o starter sem revisar chamadas bloqueantes não transforma a aplicação inteira em não bloqueante. Acesso JPA tradicional é bloqueante e precisa de uma estratégia compatível quando entra num fluxo reativo.

Programação reativa pode ser útil em determinados perfis de I/O e fluxo, mas acrescenta conceitos de composição, cancelamento e pressão. Um catálogo pequeno com transações JPA pode continuar com MVC. Meça e identifique a necessidade antes de migrar apenas para seguir uma tendência.

Consulte a documentação de WebFlux para o modelo e os requisitos. O ZIP inicial utiliza MVC e não demonstra uma pilha reativa de ponta a ponta. Essa distinção ajuda a interpretar quais garantias seus testes realmente cobrem.

7. Contratos entre versões e dados pertencentes a cada serviço

Um cliente móvel antigo pode permanecer instalado durante meses. Acrescentar um campo opcional costuma ser diferente de renomear um campo obrigatório ou mudar sua unidade. Mantenha contratos que suportem a janela de versões que você promete atender. Testes de consumidor podem conferir exemplos contra uma versão nova do provedor.

Se houver vários serviços, cada um deve ter uma responsabilidade clara sobre os dados que altera. Compartilhar tabelas para qualquer serviço escrever em qualquer campo dificulta evoluir o esquema e preservar as invariantes. Uma operação que atravessa serviços pode precisar de passos e compensações, com estados intermediários visíveis.

Uma compensação não é necessariamente o inverso perfeito de uma transação. Cancelar uma reserva pode liberar estoque, enquanto uma notificação já lida não pode ser desvista. Defina o resultado aceitável em cada etapa e ofereça meios de acompanhar pendências. O usuário precisa saber se o processo terminou, foi recusado ou aguarda recuperação.

8. Prática: uma integração que admite falha

Implemente um cliente de consulta usando o laboratório HTTP do Extra ou o catálogo Spring. Configure timeout e rode fora da thread gráfica. Simule conexão recusada, resposta lenta, JSON inválido e 409. Para cada caso, apresente uma mensagem distinta e preserve a entrada.

Depois desenhe o fluxo de retirada com chave de operação e versão. Marque a situação em que a resposta se perde após a confirmação e descreva como o cliente descobre o resultado sem descontar novamente. O trabalho termina quando uma pessoa consegue seguir o roteiro, repetir a falha e explicar o estado confirmado e o estado ainda desconhecido.

Retornar uma lista vazia quando a API falha é um fallback seguro para qualquer consulta?

Não. Isso confunde ausência de registros com resultado desconhecido e pode induzir novos cadastros. Mostre a falha ou um dado anterior identificado como desatualizado, conforme uma política explícita.

30 · Projeto final: Java no desktop, Android e servidor

1. Um projeto para aplicar o percurso completo

O projeto final é um sistema de materiais de estudo com catálogo, saldos e retiradas. O servidor concentra o estado compartilhado. Uma interface desktop atende operações de administração e um aplicativo Android consulta e solicita ações permitidas. O objetivo é integrar as decisões estudadas, mantendo as responsabilidades e as limitações visíveis.

Você já possui quatro bases para download: regra e janela Swing, regra e janela JavaFX, aplicativo Android inicial e catálogo Spring. Elas são laboratórios independentes, com requisitos e testes próprios. O projeto final orienta sua integração gradual; não apresenta as quatro bases como um único sistema já conectado e pronto para produção. Escolha Swing ou JavaFX para o cliente desktop inicial.

Antes de integrar, execute cada laboratório e registre o resultado. Uma falha local de SDK não deve ser confundida com um erro de contrato HTTP. A sequência abaixo estabelece entregas pequenas, cada uma com critérios observáveis. A seção final do Extra reúne uma matriz de verificação e um roteiro imprimível para acompanhar o trabalho.

2. Requisitos e invariantes do domínio

Cada material possui código estável e quantidade não negativa. O recebimento exige quantidade positiva e controla overflow. A retirada não pode deixar saldo negativo e deve conferir o estado compartilhado no servidor. Uma recusa preserva o saldo. O usuário precisa distinguir leitura pública, operação autorizada e ação que não chegou a ser confirmada.

Defina quais informações serão pessoais e quais são públicas. Para o estudo, use dados fictícios. Se a API permitir consultar todos os materiais sem login, isso deve ser uma decisão compatível com os dados apresentados. Introduzir nome de aluno ou histórico individual muda a política de acesso e exige revisão dos endpoints.

Escreva exemplos antes do código: estoque 5, retirada 2, resultado 3; retirada 6, conflito e saldo 5; versão antiga, conflito e saldo preservado; comando repetido com o mesmo id, um único efeito. Esses exemplos se tornam critérios de teste das camadas envolvidas.

3. Fronteiras de compartilhamento

Um módulo de domínio pode conter identificadores, regras e resultados que não dependem de UI ou persistência. Verifique a compatibilidade das APIs com todos os destinos antes de compartilhar um artefato. O Android não deve receber entidades JPA como seu modelo de tela. DTOs de rede e adaptadores traduzem contratos entre processos.

O servidor recebe requisições e confirma transações. O cliente desktop mantém rascunho, seleção e estado de carregamento. O aplicativo Android trata ciclo de vida, armazenamento local e conectividade conforme as etapas escolhidas. Copiar todo o servidor para dentro do aplicativo móvel mistura dependências e não resolve a sincronização.

Comece com fronteiras em pacotes e projetos claros. Introduza um módulo publicado compartilhado apenas quando o reaproveitamento e a compatibilidade estiverem demonstrados. Uma duplicação pequena de DTO em clientes de tecnologias diferentes pode ser aceitável se o contrato for testado e documentado.

4. Etapa 1: consolidar o servidor

Use o catálogo Spring e confirme os dezessete testes. Documente rotas, campos, códigos de resposta e os passos de CSRF do laboratório. Acrescente os casos de regra que seu escopo exigir, como recebimento e busca por código. Cada alteração deve preservar as recusas antigas.

Para armazenamento permanente, troque o banco de memória por uma instância de estudo e introduza migrações. Execute os testes relevantes nesse banco. Acrescente uma cópia de segurança e pratique restauração com dados fictícios. A etapa termina quando o servidor pode reiniciar sem perder os registros que você declarou permanentes.

Não remova filtros para facilitar a conexão do primeiro cliente. Se o mecanismo de autenticação mudar, atualize o contrato e os testes antes de integrar a tela. O servidor deve continuar recusando chamadas inválidas mesmo quando feitas por um cliente fora da sua interface.

5. Etapa 2: um cliente desktop responsivo

Adapte a janela escolhida para consultar a lista e apresentar código e saldo. O adaptador HTTP executa fora da thread gráfica. A tela mostra carregando, conteúdo e falha. Uma consulta antiga não pode sobrescrever a seleção de uma solicitação posterior. O botão de retirada usa a versão do produto que foi realmente apresentado.

Preserve os campos quando uma operação for recusada. Após sucesso, atualize o saldo a partir da resposta confirmada. Se houver timeout sem resposta, mostre que o resultado precisa ser consultado e evite repetir uma operação não idempotente às cegas. A interação por teclado e a leitura de erro fazem parte da entrega.

A etapa termina com consulta, uma escrita autorizada no ambiente local, conflito reproduzível e encerramento de tarefas ao fechar a janela. Faça o pacote desktop do sistema que você consegue conferir. Outros sistemas permanecem na matriz de suporte como pendentes até serem testados.

6. Etapa 3: um cliente Android que preserva o trabalho

Parta do aplicativo de Views. Acrescente estado de apresentação e um repositório antes de ligar a rede. Rotação e retorno à tela não devem duplicar uma retirada. O rascunho deve sobreviver às transições definidas, com armazenamento apropriado ao seu tempo de vida.

Conecte primeiro uma consulta usando o ambiente de desenvolvimento documentado. Confira o endereço visto pelo emulador ou dispositivo e mantenha a exposição do servidor controlada. Depois implemente a autenticação adequada ao cenário, sem embutir segredos reais no APK. Uma integração OAuth2 exige a configuração correspondente e não vem pronta no laboratório básico.

Se escolher funcionamento offline, defina quais consultas usam dados locais, como a defasagem aparece e quais escritas podem ficar pendentes. Para retiradas que dependem de saldo compartilhado, o cliente não deve anunciar confirmação final antes de o servidor decidir. A etapa termina com teste de rotação, desconexão, reconexão e recusa de versão.

7. Etapa 4: consistência e observação

Acrescente um identificador de operação quando precisar repetir escritas com segurança. Registre o resultado junto à alteração e teste conteúdo repetido e conteúdo conflitante. Se publicar eventos, use uma estratégia que preserve a relação com o commit, como a outbox estudada. Uma mensagem repetida deve produzir um único efeito no consumidor.

Defina métricas e logs suficientes para seguir uma operação sem registrar credenciais. Uma retirada deve ter um resultado de negócio identificável e uma duração observável. Confira o acesso aos endpoints de operação e a indisponibilidade controlada de uma dependência. O roteiro deve explicar como distinguir erro de regra, erro de acesso e falha de infraestrutura.

Essa etapa pode ficar fora da primeira versão integrada se o projeto ainda não precisa de mensageria. Registre o limite de forma explícita e mantenha a arquitetura simples. A profundidade do estudo vem de provar as garantias escolhidas, não da quantidade de ferramentas instaladas.

8. Documentação e demonstração do projeto

Publique no próprio material do projeto os requisitos, comandos, arquivos de configuração de exemplo, contratos e testes. Nenhum passo deve depender de um diretório particular do autor. Use segredos fictícios e indique onde cada valor real seria fornecido. Inclua um conjunto pequeno de dados de demonstração que possa ser descartado.

Na apresentação, mostre um fluxo de sucesso e uma recusa em cada cliente. Depois simule uma falha de conexão e explique o que ficou confirmado. Apresente a matriz de plataformas, versões e verificações. Se uma parte não foi executada, marque-a como pendente, sem inferir funcionamento a partir de uma compilação de outra plataforma.

Para revisar em grupo, cada pessoa deve explicar uma fronteira e repetir um teste da outra. Isso ajuda a encontrar instruções ausentes e dependências implícitas. A entrega final deve permitir que alguém obtenha os arquivos disponibilizados, siga o roteiro e compare o resultado com critérios escritos.

9. Prática: avaliação final por evidências

Reúna uma tabela com domínio, servidor, desktop, Android, dados e operação. Para cada linha, registre cenário, resultado esperado, resultado observado e ambiente. Inclua limites de nota, saldo insuficiente, versão antiga, acesso recusado, entrada malformada, perda de conexão, rotação e restauração de dados conforme o escopo que implementou.

Explique duas decisões e suas consequências: por exemplo, por que o domínio não importa componentes visuais e por que uma escrita após timeout precisa de idempotência ou consulta do resultado. Finalize com uma demonstração reproduzível, fontes completos e instruções de execução. Use a matriz do projeto final no Extra como apoio para acompanhar o que foi verificado e o que continua em evolução.

Compartilhar o mesmo arquivo de entidade entre servidor e Android elimina a necessidade de contrato?

Não. Persistência, transporte e apresentação possuem responsabilidades e runtimes diferentes. O contrato da API continua necessário, mesmo quando regras ou tipos compatíveis são reaproveitados em parte do projeto.
