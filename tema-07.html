1. De instruções soltas a objetos com responsabilidades

Uma classe pode reunir estado e operações que precisam obedecer às mesmas regras. Isso ajuda quando uma aplicação já não cabe em uma sequência curta no main. A vantagem não vem de criar uma classe para cada palavra do enunciado, mas de manter uma decisão de negócio em um lugar que consiga protegê-la e explicá-la.

Comece com um caso concreto: um estoque tem quantidade e operações de entrada e saída. Uma saída não deveria produzir quantidade negativa. Se qualquer código puder mudar o campo sem passar pela regra, o objeto não está garantindo seu próprio contrato. Este tema introduz a relação entre estado, método, referência e responsabilidade; encapsulamento recebe aprofundamento no tema 9.

Ao terminar, você deverá diferenciar uma classe de uma instância, seguir os argumentos de uma chamada, explicar o que uma alteração de referência muda e usar polimorfismo sem depender do tipo concreto em todo lugar. Não é necessário aprender um framework para testar essas ideias. Programas pequenos de console tornam as decisões observáveis.

2. Organizar dados e comportamentos

Programação orientada a objetos organiza o programa em objetos que possuem estado e comportamento. Uma classe define um tipo; um objeto é uma instância desse tipo. No programa abaixo, marca, modelo e bateria são atributos de um celular, enquanto tirar foto é uma operação. Para uma conta, saldo é estado e depositar é uma operação que o modifica segundo regras.

A modelagem deve atender ao problema que o programa resolve. Uma classe não precisa reproduzir tudo que um objeto do mundo real possui. Para controlar empréstimos de um livro, título e disponibilidade podem importar; para calcular frete, peso e dimensões podem ser necessários. Abstrair é escolher as informações e operações relevantes e oferecer uma forma de usá-las sem exigir que todo chamador conheça seus detalhes internos.

3. Declarar uma classe e criar objetos

class Celular {
    String marca;
    String modelo;
    int bateria;

    void tirarFoto() {
        System.out.println("Foto registrada por " + modelo);
    }
}

public class Main {
    public static void main(String[] args) {
        Celular primeiro = new Celular();
        primeiro.marca = "Marca A";
        primeiro.modelo = "Modelo 1";
        primeiro.bateria = 100;
        primeiro.tirarFoto();
    }
}

Este programa cabe em Main.java, pois apenas Main é uma classe pública de topo. Celular primeiro; declara uma variável, e new Celular() cria um objeto e devolve uma referência para ele. Declarar a variável sem instanciar não cria um celular. O ponto acessa um membro: primeiro.modelo lê o atributo e primeiro.tirarFoto() chama o método.

Dois objetos criados com new podem ter valores diferentes, mesmo pertencendo à mesma classe. Alterar a bateria de um não altera automaticamente a bateria do outro. Se duas variáveis guardarem a mesma referência, ambas acessarão o mesmo objeto. Copiar uma referência não é criar uma cópia independente do estado.

4. Métodos, parâmetros e retorno

Um método reúne instruções para executar uma tarefa. A declaração informa o nome, os parâmetros e o tipo de retorno. int somar(int a, int b) recebe dois inteiros e promete devolver um inteiro. Na chamada somar(5, 10), 5 e 10 são argumentos: valores fornecidos aos parâmetros. O nome do parâmetro pertence ao método e não precisa coincidir com o nome da variável usada pelo chamador.

static int somar(int a, int b) {
    return a + b;
}

static void apresentar(int resultado) {
    System.out.println("Resultado: " + resultado);
}

return encerra a execução atual do método e, quando necessário, entrega um valor ao chamador. Um método com retorno precisa ter um resultado compatível em todos os caminhos que podem terminar normalmente. Um método void executa uma ação sem fornecer um valor; ele pode usar return; para encerrar antes do fim. Imprimir um número e devolvê-lo são efeitos diferentes: um retorno pode ser armazenado, somado e testado sem depender do texto no console.

Em um conversor de moedas, o método pode calcular e retornar o valor, deixando a apresentação para main. Uma chamada com 105 reais e cotação 5.25 devolve 20.0. O chamador decide como formatar o resultado. A cotação deve ser fornecida pelo enunciado; zero e valores negativos são inválidos nesse modelo.

5. Membros de instância e membros static

Um atributo de instância pertence a cada objeto. Um membro static pertence à classe e é compartilhado por suas instâncias. Um método estático não possui this, pois não há um objeto receptor implícito. Esse é o motivo de os primeiros métodos auxiliares da apostila serem estáticos: podem ser chamados diretamente do main estático. A visibilidade public é outra decisão e não é o que torna essa chamada estática possível.

class Contador {
    int valor;
    static int objetosCriados;

    Contador() {
        objetosCriados++;
    }

    void incrementar() {
        valor++;
    }
}

Ao criar dois contadores, cada valor começa em zero e objetosCriados chega a dois. Incrementar um contador não altera o valor do outro. Um saldo estático seria compartilhado por todas as instâncias da classe. Para representar várias contas, o saldo deve pertencer a cada objeto de conta, evitando compartilhar indevidamente o mesmo dinheiro entre usuários.

6. Java passa argumentos por valor

Java copia o valor de cada argumento para o parâmetro. Para um primitivo, o método recebe uma cópia do número ou booleano. Reatribuir o parâmetro não altera a variável do chamador. Para um objeto, o valor copiado é a referência. O método pode usar essa referência para modificar o objeto compartilhado, mas reatribuir o parâmetro para outro objeto não troca a variável do chamador.

static void alterar(int numero, int[] valores) {
    numero = 99;
    valores[0] = 99;
}
// Se n vale 1 e dados contém {1}, depois de alterar(n, dados):
// n continua 1; dados[0] passa a 99.

Esse comportamento explica por que um método pode preencher um array recebido e por que uma função que apenas reatribui seu parâmetro não consegue substituir a referência original. Para criar outra estrutura e permitir que o chamador a use, retorne essa estrutura e atribua o retorno no ponto da chamada.

7. Sobrecarga, herança e polimorfismo

Sobrecarga declara métodos com o mesmo nome e listas de parâmetros diferentes. somar(int, int) e somar(double, double) são assinaturas distintas. Apenas mudar o tipo de retorno não cria uma sobrecarga válida. A escolha da sobrecarga considera os tipos dos argumentos na compilação, não um texto impresso pelo método.

Herança com extends permite definir uma classe a partir de outra. Java permite uma superclasse direta para uma classe. Sobrescrita fornece outra implementação para um método de instância herdado; a anotação @Override ajuda o compilador a verificar essa intenção. Quando uma referência de um tipo mais geral aponta para um objeto de uma subclasse, a chamada de um método sobrescrito usa a implementação do objeto em execução. Esse é um caso de polimorfismo.

Uma interface descreve um contrato que classes podem implementar. A relação de herança deve representar uma relação adequada de tipos. Um carro que possui um motor usa composição: guarda uma referência para um objeto Motor. Isso não faz o carro herdar do motor nem receber automaticamente seus direitos de acesso. A seguir, observe um contrato implementado por duas classes.

8. Interfaces e polimorfismo com um exemplo completo

Abstração escolhe o que um contrato precisa representar; encapsulamento controla o estado e as operações permitidas. Herança estabelece uma relação de subtipos. Polimorfismo permite que uma chamada por um contrato comum use implementações diferentes. No programa abaixo, cada mensagem possui seu texto, enquanto o método que a apresenta trabalha com o mesmo contrato.

interface Mensagem {
    String texto();
}

class BoasVindas implements Mensagem {
    @Override
    public String texto() {
        return "Bem-vindo ao estudo";
    }
}

class Lembrete implements Mensagem {
    @Override
    public String texto() {
        return "Revise o exemplo antes de executar";
    }
}

public class Main {
    static void apresentar(Mensagem mensagem) {
        System.out.println(mensagem.texto());
    }

    public static void main(String[] args) {
        apresentar(new BoasVindas());
        apresentar(new Lembrete());
    }
}

Praticar este programa no Playground

As duas linhas apresentam os textos definidos em cada classe. O parâmetro de apresentar é do tipo Mensagem; a implementação do objeto determina qual método de instância sobrescrito é executado. O chamador não precisa consultar o nome da classe nem usar um if para cada mensagem. Os métodos de implementação são públicos porque o método abstrato declarado nessa interface possui esse acesso. A anotação @Override ajuda a detectar uma assinatura que não cumpre o contrato.

Acrescente outra classe que implemente Mensagem e faça uma terceira chamada. Alterar o nome do método para textos sem implementar texto deve impedir a compilação. Essa experiência distingue contrato de simples coincidência de nomes. Abra a atividade Um contrato, duas mensagens para praticar este programa. O rascunho é salvo separadamente.

9. Classe abstrata, interface e composição

Uma classe abstrata não pode ser instanciada diretamente. Ela pode reunir estado de instância, construtores e métodos implementados ou abstratos. Sua construção participa da inicialização da subclasse. Uma interface expressa um tipo que classes podem implementar; no recorte básico, define operações exigidas. Interfaces também podem oferecer métodos default e estáticos, portanto a regra “interface nunca tem implementação” está incompleta.

Uma classe pode estender uma única classe diretamente e implementar várias interfaces. Use uma base abstrata quando há uma relação de tipos e estado ou comportamento compartilhado que pertencem àquela base. Use uma interface quando o consumidor precisa de uma capacidade ou contrato sem exigir a mesma hierarquia de classes. Um carro que possui um motor pode receber esse motor como colaborador; essa composição evita apresentar o carro como um tipo de motor. O guia de classes e métodos abstratos compara essas possibilidades.

A relação de herança deve preservar o que o chamador espera do tipo mais geral. Se uma operação da base promete aceitar determinada entrada, uma subclasse não pode recusá-la arbitrariamente e continuar cumprindo a mesma promessa. Reutilizar algumas linhas de código não basta para justificar extends. Antes de construir uma árvore de classes, escreva o contrato e teste duas implementações pelo mesmo tipo de referência.

10. Lambdas e processamento com streams

Uma lambda descreve um comportamento para uma interface funcional, que possui um único método abstrato relevante para esse contrato. Em n -> n >= 7, o parâmetro recebe um valor e a expressão responde se ele atende ao limite. A Stream API encadeia operações sobre uma fonte de dados. filter seleciona elementos, map transforma cada um e collect reúne o resultado. Isso permite descrever uma consulta sem substituir as coleções que armazenam os dados.

import java.util.Arrays;
import java.util.List;
import java.util.stream.Collectors;

public class Main {
    public static void main(String[] args) {
        List<Integer> notas = Arrays.asList(5, 7, 9, 7);
        List<Integer> aprovadas = notas.stream()
            .filter(n -> n >= 7)
            .sorted()
            .collect(Collectors.toList());
        System.out.println(aprovadas);
        System.out.println(notas);
    }
}

Praticar este programa no Playground

A saída é [7, 7, 9] e depois [5, 7, 9, 7]. Nesse pipeline, a origem continua na sequência inicial; sorted ordena os elementos do fluxo. Operações intermediárias são preguiçosas: o processamento acontece quando uma operação terminal consome o fluxo. Uma stream consumida não deve ser reutilizada. Crie outra com notas.stream() para uma nova consulta. Streams não tornam os objetos envolvidos imutáveis e efeitos colaterais nas lambdas podem alterar estado.

O exemplo usa APIs disponíveis desde Java 8 para funcionar no ambiente deste site. Recursos como Stream.toList() exigem bibliotecas posteriores e não estão incluídos no compilador do Playground. Compare o pipeline com um laço que filtra e ordena os mesmos valores. Não escolha parallelStream() apenas pelo nome: paralelismo acrescenta coordenação e pode piorar uma tarefa pequena. Experimente a atividade Filtrar notas com streams para acompanhar o pipeline. A documentação de Stream detalha as regras do fluxo.

11. Estado, memória e responsabilidade

Uma variável de referência pode deixar de apontar para um objeto quando recebe outro valor. Se o objeto não puder mais ser alcançado pelo programa, sua memória pode ser recuperada pelo coletor de lixo. O momento dessa coleta não é uma etapa que você controla apenas atribuindo null. Recursos como arquivos e conexões precisam de fechamento apropriado; coleta de memória não substitui esse cuidado.

Uma classe deve concentrar operações relacionadas a sua responsabilidade. Uma conta pode proteger saldo e movimentações; a interface de console lê a opção e apresenta mensagens. Essa separação ajuda a testar o cálculo sem precisar digitar todo o menu. No projeto de estudo, comece com métodos pequenos e nomes concretos. Criar muitas classes sem uma necessidade compreensível dificulta acompanhar o fluxo.

13. Desenhar a responsabilidade antes de desenhar as classes

Liste o que o sistema precisa fazer e quais informações cada operação exige. Para controlar uma reserva de vagas, uma classe pode conhecer sua capacidade e ocupação; uma camada de apresentação lê a opção e mostra a mensagem. A regra de reservar não precisa perguntar ao Scanner qual texto será digitado. Separar essas tarefas permite verificar o domínio sem simular toda a interface.

Evite classes que só repassam cada chamada sem acrescentar uma fronteira útil. Evite também uma classe central que conhece todas as entradas, regras e formatos de saída. O tamanho do arquivo sozinho não decide a divisão: procure decisões que mudam juntas e dependências que tornam difícil testar um comportamento isolado.

Uma responsabilidade clara pode ser descrita em uma frase: “controlar a quantidade disponível sem permitir negativos”. Se a frase começa a listar relatórios, login, arquivos e mensagens de erro da interface, talvez existam tarefas diferentes. Não crie uma arquitetura inteira antecipadamente; extraia uma fronteira quando o problema real a justificar.

14. Parâmetros e retorno formam o contrato de uma chamada

O tipo, a ordem e o significado dos parâmetros importam. Dois doubles chamados a e b podem representar preço e desconto, reais e cotação ou medidas diferentes. Nomes e documentação precisam indicar as unidades. Um retorno também exige interpretação: zero pode ser resultado válido, enquanto -1 pode ser sentinela de ausência em uma busca.

A operação não imprime o resultado dentro do método. Quem chama pode apresentá-lo em console, interface gráfica ou teste. A cotação é dada pelo exercício e não vem de uma consulta de mercado. O retorno não deve fingir sucesso quando os argumentos forem inválidos; a falha tem uma forma explícita.

Uma função com retorno não precisa modificar estado. Isso costuma facilitar a verificação porque a mesma entrada pode ser comparada à mesma regra sem depender do histórico do objeto. Quando houver estado mutável, documente quais operações o alteram e quais são apenas consultas.

15. Referências: mutar o objeto não é reatribuir o chamador

Java passa argumentos por valor. Para um primitivo, o método recebe uma cópia daquele valor primitivo. Para um objeto, recebe uma cópia do valor da referência. As duas referências podem alcançar o mesmo objeto, permitindo observar uma mutação. Reatribuir apenas o parâmetro, por outro lado, não muda a variável do chamador.

Desenhe duas variáveis apontando para o mesmo objeto antes da chamada. Durante alterar, a referência recebida inicialmente aponta para esse mesmo objeto. A criação da Caixa com valor 100 muda apenas o destino do parâmetro local. Se o objetivo fosse substituir o valor usado pelo chamador, o método poderia devolver a nova referência para uma atribuição explícita.

Não descreva esse comportamento como passagem por referência. Essa expressão costuma sugerir que o método poderia substituir diretamente a variável do chamador. A distinção evita erros em métodos que tentam “trocar” dois objetos reatribuindo somente seus parâmetros.

16. Static, instância e o risco de compartilhar estado sem querer

Um campo de instância pertence ao estado de cada objeto. Um campo static pertence à classe e é compartilhado por suas instâncias. Use static para uma decisão que realmente é da classe ou para uma função sem dependência de estado de instância. Não transforme todos os campos em static apenas para acessá-los a partir do main.

Se valor fosse static, os dois contadores observariam o mesmo total. Isso seria uma regra diferente, não uma correção para a dificuldade de acessar um campo. A escolha precisa acompanhar a propriedade do dado. Estado global mutável também dificulta testes porque uma execução pode depender de outra.

Um método static não possui this. Para operar sobre uma instância específica, ele precisaria receber ou criar essa instância. Chamar uma função por meio do nome da classe torna essa relação visível e evita que uma sintaxe permitida esconda o fato de não haver despacho de instância naquele ponto.

17. Sobrecarga e sobrescrita respondem a perguntas diferentes

Sobrecarga oferece métodos com o mesmo nome e listas de parâmetros diferentes. A escolha usa as regras de tipos da chamada. Sobrescrita fornece uma implementação de um método de instância herdado; o objeto real pode determinar qual implementação será executada. Mudar apenas o tipo de retorno não cria uma sobrecarga válida.

Use @Override ao sobrescrever. Se a grafia ou a assinatura estiver incorreta, o compilador poderá apontar que você não está sobrescrevendo como pretendia. Sem a anotação, um método extra com nome semelhante pode compilar e nunca ser chamado pelo contrato que você esperava atender.

Também diferencie membros static, que não participam do mesmo despacho dinâmico dos métodos de instância. Evite aprender polimorfismo pela ideia vaga de que “o Java escolhe o método mais específico em tempo de execução” para qualquer chamada. O tipo da referência limita quais membros podem ser chamados; o objeto e as regras do membro determinam como aquela chamada válida se comporta.

18. Polimorfismo: preserve o contrato do código que chama

Uma interface pode representar uma capacidade usada por uma rotina. O chamador não precisa conhecer cada classe concreta se o contrato oferece a operação necessária. Isso permite acrescentar uma implementação sem reescrever um switch de tipos em cada ponto de uso. A vantagem depende de uma promessa comum real, não apenas de nomes iguais.

O método apresentar usa apenas Mensagem. Uma nova implementação precisa respeitar o significado de texto, incluindo as expectativas de quem o apresenta. Se uma implementação começar a pedir leitura no console enquanto as outras apenas devolvem uma string, a surpresa pode violar a expectativa do contrato mesmo que a assinatura compile.

Herança não é apenas um mecanismo para reaproveitar linhas. Se a subclasse exige condições que o chamador da superclasse não conhece, pode não ser uma substituição adequada. Quando o relacionamento é “usa uma capacidade”, composição costuma expressar a dependência de forma mais direta.

19. Composição e dependências explícitas em um exemplo pequeno

Um serviço de apresentação pode receber a capacidade de obter uma mensagem no construtor. Ele não precisa construir internamente sempre o mesmo tipo concreto. Isso é uma forma simples de fornecer uma dependência, sem exigir um container ou um framework. O código do exercício continua inteiro e rastreável em um arquivo.

O campo final impede trocar a referência depois da construção, mas não garante a imutabilidade de qualquer objeto recebido. O contrato da dependência continua importante. O nome é validado no ponto em que entra na operação; o chamador não precisa lembrar de limpá-lo em cada interface diferente.

Não crie uma interface para toda classe automaticamente. Ela se justifica quando o código precisa depender de uma capacidade estável, quando existem alternativas ou quando a fronteira melhora o teste e a compreensão. Para uma única função trivial, uma chamada direta pode ser a solução completa mais simples.

20. Igualdade de objetos e identidade não são intercambiáveis

Dois objetos podem representar o mesmo valor e ainda possuir identidades distintas. A implementação herdada de Object para equals compara identidade. Se uma classe representa um valor, pode precisar de uma definição de igualdade por conteúdo e de hashCode coerente. Alterar equals sem acompanhar o contrato de hashCode pode prejudicar consultas em coleções baseadas em hash.

Nem todo objeto deve ser comparado por todos os campos. Em um cadastro, uma identidade estável pode determinar a equivalência, enquanto nome e endereço mudam. Em um valor como uma coordenada imutável, os componentes podem definir igualdade. Decida pelo domínio e pelos usos da classe; não gere automaticamente uma regra sem avaliar o que ela significa.

Evite usar como chave de um mapa um objeto cujos dados usados em igualdade e hash mudam enquanto ele estiver armazenado. A posição lógica da chave depende desse contrato. O tema 11 detalha os casos; aqui, reconheça que estado, identidade e igualdade são escolhas que afetam mais do que a impressão de um objeto.

21. Lambdas e streams: operações sobre dados sem esconder seus efeitos

Uma lambda pode fornecer o comportamento exigido por uma interface funcional. Em uma stream, filter escolhe elementos, map transforma e uma operação terminal produz um resultado ou efeito. O pipeline pode ser preguiçoso: declarar operações intermediárias não significa que todo o trabalho já aconteceu. Uma stream consumida também não deve ser reutilizada como se fosse uma coleção guardada.

Separar os dados de origem do resultado filtrado ajuda a testar. Não escreva uma lambda que modifica a própria coleção que está sendo percorrida. E não troque um laço claro por uma cadeia apenas para parecer avançado: a escolha precisa tornar a transformação mais legível. Quando há controle de fluxo complexo, um laço pode ser a representação mais direta.

Sorted não significa que a coleção original tenha sido ordenada. Ele participa da sequência produzida pelo pipeline. Se o contrato exige preservar a origem, teste a origem depois da operação. Em paralelo, efeitos externos exigem cuidados adicionais; não acrescente parallel como uma promessa genérica de velocidade sem medir e entender as operações.

22. Testar uma classe sem depender da sua interface de entrada

Uma classe com uma operação bem definida pode ser testada por chamadas diretas. Crie o estado inicial, aplique a operação e compare o resultado com o contrato. Não use apenas a impressão final de um projeto grande como prova de cada regra. Um teste pequeno permite localizar a primeira decisão que não corresponde ao esperado.

Inclua o histórico quando o objeto for mutável: reservar uma vaga duas vezes não é o mesmo que chamar uma função pura com os mesmos argumentos. Verifique o estado antes e depois e teste uma operação inválida para assegurar que ela não deixou uma modificação parcial. Uma exceção após metade das atribuições pode proteger a mensagem de erro sem proteger o estado.

Não exponha campos apenas para facilitar o teste. Consultas que fazem parte da interface útil podem mostrar o estado relevante; o teste deve observar o comportamento prometido. Esse cuidado mantém a implementação livre para mudar sem exigir que todo teste conheça cada detalhe privado.

23. Prática orientada, possíveis soluções e revisão

  1. Instâncias: escreva a classe Contador e crie dois objetos. Incremente o primeiro duas vezes e o segundo uma. A saída deve ser A: 2 e B: 1. Depois, em uma cópia do exercício, compartilhe a mesma referência e explique a diferença.
  2. Passagem por valor: escreva o programa Caixa sem consultar o código. Depois de alterar, imprima o valor do objeto original. Explique por que a nova Caixa de valor 100 não substituiu a variável original do main.
  3. Contrato: implemente converter com validação de reais e cotação. Faça duas chamadas válidas e uma com cotação zero. O método não deve imprimir a quantia: a apresentação fica no main.
  4. Polimorfismo: acrescente uma terceira classe Mensagem que devolva “Pratique novamente”. Use o mesmo método apresentar. Não acrescente um teste de tipo para escolher a mensagem.
Possível solução: terceira implementação do contrato

O objeto criado é conhecido neste programa pequeno, mas a rotina de apresentação depende somente do contrato. A nova implementação não exige modificar a rotina. Se mensagens externas pudessem ser ausentes, preserve a validação de entrada usada no laboratório anterior.

Conferir o raciocínio sobre estado e chamadas

Os contadores independentes imprimem 2 e 1. Na Caixa, a mutação do objeto mantém valor 9 no original, enquanto a reatribuição do parâmetro não muda a referência do main. Na conversão, dividir 100 por 5 produz 20; cotação zero é recusada antes do cálculo. Uma implementação válida de Mensagem fornece o texto pela operação comum.
