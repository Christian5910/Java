1. O contrato de uma decisão: do enunciado à condição

Uma decisão correta começa antes do if. Escreva quais entradas são aceitas, quais resultados podem sair e quais condições separam os resultados. Imagine uma inscrição que exige idade mínima e autorização. Ter idade suficiente não substitui a autorização se a regra exigir ambas. A estrutura sintática é curta; o trabalho está em traduzir as palavras sem trocar o sentido.

Ao estudar este capítulo, leia primeiro a regra em português. Separe validação de classificação: uma nota negativa não é uma nota baixa válida; uma entrada ilegível não é zero. Depois desenhe os caminhos e escolha entradas que percorram cada um deles. Só então escreva o programa. Essa ordem permite avaliar a solução sem depender de ela parecer funcionar com o primeiro exemplo.

Você precisará reconhecer boolean, comparações, Scanner e a diferença entre texto e número. Ao terminar, deverá escrever condições compostas, organizar intervalos sem sobreposição indevida, escolher entre if e switch e verificar os limites da regra. Os exemplos usam Java 17 sem recursos preview; uma sintaxe encontrada em documentação de outra versão precisa ser conferida antes de ser copiada.

2. Condições precisam produzir booleanos

Uma estrutura condicional escolhe quais instruções executar. O if avalia uma expressão booleana e executa o bloco quando ela é verdadeira. Um else fornece o caminho alternativo. Em Java, um número como 1 não é usado diretamente como verdadeiro: a condição deve ter tipo boolean. Para comparar idade com um limite, escreva idade >= 18.

Use chaves mesmo quando o bloco contém uma única instrução. Assim, acrescentar outra operação não muda silenciosamente o alcance da condição. Um ponto e vírgula logo depois de if (condicao) cria uma instrução vazia e pode deixar o bloco seguinte sem a proteção pretendida. A indentação ajuda a leitura, mas são as chaves e a sintaxe que determinam o fluxo.

double media = 7.0;
if (media >= 7.0) {
    System.out.println("Aprovado");
} else {
    System.out.println("Recuperação");
}

Para esse enunciado, o valor exatamente igual a 7 já está aprovado. Trocar >= por > altera a regra no limite. Um teste com 9 não revelaria o problema; testar 6.9, 7.0 e 7.1 permite separar os dois comportamentos. O resultado esperado deve vir da regra, antes de observar o que o código faz.

3. Vários ifs e uma cadeia if/else if

Vários if independentes podem executar vários blocos. Em uma cadeia if / else if / else, o primeiro caminho verdadeiro encerra a escolha. Essa diferença aparece na classificação de notas: se você deseja uma única categoria, organize condições sem sobreposição indevida. Se deseja registrar avisos independentes, como atraso e documentação incompleta, vários testes separados podem ser adequados.

if (media < 0 || media > 10) {
    System.out.println("Nota inválida");
} else if (media >= 7) {
    System.out.println("Aprovado");
} else if (media >= 5) {
    System.out.println("Recuperação");
} else {
    System.out.println("Revisar conteúdo");
}

Os limites intermediários desse exemplo são uma regra de exercício, não uma política universal de avaliação. Quando o segundo else if é alcançado, já sabemos que a média é menor que 7; por isso, media >= 5 cobre o intervalo de 5 incluído a 7 excluído. Se você testar media >= 5 antes de media >= 7, valores altos entrarão na primeira condição e a segunda categoria não será alcançada.

4. Condições compostas e negação

Uma regra pode exigir aprovação por nota e presença: media >= 7 && presenca >= 75. Usar || permitiria aprovação quando apenas uma exigência fosse atendida, o que é outra regra. Parênteses ajudam a separar condições compostas. Prefira uma expressão que o leitor consiga relacionar ao enunciado, mesmo que a linguagem permita retirar alguns parênteses.

A negação de “usuário correto e senha correta” é “usuário incorreto ou senha incorreta”. Essa relação permite escrever a condição de recusa de um login. As leis de De Morgan ajudam a conferir: !(a && b) equivale a !a || !b, e !(a || b) equivale a !a && !b. Experimente as quatro combinações booleanas para verificar sem depender de memorização.

5. Resolver o salário semanal

Considere este enunciado: abaixo de 40 horas, o pagamento é de R$ 15 por hora; a partir de 40 horas, são R$ 600 mais R$ 21 por hora excedente. Em 40 horas, o resultado é R$ 600. Horas negativas devem ser rejeitadas. Os valores são dados de um exercício de função por partes e não representam regras trabalhistas gerais.

double horas = 45;
if (horas < 0) {
    System.out.println("Horas inválidas");
} else {
    double salario;
    if (horas <= 40) {
        salario = horas * 15;
    } else {
        salario = 600 + (horas - 40) * 21;
    }
    System.out.printf(java.util.Locale.US, "Salário: R$ %.2f%n", salario);
}

Para 45 horas, as cinco horas excedentes acrescentam R$ 105 à base, chegando a R$ 705. Teste -1, 0, 39, 40 e 41. Se uma condição para horas acima de 71 vier depois de um ramo que já aceita todas as horas acima de 40, ela nunca será alcançada. Uma faixa específica deve ser verificada antes de uma faixa que a contenha, ou as condições precisam descrever intervalos sem sobreposição.

6. Switch tradicional

switch seleciona caminhos conforme o valor de uma expressão. Ele é conveniente em menus com opções conhecidas. Na forma tradicional, cada case marca um ponto de entrada. break encerra o switch; sem ele, a execução pode continuar pelos casos seguintes, comportamento chamado fall-through. default trata valores que não combinaram com os rótulos.

int opcao = 2;
switch (opcao) {
    case 1:
        System.out.println("Consultar saldo");
        break;
    case 2:
        System.out.println("Depositar");
        break;
    default:
        System.out.println("Opção inválida");
}

Na referência Java 17, esse tipo de switch aceita, entre outros, int, char, String e enums; não aceita diretamente double como seletor. Os casos precisam respeitar o tipo e as regras de constantes. Para testar intervalos de valor, como faixas de nota, if / else if costuma expressar melhor a regra. As extensões de switch de versões posteriores não são pressupostas nesta apostila.

7. Switch com seta e expressão switch

A forma moderna usa case ... ->. Essa sintaxe está disponível na versão de referência e evita o fall-through da forma com dois-pontos. Um switch também pode produzir um valor. Nesse caso, todos os caminhos possíveis precisam ser cobertos; em um seletor inteiro, default normalmente cumpre essa função. Não misture as duas formas de rótulo no mesmo bloco de switch.

int opcao = 1;
String estacao = switch (opcao) {
    case 1 -> "Primavera";
    case 2 -> "Verão";
    case 3 -> "Outono";
    case 4 -> "Inverno";
    default -> "Estação desconhecida";
};
System.out.println(estacao);

Os números de 1 a 4 identificam opções do exercício, não meses do ano nem um calendário climático. Se um ramo de uma expressão switch precisa de várias instruções, use um bloco e yield para fornecer seu resultado. return sai do método inteiro; yield fornece o valor da expressão switch. Para uma decisão curta de dois valores, o ternário condicao ? valorSeVerdadeiro : valorSeFalso pode ser suficiente.

8. Enumerações para opções conhecidas

Um enum representa um conjunto definido de constantes com um tipo próprio. Ele ajuda quando estados ou opções têm significado no programa, como uma tarefa PENDENTE ou CONCLUIDA. Usar esse tipo evita espalhar números sem explicação e reduz erros de grafia em comparações de texto. A entrada de um usuário ainda precisa ser validada antes de virar um estado do domínio.

enum Situacao {
    PENDENTE, EM_ANDAMENTO, CONCLUIDA
}

public class Main {
    public static void main(String[] args) {
        Situacao atual = Situacao.EM_ANDAMENTO;
        String mensagem = switch (atual) {
            case PENDENTE -> "Ainda não começou";
            case EM_ANDAMENTO -> "Estudo em andamento";
            case CONCLUIDA -> "Estudo concluído";
        };
        System.out.println(mensagem);
    }
}

Praticar este programa no Playground

A saída é Estudo em andamento. Troque a constante e preveja a nova mensagem. Os casos cobrem todas as constantes desse tipo; não há leitura de entrada no exemplo. Situacao.valueOf("CONCLUIDA") exige o nome exato e lança uma exceção se ele não existir. Um texto arbitrário não vira enum automaticamente. Evite gravar ordinal() como um código de negócio permanente, pois reorganizar as constantes muda suas posições. Para testar, copie o programa para o editor de decisões e exporte o rascunho anterior se quiser preservá-lo.

9. Verificar a calculadora

Uma calculadora deve separar leitura, escolha da operação e cálculo. Cada caso precisa aplicar o operador correto. Um método que promete devolver um valor deve fazê-lo em todos os caminhos que terminam normalmente, ou lançar uma exceção apropriada. Mantenha uma única instância de Scanner para coordenar as leituras. Primeiro confira a compilação; depois teste cada operação e a divisão por zero.

Ao testar divisão, inclua divisor zero. Ao testar o menu, inclua um texto de operação desconhecido. Se o programa pede confirmação, defina claramente o significado de continuar ou encerrar: um booleano chamado continuar deve retornar verdadeiro quando a repetição deve continuar. Pratique o salário e a calculadora com switch, alterando uma entrada de cada vez.

10. Tabela de decisão: torne visíveis as combinações

Uma tabela de decisão lista condições e ações. Para uma regra com nota suficiente e presença suficiente, existem quatro combinações booleanas. Testar somente uma aprovação e uma reprovação deixa combinações sem conferir. Escreva: nota suficiente e presença suficiente aprovam; se uma das exigências faltar, o resultado deve recusar. Se a condição implementada usar ou em vez de e, as duas combinações intermediárias revelarão o defeito.

Essa tabela pressupõe entradas válidas. Acrescente outra etapa para média fora de 0 a 10, presença fora de 0 a 100 e valores não finitos. Não misture uma entrada inválida com um resultado negativo da regra. Um aviso específico permite corrigir a informação; uma simples reprovação poderia esconder um cadastro incorreto.

Quando houver mais condições, a tabela cresce. Não use esse crescimento como motivo para abandonar a regra: procure condições dependentes e estados impossíveis, documente-os e reduza apenas o que o domínio permite. Para regras pequenas, quatro ou oito linhas no papel frequentemente revelam um erro antes da primeira compilação.

11. Curto-circuito e a ordem de validação

Em uma condição composta, a ordem pode impedir uma operação inválida. A expressão nome != null && !nome.isEmpty() só consulta o tamanho se houver uma referência. Uma consulta a uma posição de array pode ser protegida por índice não negativo e menor que length. A proteção precisa aparecer antes do acesso, pois Java avalia os operandos da esquerda para a direita.

Não substitua && por & apenas por achar a grafia menor. Com booleanos, a segunda forma avalia os dois lados e pode atingir o acesso que você pretendia evitar. Também não dependa de uma chamada de gravação no lado direito: por curto-circuito, ela pode não acontecer. Prefira calcular a regra sem efeitos externos e executar a ação no bloco correspondente.

A negação deve respeitar o mesmo cuidado. “Não está entre 0 e 10” significa valor menor que 0 ou maior que 10. Escrever menor que 0 e maior que 10 cria uma condição impossível para um número comum. Confira esse tipo de erro usando exemplos concretos nos dois lados do intervalo.

12. Intervalos: pertencimento, prioridade e fronteiras

Considere três categorias de um exercício: abaixo de 5, de 5 até antes de 7 e de 7 em diante. Você pode verificar os limites em ordem crescente com comparações menores que. Pode também começar pela faixa mais alta e descer. O que não funciona é testar primeiro uma faixa abrangente que já aceita tudo o que um ramo posterior pretendia separar.

Os pontos exatos merecem testes próprios. Para cada fronteira, experimente imediatamente abaixo, exatamente nela e imediatamente acima, respeitando o domínio. Para idade inteira, 17, 18 e 19 são casos úteis. Para uma nota decimal, 6.99, 7 e 7.01 ajudam a perceber a inclusão do limite. A precisão do tipo não define por você como uma política de arredondamento deve funcionar.

Os retornos antecipados tornam cada exclusão visível. Ao chegar à última linha, o método já excluiu entradas inválidas e as duas faixas anteriores. Não há necessidade de repetir todas as comparações. O teste percorre cada limite relevante e demonstra por que NaN precisa de validação explícita: comparações ordenadas não o colocam automaticamente fora de um intervalo.

13. Blocos, escopo e a associação do else

O else pertence ao if compatível mais próximo que ainda não tenha else. Uma indentação bonita não muda essa associação. Use chaves para mostrar o grupo de instruções e evitar que uma alteração posterior acrescente uma linha fora da condição. Um ponto e vírgula depois da condição cria uma instrução vazia; o bloco seguinte pode executar sempre, apesar da indentação.

Uma variável criada dentro de um bloco pertence àquele escopo. Se precisar produzir um resultado para usar depois, declare-o antes e atribua em todos os caminhos válidos ou escreva um método que devolva o resultado. Não inicialize um resultado com zero apenas para calar o compilador quando zero não é uma resposta válida para todos os caminhos.

Na revisão, pergunte o que acontece quando cada condição é falsa. Muitos erros ficam escondidos porque o autor só seguiu a leitura pelo caminho verdadeiro. Retire temporariamente os textos das mensagens e desenhe apenas as chaves e setas. Isso expõe a estrutura que realmente será executada, sem depender da apresentação visual do editor.

14. Guardas: rejeitar cedo e manter a regra visível

Uma guarda verifica um requisito e encerra o caminho quando ele falha. Em um método de cálculo, validar argumentos no início evita colocar toda a operação dentro de vários níveis de if. Isso não significa colocar return em qualquer lugar: cada encerramento deve corresponder a um motivo claro e impedir que um resultado parcial seja usado como completo.

Há também uma escolha de interface. Um programa de console pode imprimir um aviso e retornar de main. Um método reutilizável costuma devolver um resultado documentado ou lançar uma exceção de contrato. Se ele imprimir e ainda devolver zero para uma entrada inválida, quem chamou pode confundir falha com um cálculo legítimo. Você verá exceções em mais detalhes adiante; agora reconheça que a estratégia de falha precisa ser explícita.

A clareza não depende apenas da quantidade de linhas. Uma condição muito longa com vários efeitos pode ser menor no arquivo e mais difícil de revisar. Dê nomes intermediários quando eles expliquem conceitos reais, como notaValida e presencaSuficiente. Evite nomes que apenas repitam uma parte arbitrária da sintaxe.

15. Switch em Java 17: quando escolhe uma ação e quando produz um valor

Um switch statement escolhe instruções. Uma expressão switch produz um valor que será usado em uma atribuição, retorno ou outra expressão. Na forma com seta, não há a passagem automática para o próximo case. Quando o ramo precisa de várias instruções para calcular seu resultado, um bloco pode usar yield. Isso é diferente de return, que encerra o método.

O default deste exercício representa uma escolha desconhecida que produz zero unidades, por decisão do enunciado. Em uma operação real em que zero pudesse ser confundido com sucesso, prefira uma falha explícita ou uma apresentação diferente. Não copie a política de fallback sem copiar também o significado que a justifica.

Um seletor String nulo não é atendido pelo default de um switch comum de Java 17: valide a referência antes. Os tipos admitidos e as formas de case dependem da versão. Não use neste capítulo um exemplo moderno com case null como se ele fosse automaticamente compatível com o compilador configurado para 17. A versão é parte do contrato executável.

16. Laboratório completo: uma calculadora com entrada conferida

O contrato é pequeno: receber dois números finitos e uma operação entre +, -, * e /; recusar divisor zero; não apresentar infinito como resposta calculada. A entrada usa ponto decimal e pode ser fornecida em linhas separadas. O programa encerra após uma operação. Um menu repetido pertence ao próximo tema.

Teste depois 10, 0 e /; 10, 4 e ?; apenas um número; texto no lugar do segundo número; e dois números grandes cuja multiplicação exceda a faixa de double. Entradas finitas não garantem resultado finito. A conferência final evita apresentar esse resultado como se atendesse ao contrato.

17. Estado conhecido não é apenas um número de menu

Um enum é útil quando as opções pertencem ao domínio, como estado de uma tarefa. O menu pode apresentar 1 e 2, mas o restante do programa pode trabalhar com nomes como PENDENTE e CONCLUIDA. Faça a conversão da entrada em um ponto controlado. Isso evita espalhar números cujo significado cada método precisa adivinhar.

Não confunda o número exibido ao usuário com ordinal. Ordinal é a posição da constante na declaração; mover uma constante altera essa posição. Se um arquivo ou protocolo exige códigos permanentes, declare e valide esses códigos explicitamente. Uma expressão switch sobre um enum também exige manutenção quando o conjunto de estados muda: percorra os usos e os testes, não apenas a declaração.

Nem toda divergência de texto deve ser normalizada. Um comando de menu pode aceitar maiúsculas e espaços externos; uma senha pode exigir comparação exata. Primeiro defina a regra de entrada, depois transforme. Conservar um texto de exibição separado de uma chave técnica ajuda a preservar o que a pessoa informou.

18. Revisar decisões com testes que distinguem regras

Um teste útil deve separar uma implementação correta de uma versão plausível, mas errada. Se a aprovação começa em 7, um teste com 9 não distingue maior que de maior ou igual. Se duas condições precisam ser satisfeitas, um caso com ambas verdadeiras não distingue e de ou. Escolha ao menos uma entrada em que as duas implementações dariam respostas diferentes.

Escreva os resultados esperados a partir do contrato, antes de observar a saída atual. Copiar a saída do programa para o teste pode preservar o próprio erro que você tentava descobrir. Para números, calcule uma referência por outro caminho. Para classificações, marque a faixa correspondente na tabela de decisão.

Ao corrigir um ramo, rode novamente os casos dos ramos vizinhos. Uma troca na ordem dos ifs pode resolver uma categoria e capturar indevidamente outra. Registre em poucas linhas qual defeito cada caso evita. Você não precisa criar uma ferramenta complexa para isso: uma pequena lista de entradas e saídas já torna a revisão repetível.

19. Prática progressiva, resoluções e critérios de domínio

  1. Classificação: implemente classificar com as três faixas apresentadas. Use um array contendo 4.99, 5, 6.99, 7 e 10 e imprima uma resposta por elemento. Acrescente -1 e NaN e confira que sejam recusados antes da classificação.
  2. Presença: receba média e presença, nessa ordem. Aceite apenas média finita entre 0 e 10 e presença finita entre 0 e 100. Imprima Dados inválidos para entradas fora do contrato. Para as demais, exija média mínima 7 e presença mínima 75. Teste as quatro combinações da tabela.
  3. Calculadora: escreva o laboratório sem consultar a solução. Teste cada operação e os caminhos de recusa. Registre por que default não deve fazer uma soma como substituto para operação desconhecida.
  4. Diagnóstico: crie uma cópia da classificação e troque nota < 5 por nota <= 5. Qual entrada revela a diferença? Depois restaure. Faça o mesmo com o limite de aprovação.
Possível solução: nota e presença

Para a versão com entrada, leia os valores com Scanner e passe-os ao método. Separar a decisão da leitura permite testar o contrato sem reproduzir todo o console em cada chamada.

Conferir as fronteiras e explicar a escolha

As notas 4.99, 5, 6.99, 7 e 10 resultam em Revisar, Recuperação, Recuperação, Aprovado e Aprovado. A nota 5 distingue < de <= na primeira faixa. A nota 7 distingue o início da aprovação. Não existe escolha universal para essas fronteiras: neste exercício elas vêm do enunciado.

Avance quando conseguir justificar cada caminho e encontrar um teste que o percorra. Se estiver decorando a forma do if sem relacioná-la à regra, volte à tabela. O próximo capítulo repete operações; as condições estudadas aqui serão a forma de controlar quando parar.
