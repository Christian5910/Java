1. Do Java de desktop ao aplicativo Android

No Android, você escreve classes Java que utilizam as APIs do SDK e uma interface que segue o ciclo de vida da plataforma. O build transforma fontes e recursos no pacote instalado. O dispositivo executa a aplicação no ambiente Android, com isolamento, permissões e limites próprios. A JVM que executa o Gradle no computador de desenvolvimento tem uma função diferente do runtime do aplicativo no aparelho.

O primeiro laboratório usa Views descritas em XML e uma Activity Java. A tela recebe uma nota, apresenta a situação e preserva o resultado numa recriação simples. Ele foi preparado com versões fixadas: JDK 17 para o build, Gradle 8.9, Android Gradle Plugin 8.7.3, compileSdk e targetSdk 35, minSdk 23. Essas versões atendem à reprodução do exercício; publicação em loja exige conferir requisitos atuais.

As instruções completas e todos os fontes estão no ZIP abaixo. Não há dependência de arquivos privados nem de uma chave de serviço. O aplicativo não pede acesso à internet. O teste isolado da regra pode executar no JDK local; a interface, a instalação e a rotação precisam de Android Studio com emulador ou um dispositivo adequado.

2. JDK, Gradle e SDK precisam combinar

O JDK executa ferramentas do build. Gradle coordena tarefas, o plugin Android acrescenta tarefas e regras específicas, e o SDK fornece APIs e ferramentas de compilação. Uma combinação incompatível pode falhar antes de compilar seu primeiro arquivo Java. Confira a documentação de JDKs no build Android e as notas do plugin 8.7 para o laboratório fixado.

No Android Studio, abra a pasta que contém settings.gradle. Selecione JDK 17 para o Gradle, instale SDK Platform 35 e use Gradle 8.9 local conforme o LEIA-ME. O pacote não traz um Gradle Wrapper; por isso, a distribuição local precisa estar instalada e selecionada. No terminal, gradle --version deve confirmar a versão usada antes de assembleDebug.

compileSdk determina as APIs disponíveis na compilação. minSdk determina o nível mínimo que você declara atender. targetSdk informa o nível de comportamento para o qual o aplicativo foi preparado e participa das políticas da plataforma. Chamar uma API posterior ao minSdk exige uma verificação de disponibilidade ou uma alternativa compatível. Escrever sintaxe Java 17 no projeto não torna todas as APIs Java SE 17 disponíveis em qualquer aparelho.

3. Ler a estrutura do projeto

settings.gradle declara repositórios e inclui o módulo app. O build.gradle da raiz fixa a versão do plugin. O build do módulo declara namespace, SDKs, identificador da aplicação e opções de compilação. O manifesto informa a Activity inicial, a configuração do aplicativo e os componentes publicados. A Activity de entrada possui exported explícito para o launcher conseguir abri-la.

Os fontes ficam em app/src/main/java e os recursos em app/src/main/res. Strings apresentadas na tela ficam em values/strings.xml para facilitar revisão e tradução. O layout activity_main.xml contém ScrollView, LinearLayout, rótulo, campo, botão e resultado. A classe R é gerada a partir dos recursos; ela não deve ser escrita manualmente.

O namespace identifica o espaço de nomes de recursos e classes geradas. applicationId identifica o aplicativo instalado. Eles podem coincidir no exercício e ter papéis diferentes no build. Mover um arquivo entre pacotes exige revisar a declaração package e as referências relevantes. Uma falha de recurso pode fazer R parecer ausente; leia a primeira falha XML antes de tentar criar uma classe R própria.

4. Montar a tela com Views XML

O layout usa largura disponível e altura adaptada ao conteúdo. Um ScrollView permite percorrer os controles quando teclado, escala de fonte ou orientação reduzem a área visível. O campo recebe inputType numérico decimal com sinal, mas a regra ainda valida tudo que chega: teclado e preenchimento por outros meios não garantem a faixa de notas.

O projeto também trata os insets das barras do sistema, do recorte e do teclado em Android 15 ou posterior. Esse ajuste evita que controles sejam cobertos quando o targetSdk 35 ativa o desenho de ponta a ponta. Consulte o guia de insets para Views ao adaptar a tela. TextView com labelFor associa o nome do campo à entrada. O botão e o campo possuem altura mínima de 48dp no exemplo. A mensagem usa uma região acessível de atualização suave. Não atribua uma descrição redundante a cada texto que já é legível pela tecnologia assistiva; confira a leitura real com TalkBack.

Na Activity, setContentView infla o layout e findViewById encontra os controles por id. Faça a busca depois de instalar o conteúdo correspondente. Um id único possibilita localizar o controle e contribui para mecanismos de restauração de estado da hierarquia. O código a seguir mostra a ligação central, dentro de onCreate, com os recursos disponíveis no pacote.

setContentView(R.layout.activity_main);
EditText nota = findViewById(R.id.nota);
TextView resultado = findViewById(R.id.resultado);
findViewById(R.id.conferir).setOnClickListener(view -> {
    try {
        boolean aprovado = Regra.aprovado(nota.getText().toString());
        resultado.setText(aprovado ? R.string.aprovado : R.string.recuperacao);
        nota.setError(null);
    } catch (IllegalArgumentException erro) {
        nota.setError(getString(R.string.invalida));
        resultado.setText(R.string.invalida);
    }
});

5. O ciclo de vida da Activity

A Activity passa por estados de criação, início, retomada, pausa, parada e destruição conforme a interação com o sistema. onCreate prepara a instância; onStart e onResume acompanham sua entrada em primeiro plano. onPause e onStop ajudam a suspender recursos associados à visibilidade. onDestroy pode ocorrer numa recriação, mas não deve ser tratado como uma garantia de salvamento de todos os dados antes de o processo desaparecer.

Uma mudança de configuração pode destruir a instância e criar outra. Se você guardar o resultado apenas num campo da Activity, a nova instância começa sem esse valor. O laboratório salva o texto do resultado em onSaveInstanceState e o recupera quando recebe um Bundle. O campo de entrada tem id e usa os mecanismos da hierarquia de Views para seu estado de edição.

Bundle é apropriado para estado pequeno necessário à reconstrução da interface. Ele não substitui armazenamento persistente de registros nem deve carregar grandes coleções de objetos. O guia do ciclo de vida descreve as transições. Diferencie recriação da tela, morte do processo e remoção definitiva do aplicativo ao planejar o que precisa sobreviver.

6. Thread principal, recursos e permissões

A thread principal processa a interação e os eventos da interface. Não faça acesso de rede ou processamento pesado dentro do listener do botão. O cálculo de uma nota é curto. Consultas externas precisam de trabalho fora da thread principal, resultado vinculado à tela ativa e tratamento de cancelamento e falha.

O laboratório não usa câmera, localização nem internet, portanto não declara essas permissões. Quando acrescentar uma capacidade, identifique se ela exige declaração no manifesto e autorização em tempo de execução. A recusa deve deixar a aplicação num estado compreensível, com uma alternativa quando possível. Solicite o acesso no momento em que a pessoa entende sua finalidade.

Não armazene senha de servidor dentro do APK. O pacote pode ser inspecionado e seus recursos podem ser extraídos. Configuração de endereço e credenciais possuem ameaças diferentes. Dados sensíveis exigem uma política de armazenamento, transmissão e sessão adequada ao aplicativo. O tema 21 continua essa separação ao introduzir repositórios e conectividade.

7. Compilar e verificar o primeiro aplicativo

Com os requisitos instalados, execute gradle :app:assembleDebug ou use o build do Android Studio. O APK de depuração fica em app/build/outputs/apk/debug. A compilação gera um pacote; abrir a aplicação no emulador ou dispositivo é uma verificação adicional. Consulte o LEIA-ME se o plugin solicitar uma versão de Build-Tools diferente da já instalada.

O arquivo TestesRegra.java executa nove verificações da função Regra.aprovado sem depender do SDK. Ele confere aprovação, recuperação e recusas. Esse teste ajuda a isolar uma falha de domínio de uma falha de layout. A execução bem-sucedida não comprova restauração de tela, adaptação de tamanho, instalação nem funcionamento numa versão específica do Android.

8. Prática: observar recriação e corrigir entradas

Abra o aplicativo, informe 7,5 e confira a aprovação. Gire a tela e confirme a preservação da entrada e do resultado. Repita com 6 e com um campo vazio. Aumente a fonte, abra o teclado e confira se todos os controles continuam alcançáveis. Use TalkBack para identificar o campo e ouvir a mudança de resultado.

Como evolução, acrescente um nome com um recurso de texto próprio e preserve seu rascunho numa recriação. Não prometa persistência depois de fechamento forçado. Entregue os resultados de teste com a versão do emulador ou aparelho utilizado e explique quais dados estão no Bundle, quais estão nos controles e quais não são gravados.

A configuração sourceCompatibility Java 17 disponibiliza Swing num aplicativo Android?

Não. A configuração da linguagem não substitui as APIs da plataforma. A tela deste projeto usa Views do Android; o reaproveitamento deve se concentrar em regras e bibliotecas compatíveis com o destino.
