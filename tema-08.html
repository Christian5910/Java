1. Construir é estabelecer um estado inicial que faça sentido

Criar um objeto não é apenas reservar espaço e preencher campos. O programa passa a ter uma referência para uma entidade que promete certas regras. Um círculo precisa de um raio permitido; um produto precisa de um nome; uma reserva precisa de uma capacidade coerente. Se o objeto só ficar válido depois de uma sequência de setters que alguém talvez esqueça, as operações seguintes terão de lidar com um estado incompleto.

Este capítulo continua o estudo de classes e referências. A meta é escrever construtores que recebam o necessário, concentrem validação e não tornem disponível um estado contraditório. Você deverá distinguir o construtor padrão gerado pelo compilador de uma forma sem argumentos declarada por você, explicar o encadeamento e justificar até onde uma cópia deve ser independente.

Os exemplos adotam Java 17. Regras de versões posteriores não mudam automaticamente os projetos configurados para essa versão. No Playground, os programas completos deste capítulo cabem em um Main.java com classes auxiliares sem public. Exemplos que exigem arquivos separados ou recursos adicionais indicam essa necessidade no próprio texto.

2. Definir como um objeto começa

Um construtor participa da inicialização de um objeto. Ele tem o mesmo nome da classe e não declara tipo de retorno, nem mesmo void. Celular(String modelo) pode ser um construtor de Celular; void Celular(String modelo) é um método comum. A expressão new cria o objeto e aciona a inicialização correspondente. O construtor pode atribuir atributos e validar argumentos para evitar que o objeto comece em um estado incoerente.

A apostila chama o construtor de método especial para introduzir a ideia. Na linguagem, construtores possuem regras próprias e não são métodos comuns: não são herdados e não podem ser chamados como uma operação qualquer com ponto. Esse detalhe importa quando você começa a usar sobrecarga e herança.

3. Construtor sem argumentos e construtor padrão

Se uma classe comum não declara construtor, o compilador fornece um construtor padrão. Ele não é criado pela JVM em tempo de execução. Depois que você declara qualquer construtor, o compilador não acrescenta automaticamente aquele sem argumentos. Se precisar das duas formas, declare as duas. Uma classe com apenas Celular(String modelo) não aceita new Celular() sem outra declaração correspondente.

class Celular {
    String modelo;
    int bateria;

    Celular(String modelo) {
        this.modelo = modelo;
        this.bateria = 100;
    }
}

public class Main {
    public static void main(String[] args) {
        Celular aparelho = new Celular("Modelo de estudo");
        System.out.println(aparelho.modelo + ": " + aparelho.bateria);
    }
}

this.modelo identifica o atributo do objeto atual; modelo identifica o parâmetro nesse escopo. Sem a distinção, modelo = modelo; apenas reatribui o parâmetro a ele mesmo e deixa o atributo com o valor anterior. Quando não há conflito de nomes, o uso de this pode ser opcional, mas a referência explícita ajuda a acompanhar a inicialização.

4. Valores iniciais dos atributos

Antes das atribuições feitas pelo seu código, campos de instância recebem valores padrão: zero para tipos numéricos, false para booleano, '\u0000' para char e null para referências. Um caractere padrão não é um texto vazio. Variáveis locais não recebem essa autorização de leitura automática: precisam de atribuição antes do uso. Os elementos de arrays, por sua vez, também são inicializados com valores padrão.

Esses padrões não necessariamente atendem ao domínio. Um saldo inicial zero pode ser aceitável, mas um título nulo pode não ser. O construtor deve receber ou estabelecer as informações obrigatórias. Exigir que o chamador lembre de executar vários setters depois de new pode deixar períodos em que o objeto está incompleto e sujeito a erros.

5. Sobrecarga e encadeamento

class Circulo {
    private double raio;
    private String cor;

    Circulo() {
        this(1.0, "azul");
    }

    Circulo(double raio, String cor) {
        if (!Double.isFinite(raio) || raio <= 0) {
            throw new IllegalArgumentException("Raio deve ser positivo e finito");
        }
        this.raio = raio;
        this.cor = cor;
    }

    double area() {
        return Math.PI * raio * raio;
    }
}

Os dois construtores têm listas de parâmetros diferentes. O construtor sem argumentos chama o outro com valores de referência usando this(...), concentrando a validação e a atribuição. Na versão adotada, essa chamada precisa ser a primeira instrução do construtor. Não crie uma cadeia circular em que um construtor chama outro e volta a chamar o primeiro.

new Circulo() inicia com raio 1.0; new Circulo(2.0, "verde") usa raio 2.0. A área do segundo é quatro vezes a do primeiro, pois o raio é elevado ao quadrado. O valor de Math.PI evita repetir uma aproximação manual de pi em cada objeto. A cor não altera a área nesse modelo e poderia ser validada separadamente se a regra exigisse um conjunto de cores.

6. Validar antes de tornar o estado disponível

O exemplo rejeita raio não positivo e valores não finitos. O método Double.isFinite ajuda a excluir NaN e infinito, que passariam por algumas verificações ingênuas. Uma comparação simples raio <= 0 não reconhece NaN como um valor válido ou inválido da forma esperada: comparações ordenadas com ele retornam falso. Para dados de entrada, valide o significado exigido pelo programa.

throw new IllegalArgumentException(...) informa que um argumento não atende ao contrato. O código chamador pode tratar essa exceção para apresentar uma mensagem e permitir correção. Apenas imprimir “valor inválido” e continuar atribuindo o mesmo valor não protege o estado. O construtor deve estabelecer claramente o objeto válido ou interromper sua criação com a falha apropriada.

7. Construtores e herança

Uma subclasse precisa inicializar a parte herdada do objeto. Na referência Java 17, super(...) chama um construtor da superclasse como primeira instrução. Quando não há chamada explícita a outro construtor, o compilador tenta usar super(). Se a superclasse não oferecer um construtor sem argumentos acessível, a subclasse precisa informar os argumentos em uma chamada explícita.

Construtores não são sobrescritos. Uma subclasse pode definir seus próprios construtores, com nomes iguais ao nome da própria subclasse. Isso difere de um método de instância com @Override. Ao revisar, separe o processo de construção das operações que serão chamadas depois que o objeto existir.

8. Construtor de cópia e limites da cópia

Um construtor de cópia recebe outro objeto do mesmo tipo e inicializa uma nova instância com os valores escolhidos. Você precisa implementá-lo: Java não fornece esse construtor automaticamente para classes comuns. Defina como tratar uma origem nula. Copiar campos primitivos produz valores independentes; copiar uma referência de array ou lista continua compartilhando o objeto se nenhuma estrutura nova for criada.

Suponha que um cadastro possua um nome e uma lista de telefones. Copiar a string do nome é adequado para compartilhar seu conteúdo imutável. Para impedir que uma alteração na lista original modifique a cópia, crie outra lista. Se os elementos dessa lista forem objetos mutáveis, a independência desses elementos exigirá outra decisão de cópia. O contrato deve dizer até onde vai essa separação. Relacione esse cuidado ao boletim com cópia defensiva antes de oferecer uma operação de duplicação.

9. Erros comuns no exercício

Um erro frequente é declarar um método com o nome da classe e void e esperar que seja executado automaticamente no new. Outro é criar um construtor com argumentos e continuar chamando a forma vazia. Também aparece a atribuição do parâmetro a ele mesmo por falta de this. Cada caso pode ser observado com um atributo que será impresso logo após a criação.

A visibilidade do construtor controla quem pode utilizá-lo. Uma classe pública com construtor sem modificador pode ser visível fora do pacote enquanto aquele construtor não é acessível ali. Nome de classe, lista de parâmetros e modificador precisam ser examinados em conjunto ao investigar uma falha de instanciação.

10. Prática orientada

Crie um círculo com raio padrão e outro com raio 2.0. Compare suas áreas, depois tente criar raios 0 e -1 e observe a falha de validação. Acrescente uma sobrecarga que receba somente o raio e delegue para o construtor principal com uma cor definida. Teste se a regra continua concentrada em um lugar. Ao revisar, diferencie o que o compilador fornece do que você escreveu explicitamente.

Abrir a atividade de construtores. Para a distinção entre construtor declarado e padrão, consulte as regras de construtores da especificação Java.

11. O contrato do objeto começa pelos estados permitidos

Antes de escrever o construtor, liste o que precisa ser verdade depois que ele termina. Para um produto simples: nome não nulo, nome não vazio após remover espaços externos e quantidade não negativa. Para um círculo: raio positivo e finito. Essas afirmações são invariantes do modelo; as demais operações também deverão preservá-las quando houver mutação.

Nem todo valor padrão da linguagem é um valor padrão do domínio. Zero pode representar uma quantidade vazia válida, mas um prazo zero pode não representar uma entrega válida. Não confunda “o campo foi inicializado” com “o objeto atende à regra”. A primeira afirmação fala do mecanismo da linguagem; a segunda depende do problema.

Um construtor deve validar os dados de que precisa sem tentar adivinhar informações ausentes. Se a regra não permite nome vazio, substituí-lo silenciosamente por “Sem nome” pode esconder um erro de cadastro. Se o domínio permite essa ausência, represente-a explicitamente e documente quais operações continuam disponíveis.

12. Ordem de inicialização: valores padrão, parte herdada e corpo

Na perspectiva do programa Java, campos recebem valores padrão antes de inicializações explícitas. A construção também envolve a parte da superclasse. Só depois de retornar dessa inicialização a parte da subclasse executa seus inicializadores de instância e o restante do seu construtor. Essa ordem importa quando um método chamado cedo demais tenta observar dados da subclasse.

O exemplo não depende de uma chamada a método sobrescrito durante a construção. Ele apenas torna a ordem observável por mensagens. Não generalize a ordem das linhas do arquivo como se todos os campos de todas as classes fossem inicializados antes de qualquer construtor participar.

Inicializadores de campos e blocos de inicialização podem simplificar valores locais, mas também podem esconder trabalho que lança exceção. Evite consultas externas, gravações e outras operações surpreendentes em inicializações de um objeto de domínio simples. Quem usa new deve conseguir compreender o que precisa fornecer e que tipo de falha pode acontecer.

13. Padrão, sem argumentos e construtor com parâmetros

O termo construtor padrão tem um significado específico: ele é fornecido pelo compilador quando a classe comum não declara nenhum construtor. Um construtor sem argumentos escrito por você pode aplicar regras ou delegar a outra forma, mas não é aquele construtor implícito. Essa distinção evita atribuir à JVM uma criação que pertence à compilação.

Ao declarar uma forma com parâmetros, não espere que a forma vazia continue existindo automaticamente. Se ela representa um estado válido e útil, declare-a com os valores que o contrato permite. Não invente valores arbitrários apenas para conservar uma chamada antiga que já não tem informações suficientes.

Um construtor não declara retorno, nem mesmo void. Um método com o nome da classe e retorno void não será chamado automaticamente por new. Quando uma instância parece começar sem os dados esperados, confira essa diferença antes de acrescentar chamadas repetidas de inicialização no main.

14. Encadeamento para validar uma única vez

Sobrecargas podem oferecer conveniência sem duplicar as regras. Um construtor que recebe somente nome pode fornecer quantidade zero ao construtor principal; a versão com nome e quantidade faz a validação comum. Na referência Java 17, a chamada this(...) ou super(...) deve aparecer como primeira instrução quando usada dessa forma.

As duas formas permitidas passam pela mesma verificação. Se amanhã a quantidade máxima do exercício for limitada, a decisão terá um único ponto de atualização. Os testes ainda precisam percorrer cada forma pública de construir, pois uma sobrecarga poderia fornecer um argumento incompatível com a nova regra.

Evite cadeias difíceis de seguir e chamadas circulares entre construtores. Se a lista de combinações crescer muito, talvez a interface precise de outra apresentação, mas não crie um builder para um objeto simples com dois dados. Primeiro mantenha os nomes, a quantidade de parâmetros e o caminho de validação claros.

15. Quando um construtor falha, não finja que houve um objeto válido

Se um construtor lança uma exceção e não termina normalmente, a expressão new não entrega ao chamador um resultado de construção bem-sucedida. Isso permite impedir o uso de uma instância que não atende ao contrato. Apenas imprimir uma mensagem e continuar o corpo normalmente deixa o objeto existir com dados que o próprio código acabou de chamar de inválidos.

O chamador deve tratar a falha em um ponto capaz de explicar o problema ou pedir correção. Um programa de console pode capturar IllegalArgumentException e mostrar a mensagem. Uma biblioteca pode deixar a exceção seguir para a camada responsável. Não capture qualquer exceção apenas para retornar uma instância vazia, a menos que essa política seja explícita e faça sentido no domínio.

Uma falha durante a construção também não desfaz automaticamente efeitos externos já realizados. Se o construtor gravou um arquivo antes de validar o último argumento, essa gravação pode permanecer. Por isso, valide antes de publicar o estado e evite efeitos externos desnecessários no processo. Recuperação de memória e reversão de uma operação de negócio são responsabilidades diferentes.

16. Não publique this antes de terminar a construção

Durante o construtor, o objeto ainda está estabelecendo suas invariantes. Guardar this em uma coleção global, registrar callbacks que podem executar imediatamente ou iniciar uma tarefa que observa os campos pode expor esse estado incompleto. Mesmo em um programa sem threads explícitas, uma chamada indireta pode ocorrer antes do ponto que você imaginava.

Chamar um método sobrescrevível do construtor é uma forma de risco. O despacho pode chegar a uma implementação da subclasse antes que seus campos tenham recebido as inicializações explícitas. O resultado pode ser zero, null ou outro estado intermediário. Para a inicialização, prefira operações que não dependam de uma extensão ainda não construída.

Isso não exige transformar toda classe em uma arquitetura complicada. Um objeto simples pode validar argumentos, atribuir seus campos privados e terminar. Depois, uma rotina externa pode registrar a instância ou iniciar o trabalho que depende dela. Essa separação também torna mais fácil testar o domínio sem acionar serviços inesperados.

17. Final e imutabilidade: proteja também os objetos recebidos

Um campo final impede uma nova atribuição àquele campo depois da inicialização permitida, mas não impede que um array ou uma lista referenciada seja alterada. Um objeto com private final double[] notas não é automaticamente imutável. Se ele guarda o próprio array que o chamador forneceu, esse chamador ainda pode mudar seus elementos por outra referência.

O laboratório copia na entrada e na saída. A primeira cópia evita que o chamador altere o estado por sua referência inicial. A segunda impede que uma consulta entregue o armazenamento interno para modificação. Para doubles, a cópia dos elementos já separa os valores. Para elementos mutáveis, seria necessário definir outro nível de independência.

A cópia tem custo proporcional à quantidade de elementos. Não a retire apenas por parecer repetitiva se ela protege o contrato. Se o volume justificar outra estratégia, considere representações imutáveis ou outra interface e verifique a propriedade dos dados. O ganho precisa ser medido sem eliminar a proteção que o usuário espera.

18. Construtor de cópia: defina o que permanecerá compartilhado

Um construtor que recebe outra instância pode criar uma cópia, mas Java não o fornece automaticamente para uma classe comum. O contrato deve dizer quais dados são duplicados e quais referências podem ser compartilhadas. Strings podem compartilhar conteúdo imutável; uma lista de objetos mutáveis exige uma decisão adicional sobre cada elemento.

O método definir usa a verificação de limites do próprio array para índices inválidos; este exercício não fornece uma mensagem personalizada para essa falha. A construção e a cópia não mudam a regra de acesso posterior. Defina separadamente quais erros cada operação assume tratar.

Clone também não é uma promessa universal de cópia profunda. Em uma matriz de objetos, duplicar o array externo não duplica as linhas nem os objetos internos. Evite usar termos como “duplicar tudo” sem descrever a estrutura concreta. Uma cópia correta é a que atende ao grau de independência combinado.

19. Herança: inicializar a parte comum sem repetir o contrato

Se uma classe base exige um código, uma subclasse não pode ignorar essa necessidade. Ela precisa chamar um construtor acessível da base com um argumento válido. Quando não há chamada explícita, o compilador tenta a forma super() em uma classe comum; se essa forma não existe ou não é acessível, a compilação falha.

A base protege o código; a subclasse protege o título. Isso não significa que você deva usar herança em todo cadastro com campos parecidos. A relação de substituição precisa fazer sentido para as operações. Se duas classes apenas usam um mesmo componente, composição pode manter os contratos mais independentes.

Construtores não são herdados nem sobrescritos. A subclasse declara os seus, com seu próprio nome. Uma anotação Override não transforma um construtor em método herdado. Ao diagnosticar uma falha, confira nome, acesso, lista de parâmetros e a chamada inicial à base.

20. Fábricas nomeadas e listas de parâmetros difíceis de ler

Uma chamada com vários parâmetros do mesmo tipo pode esconder trocas: Pessoa("Ana", "Recife", "Rua A") depende de lembrar a ordem. Nomes claros, tipos adequados e uma interface menor podem ajudar. Em algumas situações, um método de fábrica com nome expressivo comunica uma forma de criação melhor do que outra sobrecarga ambígua.

Uma fábrica não elimina a validação do construtor ou da rotina comum de construção. Ela deve conduzir aos mesmos estados permitidos. Também pode escolher quando criar uma nova instância ou devolver um objeto apropriado, mas essas possibilidades não justificam acrescentá-la a todo exemplo. Para o Produto com nome e quantidade, o encadeamento já resolve a necessidade de forma direta.

Outro caso delicado envolve null e sobrecargas de referências não relacionadas. Uma chamada com null pode ser ambígua quando há construtores que recebem tipos diferentes igualmente aplicáveis. O compilador precisa de uma escolha definida. Em vez de adicionar casts arbitrários nos chamadores, revise se a interface de construção está realmente comunicando alternativas claras.

21. Testar a construção inclui conferir a falha e a independência

Faça testes de estados mínimos válidos, estados típicos e cada argumento inválido. Para quantidade não negativa, zero é válido e menos um é inválido. Para nome obrigatório, null, vazio e somente espaços são casos diferentes. Para raio positivo, zero não é permitido, e NaN precisa de uma verificação que realmente o reconheça.

Nas cópias, o teste deve alterar a origem depois da construção e também alterar o que uma consulta devolveu. Se você testar somente a descrição inicial, uma implementação que compartilha tudo parecerá correta. A independência é um comportamento observado depois de mudanças por outras referências.

Uma validação em um construtor não autoriza os demais caminhos a violarem a mesma regra. Percorra sobrecargas, fábricas e operações de mutação. No próximo tema, setters e outros métodos precisarão preservar invariantes da mesma forma. Não basta que uma instância comece válida e aceite dados incoerentes na primeira atualização.

22. Prática orientada, resoluções e revisão da construção

  1. Produto: escreva dois construtores, um com nome e outro com nome e quantidade. A primeira forma deve delegar quantidade zero. Aceite Caderno com 0 e 3; recuse null, nome vazio e quantidade -1. Mostre as mensagens de falha no main.
  2. Círculo: ofereça raio padrão 1 e raio informado. Valide valor positivo e finito. Compare as áreas para 1 e 2 usando Math.PI. Teste 0, -1 e NaN como recusas.
  3. Cópia defensiva: construa um Boletim com {6, 8}; modifique a entrada original e uma cópia obtida por consulta. O estado do Boletim deve continuar {6, 8}.
  4. Diagnóstico: em uma cópia do exercício, coloque void antes do nome que deveria ser construtor. Explique por que a inicialização automática deixou de ocorrer e restaure a declaração.
Possível solução: círculo com construção validada

O raio padrão é válido segundo o mesmo contrato da forma com parâmetro. O cálculo usa double e a saída de duas casas é uma apresentação; para raios muito grandes, uma aplicação que prometa área finita precisaria limitar o intervalo ou conferir o resultado. O exercício não promete aritmética ilimitada.

Conferir produto, cópia e diagnóstico

O Produto com somente nome começa em quantidade zero. As outras recusas lançam IllegalArgumentException, sem entregar uma construção válida ao chamador. Na cópia defensiva, o Boletim continua mostrando 6 e 8 após as duas tentativas externas de alteração. Uma declaração com void é um método comum; ela não é executada automaticamente por new.

Você pode avançar quando sabe explicar quais estados o construtor aceita, por que cada sobrecarga preserva a regra e quais dados são compartilhados ou copiados. O tema 9 continua com encapsulamento e operações que mantêm a coerência depois da construção.
