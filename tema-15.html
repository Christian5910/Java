1. Do projeto pequeno ao programa distribuído

Até o tema 14, você organizou regras, entradas e armazenamento para que cada parte pudesse ser verificada. A continuação leva esse mesmo cuidado a aplicações com janela, dispositivos móveis e serviços HTTP. Comece identificando o que já pode ser reaproveitado. A regra que recusa uma nota fora de 0 a 10 pode viver numa classe Java sem importar Swing, Android ou Spring. Cada plataforma converte sua entrada e apresenta o resultado de uma maneira própria.

Uma dependência aparece quando uma parte precisa conhecer um tipo, recurso ou comportamento de outra. Se a classe de domínio recebe um JTextField, ela passa a depender de uma biblioteca gráfica e dificulta testes sem tela. Se recebe o valor da nota, preserva um contrato que cabe no terminal, numa janela ou numa requisição. A direção das dependências influencia quais mudanças se espalham pelo projeto e quais ambientes conseguem executar determinada parte.

Este tema usa Java 17 como referência dos laboratórios locais. Os exemplos de módulos exigem um JDK instalado e terminal; o Playground continua dedicado ao seu catálogo de console. Você pode ler e imprimir todo o percurso no site. Quando houver um projeto externo ao navegador, o texto indicará os arquivos para download, os requisitos e uma forma de conferir a execução.

2. Pacote, módulo e artefato têm responsabilidades diferentes

Um pacote organiza nomes e participa do controle de acesso da linguagem. Um módulo nomeado, introduzido pelo sistema de módulos da plataforma, declara dependências e quais pacotes exporta. Um artefato de build é uma unidade publicada ou produzida, como um arquivo JAR identificado por coordenadas Maven. Um projeto pode conter muitos pacotes, produzir um artefato e ainda executar sem um módulo nomeado.

O arquivo module-info.java fica na raiz dos fontes de um módulo. A diretiva requires declara leitura de outro módulo; exports disponibiliza um pacote para uso por outros módulos. Exportar não torna membros privados públicos. Acesso continua sujeito à visibilidade das classes e dos membros. Também não equivale a liberar reflexão sobre todos os detalhes internos. Bibliotecas que precisam de reflexão profunda podem exigir opens, de preferência restrito ao módulo que realmente precisa dela.

Evite acrescentar module-info.java ao primeiro projeto Spring apenas para torná-lo mais organizado. Bibliotecas e plugins possuem requisitos de resolução e reflexão próprios. Primeiro faça o build funcionar, entenda como as dependências entram e decida se a fronteira de módulos resolve uma necessidade do projeto. Consulte a especificação de pacotes e módulos quando precisar conferir as regras de leitura e exportação.

3. Um módulo mínimo que você pode compilar

Crie a pasta src/estudo.core. Dentro dela, salve module-info.java e o diretório br/estudo/core contendo Saudacao.java. O nome do diretório que está imediatamente abaixo de src coincide com o nome do módulo usado pelo comando. A classe pública pertence ao pacote br.estudo.core, que também determina seu caminho relativo. Use exatamente as declarações abaixo em dois arquivos separados.

// src/estudo.core/module-info.java
module estudo.core { exports br.estudo.core; }

// src/estudo.core/br/estudo/core/Saudacao.java
package br.estudo.core;
public class Saudacao {
    public static void main(String[] args) {
        System.out.println("Módulo pronto");
    }
}
javac --release 17 -encoding UTF-8 -d mods --module-source-path src -m estudo.core
java --module-path mods -m estudo.core/br.estudo.core.Saudacao

4. Ler a resolução antes de trocar opções

A saída esperada é Módulo pronto. Se a classe não for localizada, confira a pasta a partir da qual executou o comando, a declaração de pacote e o nome qualificado depois da barra. Se um módulo exigido estiver ausente, a JVM interrompe a inicialização antes de chamar main. Alterar o código da regra não resolve uma dependência que o resolvedor não conseguiu encontrar.

No classpath, classes de bibliotecas tradicionais participam do módulo sem nome. No module-path, JARs modulares declaram seu descritor; alguns JARs sem descritor podem ser tratados como módulos automáticos. Os nomes resultantes e as possibilidades de leitura exigem atenção. Para começar, mantenha um exemplo integralmente no classpath ou um conjunto pequeno de módulos explícitos. Misturar caminhos sem compreender cada entrada costuma produzir mensagens difíceis de relacionar com a intenção do projeto.

O comando jdeps ajuda a inspecionar dependências de classes e artefatos. O resultado observado depende das classes analisadas e das opções utilizadas; recursos carregados por reflexão ou nomes construídos em execução podem exigir configuração adicional. A inspeção apoia a preparação do runtime, mas a confirmação final continua sendo executar os fluxos relevantes com o pacote produzido.

5. Maven e Gradle no trabalho cotidiano

Maven organiza um ciclo de vida com etapas como compile, test e package. O pom.xml declara a identidade do projeto, as dependências e a configuração dos plugins. Gradle descreve tarefas e relações num build próprio. Um projeto deve indicar qual ferramenta usa e sua versão adequada. Aprender os dois ao mesmo tempo não é requisito para acompanhar o laboratório Spring, que usa Maven.

Uma dependência pode trazer outras dependências transitivas. É por isso que adicionar um starter fornece várias bibliotecas sem listar cada uma manualmente. O gerenciamento de versões coordena esse conjunto. Alterar individualmente uma biblioteca gerida pelo framework pode criar incompatibilidades que só aparecem na inicialização. Inspecione a árvore com mvn dependency:tree e leia a recomendação da linha utilizada antes de sobrescrever versões.

O escopo também importa. Uma biblioteca necessária apenas em teste deve ficar no escopo test. Uma implementação de banco pode entrar em runtime quando o código compila usando APIs mais gerais. O artefato que você entrega deve carregar o necessário para executar, com licenças e configuração apropriadas. A pasta de cache local do desenvolvedor não deve ser a única explicação de por que um programa funciona.

6. Recursos, codificação e caminhos portáveis

Um arquivo dentro do JAR é um recurso da aplicação. Um documento criado pelo usuário é um dado externo. Para um modelo de relatório empacotado, use getResourceAsStream com caminho conhecido e trate retorno nulo. Para uma exportação escolhida pelo usuário, receba um Path externo e verifique permissões e falhas. Um recurso dentro do JAR não oferece necessariamente um caminho gravável no sistema de arquivos.

Declare UTF-8 no build e nas operações de texto. Acentos que funcionam numa máquina podem depender da codificação padrão de outra instalação. Use Path.resolve para compor caminhos, em vez de concatenar barras fixas. Diferenças de maiúsculas e minúsculas, nomes reservados e permissões também variam entre sistemas. Teste com o mesmo conjunto de nomes e caracteres nas plataformas que você pretende apoiar.

Configuração como endereço do servidor deve ser fornecida por mecanismo documentado. Evite embutir a pasta do seu computador ou credenciais nos fontes e no JAR. Uma configuração inválida deve gerar uma mensagem que ajude o usuário a corrigir o valor sem revelar segredos. Separar configuração de regra prepara a distribuição desktop e a configuração externa do Spring Boot.

7. Contrato compartilhado sem acoplar as telas

Imagine uma operação registrarNota que recebe matrícula e valor. O domínio valida a matrícula, verifica a faixa e devolve um resultado de negócio. O adaptador Swing lê o campo e atualiza um rótulo. O adaptador HTTP transforma o JSON em uma chamada e escolhe o status. O domínio permanece responsável pela regra mesmo que exista uma validação antecipada no formulário.

O compartilhamento precisa respeitar a API disponível em cada destino. Android possui runtime e bibliotecas próprias; uma classe que compila para Java 17 no servidor pode chamar uma API ausente no aparelho. Você pode compartilhar fontes ou um artefato de domínio compatível, mantendo adaptadores separados. Anotações JPA, componentes gráficos e referências ao contexto Android ficam fora dessa fronteira quando não fazem parte da regra comum.

Antes de dividir tudo em muitos módulos, escreva um teste da regra sem levantar a aplicação. Se o teste exige uma janela ou banco para comparar 6,5 com a nota mínima, existe uma dependência que merece revisão. Uma separação pequena, visível em pacotes e construtores, costuma ser suficiente para demonstrar o contrato antes de introduzir novos artefatos.

8. Prática: preparar uma base reaproveitável

Compile o módulo da saudação e registre os comandos e a saída. Depois acrescente uma classe pública Nota com um método avaliar que receba texto e recuse valor vazio, não numérico, infinito ou fora da faixa. Preserve essa validação no domínio. Execute um teste de 7, de 6,5 e de uma recusa, sem carregar uma biblioteca de interface.

Faça uma segunda experiência controlada: renomeie o pacote sem mover o arquivo e tente compilar a partir de uma pasta de saída vazia. Com a opção -m, o javac recompila só os arquivos mais novos que as classes já geradas e pode terminar sem erro sobre uma saída antiga. Leia a mensagem e corrija a estrutura. Por fim, descreva quais dados seriam recurso do JAR e quais seriam documentos do usuário. O trabalho está concluído quando outra pessoa consegue compilar a pasta extraída com os requisitos declarados, explicar a dependência de cada parte e repetir as verificações.

Para repetir esta prática com um ponto de partida que já compila, um roteiro passo a passo, as falhas controladas, critérios de conclusão e uma possível solução em pasta separada, baixe o laboratório de módulos e build. Ele executa no seu computador, com JDK 17 ou superior, e não no Playground.

Um pacote exportado permite acessar um campo private de outra classe?

Não. exports abre o pacote para acesso normal entre módulos, preservando as regras de visibilidade da linguagem. Reflexão profunda possui regras próprias e não deve ser liberada indiscriminadamente.
